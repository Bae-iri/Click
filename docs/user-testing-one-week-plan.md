# 클릭 사용자 테스트 및 검증: 1주 실행 계획

- 작성일: 2026-11-07
- 기간: 착수일부터 7일, D1~D7. 일정표의 날짜는 실제 시작일에 맞춰 입력한다.
- 목적: 현재 MVP의 사용자 효과와 주요 결함을 확인하고, 수정·재검증 결과까지 제출 가능한 형태로 남긴다.
- 운영 가정: 팀원 2명, 현재 동작을 확인한 삼성 테스트폰 1대, 하루 약 4~6시간. 다른 기종 지원을 이번 주 결과로 주장하지 않는다.
- 평가 성격: **소규모 탐색적 비교 평가 + 정해진 사례에 대한 기술 검증**. 통계적으로 효과를 확증하거나 전체 제품의 안전성을 입증하는 연구로 표현하지 않는다.
- 현재 상태: **계획서**. 아래 표본 수·시험 수는 예정이며, 실제 수집·통과 결과가 아니다.

## 1. 이번 주에 할 일과 제외할 일

| 이번 주 필수 | 이번 주 제외 또는 후속 과제 |
| --- | --- |
| 글자 크기·화면 밝기·미디어 음량의 실제 결과 확인 | 지원 설정 전체·모든 기종·모든 OS 검증 |
| 직접 수행과 클릭 사용의 성공률·어려움·시간 비교 | 수십 명 규모의 확증 연구, 유의한 p값 확보 |
| 첫 튜토리얼 이해와 중지·내용 수정 조작 확인 | 음성 대 글 입력, 안내 대 자동 모드의 별도 사용자 비교 실험 |
| 의도 이해·메뉴 선택·실행·완료 판단의 오류 구분 | AI2 개선 효과·개인화 효과의 인과 검증 |
| 알려진 화면 오류·권한·네트워크·중지 반례 시험 | 자연 이용률·장기 학습·1주 뒤 유지율 검증 |
| 테스트 데이터로 개인정보 전송·저장·철회·삭제 확인 | 계약·외부 업체 보관·백업 삭제가 미확인인 상태에서 개인정보 검증 완료 선언 |

새로운 분석 SDK, 녹음·화면 녹화 기능, 대규모 로그 수집 기능은 이번 주에 개발하지 않는다. 수기 기록표와 기존에 확인 가능한 기술 기록을 사용한다. 기존 운영 기록이 연구에 필요한 항목을 모두 제공한다고 가정하지 않는다.

기존 [AI 품질 평가 기준](./ai-quality-evaluation.md)의 독립 판정·개인정보·필수 반례·평가 상태 원칙을 따른다. 이 계획의 축소된 시험 범위가 기존 제품 인수 기준을 대체하지 않는다. 합성 반례 시험과 실제 사용자 결과도 합산하지 않는다.

## 2. 가설과 검증 방법

주가설은 U1 하나로 고정한다. U2~U4는 보조·탐색 평가이고, T1~T4는 기술 요구조건이다. 모든 항목에 p값을 붙이지 않는다.

| ID | 가설 또는 요구조건 | 방법 | 수집할 핵심 데이터 |
| --- | --- | --- | --- |
| U1 · 주가설 | 클릭을 사용하면 연구자의 도움 없이 설정 작업을 완료하는 비율이 높아진다. | 동일 참가자의 직접 수행·클릭 사용 비교. **주검정 과제는 글자 크기**, 밝기·음량은 보조 결과로 보고 | 실제 성공, 연구자 도움, 실패·포기·시간 초과, 설정 전후 값 |
| U2 | 클릭을 사용하면 작업을 더 쉽게 느끼고 부담이 줄어든다. | 작업 직후 쉬움 점수, 조건 종료 후 부담 점수 비교 | 쉬움 1~5점, 부담 1~5점, 이유 한 문장 |
| U3 | 클릭을 사용하면 작업 완료 시간이 줄어든다. | 같은 사람이 두 조건 모두 성공한 같은 과제의 시간 비교 | 시작·종료, 경과 시간, 비교에 포함된 사람 수 |
| U4 | 첫 튜토리얼 후 지원 범위와 자동 모드를 이해하고 중지·내용 수정을 사용할 수 있다. | 설명 확인 질문 3개, 중지·수정 과제 각 1회 | 최초 답변, 재설명 여부, 최초 조작 성공, 도움 여부 |
| T1 | 의도를 올바르게 구분하고, 모호하거나 미지원인 요청에는 확인·중단을 선택한다. | 사전 정답이 있는 문장 시험 및 일부 음성 입력 시험 | 정답·예측 의도, 방향, 추가 질문·보류, 음성 입력 이용 가능 여부 |
| T2 | 실제 화면의 올바른 대상을 안내·조작하고, 실제 변화가 있을 때 결과를 확인한다. | 정상 실행과 화면 반례 시험 | 정답·선택 대상, 조작 전후 값, 잘못된 하이라이트, 변경 없는 완료 안내 |
| T3 | 오류·화면 변경·중지·권한 문제에서 오래된 안내나 새 자동 동작을 이어가지 않는다. | 오류 주입·중지·화면 변경 시험 | 복구 또는 안전 중단, 반복 안내, 중지 후 새 동작, 재연결 상태 |
| T4 | 개인정보를 고지한 범위대로 처리하고, 계정 접근·동의 철회·탈퇴를 올바르게 처리한다. | 가짜 개인정보·테스트 계정으로 전송·저장·처리 결과 대조 | 전송 대상과 필드 종류, 금지 정보 검출, 권한 없는 접근, 철회·삭제 결과 |

**U2 설문은 이번 평가를 위한 자체 문항이다. SUS 또는 NASA-TLX 점수라고 부르지 않는다.** 본실험 중 수행 방법을 계속 말하게 하는 생각 말하기는 요구하지 않는다. 이유와 의견은 작업 후 질문해 시간 측정에 미치는 영향을 줄인다.

## 3. 참가자와 모집 마감

| 구분 | 인원 | 운영 원칙 |
| --- | --- | --- |
| 파일럿 | 2명 | 실제 목표 사용자에 가까운 사람. 본실험 수치에 합산하지 않음 |
| 본실험 | **10명 목표** | 휴대폰 설정을 혼자 바꾸는 데 어려움을 느끼는 목표 사용자. 개발팀·기존 숙련 사용자는 제외 |
| 예비 | 2명 | 미참석 대체용. 유의한 결과를 얻기 위한 추가 모집에 사용하지 않음 |
| 실행 하한 | 8명 | 운영상 목표일 뿐 통계적으로 충분한 인원이라는 뜻이 아님. 부족해도 일정을 연장하지 않고 실제 인원·한계를 보고 |

- 총 모집 목표는 파일럿 2명 + 본실험 10명 + 예비 2명 = 14명이다.
- D1에 최소 본실험 8명의 시간대를 확정하고, D2 종료까지 남은 시간대를 확정한다.
- 본실험은 D3·D4에 하루 5명, **1인 60분 슬롯**으로 예약한다. 필요한 대체 세션은 D5 오전까지만 진행한다.
- 본실험 상한은 10명으로 고정한다. 중간 p값을 보고 인원을 늘리거나 조기에 종료하지 않는다.
- 연령대와 설정 사용 경험을 기록하되 이번 표본으로 연령·숙련도 집단 간 통계 비교를 하지 않는다. 목표 사용자를 구하지 못해 다른 집단을 평가하면 제목과 결론에 그 집단을 명시한다.
- 대학생으로만 수행한 평가를 고령층 사용자 효과로 해석하지 않는다.

## 4. D1~D7 일정과 담당

담당 A는 모집·진행·설문·결과 정리를 맡고, 담당 B는 기기·독립 관찰·기술 시험·결함 수정을 맡는다. 본실험 시간에는 두 명이 함께 진행한다. 수정·시험은 참가자가 기기를 사용하지 않는 시간에 한다.

| 날짜 | 담당 A | 담당 B | 당일 종료 조건 |
| --- | --- | --- | --- |
| **D1: 범위·모집·정답 고정** | 모집과 예약, 참여 설명, 과제 문구·관찰표 작성 | 평가할 기기·OS·서버·모델 범위 확인, 테스트 계정 준비, 기술 사례와 정답 작성 | 본실험 8명 이상 예약, 평가 범위·주가설·기록 양식 확정 |
| **D2: 파일럿·수정·버전 고정** | 파일럿 2명 진행, 문구·시간·설문 점검 | 필수 반례·개인정보 선점검, 차단 결함 수정, 수정 사례 재검증 | 필수 선점검 통과, 제한 시간 확정, 본실험 버전 V1과 서버 설정 고정 |
| **D3: 본실험 전반** | 참가자 5명 진행 | 독립 결과 확인·기록·설정 복원, 세션 후 자료 확인 | 5명분 기록 대조, 누락 확인. 과제·평가 기준 변경 금지 |
| **D4: 본실험 후반** | 참가자 5명 진행 | 독립 관찰·기록, 기술 사례 시험 병행은 세션 외 시간에만 | 10명 목표 완료, 직접→클릭 / 클릭→직접 순서 균형 확인 |
| **D5: 결함 재현·수정** | 필요 시 오전 대체 세션, 인터뷰 분류, 데이터 정리 | V1 결함 재현, 수정 버전 V2 작성, 기술 시험 완료 | 결함별 재현 조건·영향·수정 여부 기록. 사용자 결과는 V1 자료로 보존 |
| **D6: 재검증·분석** | 성공률·시간·설문 분석, 필요 시 2~3명에게 수정 UI만 짧게 확인 | V2 필수 반례 회귀, 실제 설정값·중지·개인정보 재점검 | V1 사용자 결과와 V2 재검증 결과 구분. 미해결·미확인 항목 확정 |
| **D7: 보고·제출** | 결과표·해석·한계 작성 | 기술 결과·버전·결함 목록 검수 | 최종 보고서와 제한된 결과 데이터, 미해결 목록 제출 |

**1주 뒤 재방문 평가는 이번 일정에서 제외한다.** D6에 기존 참가자가 수정 UI를 다시 봤다면 이는 재검증 자료이며, 장기 기억·유지율이나 독립적인 신규 사용자 효과의 근거로 쓰지 않는다.

## 5. 본실험: 조건·과제·성공 기준

### 5.1 비교 조건

| 조건 | 방법 | 통제 |
| --- | --- | --- |
| A · 직접 | 클릭 없이 휴대폰 기본 기능으로 수행 | 설정 검색·빠른 설정 사용 허용. 연구자 조작 도움·인터넷 검색은 허용하지 않음 |
| B · 클릭 | 클릭을 통해 수행, **자동 모드 켜짐으로 통일** | 말 또는 글 중 편한 방식 사용 가능. 선택과 중간 변경을 기록하고 입력 방식의 우열은 분석하지 않음 |

- 본실험은 계정 로그인·권한 설정이 준비된 상태에서 시작한다. 튜토리얼은 참가자가 처음 확인한다. 따라서 가입·권한 설정 전체를 혼자 완료하는 비율은 본실험의 측정 대상이 아니다. 해당 흐름은 파일럿과 기술 점검에서만 평가한다.
- 두 조건 시작 전에 같은 튜토리얼·기본 조작 연습을 제공한다. 실험 과제의 설정 경로는 시연하지 않는다.
- 튜토리얼 뒤 지원 범위·자동 조작·중지 방법을 물어 최초 답변을 기록한다. 이해가 부족하면 재설명하고 그 횟수를 남긴 뒤 실험한다.
- 앱의 자동 모드 설명·동의 절차는 건너뛰지 않는다.
- 이 비교는 **준비·연습을 마친 뒤 자동 모드를 포함한 클릭 전체의 효과**를 평가한다. 하이라이트나 음성 입력만의 효과로 표현하지 않는다.

### 5.2 수행 순서

- 참가자를 사전에 무작위로 배정하되 A→B 5명, B→A 5명이 되도록 한다. 최종 8명이면 4명씩 맞춘다.
- 과제는 글자 크기·밝기·음량의 순서를 참가자 사이에 고르게 배정한다. 같은 참가자는 두 조건에서 같은 과제 순서를 따른다.
- 매 과제마다 같은 홈 화면과 같은 시작값으로 복원한다. 클릭 조건에서만 커서를 표시한다.
- 기기·언어·네트워크·화면 방향·읽을 수 있는 시작 글씨 크기를 통제한다. 밝기는 자동 밝기를 끈다.
- 반복하면서 메뉴를 배우는 영향이 남으므로 순서별 결과도 함께 제시한다. 순서 균형이 학습 효과를 완전히 제거한다고 주장하지 않는다.

### 5.3 과제

| ID | 읽어줄 문구 | 독립 성공 기준 |
| --- | --- | --- |
| FONT | 현재보다 글자 크기를 한 단계 크게 바꿔주세요. | 실제 글자 크기 단계가 정확히 한 단계 증가하고 참가자가 완료 선언 |
| BRIGHTNESS | 화면을 지금보다 밝게 바꿔주세요. | 자동 밝기가 꺼진 동일 조건에서 실제 밝기 값이 시작값보다 증가하고 참가자가 완료 선언 |
| VOLUME | 미디어 소리를 한 단계 크게 바꿔주세요. | 벨소리가 아닌 실제 미디어 음량이 정확히 한 단계 증가하고 참가자가 완료 선언 |

모든 시작값은 최댓값보다 낮고 과제를 수행할 수 있는 범위로 정한다. 큰 글씨가 필요한 참가자에게 읽기 어려운 시작값을 강제하지 않는다. 한 참가자에게 정한 기준은 두 조건에서 같게 한다. 시험 후 기기 설정을 원래대로 복원한다.

### 5.4 시간·결과 판정

- 잠정 제한 시간: **과제당 180초**. 파일럿에서 현실성이 없는 경우 D2에 한 번 조정하고, 확정한 값을 기록한다. 본실험 시작 후 변경하지 않는다.
- 시작: 과제를 읽어준 뒤 ‘시작하세요’라고 말한 시점. 요청 입력·음성 변환·서버 대기·설정 이동 시간을 포함한다.
- 종료: 실제 목표가 적용되고 참가자가 완료를 선언한 시점. 완료 선언만으로 성공 처리하지 않는다.
- 연구자의 경로 설명·대리 조작 없이 완료해야 독립 성공이다. 클릭의 안내·자동 조작은 허용한다.
- 연구자에게 도움을 요청하면 독립 성공 판정은 종료한다. 이후 도와서 완료했는지는 별도로 기록한다.
- 시간 초과·포기·잘못된 결과·앱 오류는 분모에서 조용히 제외하지 않는다. 참여 철회는 작업 실패와 별도 상태로 기록하고 사전 동의한 자료 처리 절차를 따른다.
- 관찰자가 실제 설정 단계·기기 설정값을 확인한다. 앱의 DONE·성공 메시지·자체 로그만으로 정답을 정하지 않는다. 확인할 수 없으면 `UNVERIFIABLE`로 남기고 독립 성공에 포함하지 않는다.

### 5.5 60분 진행표

| 분 | 내용 |
| --- | --- |
| 0~5 | 참여 설명·동의·사용 경험 확인 |
| 5~13 | 첫 튜토리얼·기본 조작 연습·이해 질문 3개 |
| 13~28 | 첫 조건: 3과제, 설정 복원, 과제별 쉬움 질문 |
| 28~33 | 조건별 부담 질문·휴식·상태 복원 |
| 33~48 | 두 번째 조건: 3과제, 설정 복원, 쉬움·부담 질문 |
| 48~54 | 클릭 중지·요청 내용 수정의 짧은 조작 확인 |

휴식·기기 복원·인터뷰 시간은 과제 시간과 구분한다. 피로하거나 중단을 원하면 계속하도록 압박하지 않는다.

### 5.6 질문 문구

- 튜토리얼 후: ‘클릭이 지금 도와줄 수 있는 작업은 무엇인가요?’, ‘자동 모드를 켜면 무엇이 달라지나요?’, ‘멈추려면 어떻게 하나요?’
- 과제 후: ‘방금 작업은 얼마나 쉬웠나요?’ — 1 매우 어려움 ~ 5 매우 쉬움.
- 조건 후: ‘이 방법으로 작업하면서 머리를 쓰고 집중하는 부담이 얼마나 컸나요?’ — 1 매우 낮음 ~ 5 매우 높음.
- 인터뷰: ‘어디에서 가장 헷갈렸나요?’, ‘안내가 맞는지 어떻게 판단했나요?’, ‘실제로 사용할 것 같은 상황과 사용하지 않을 상황은 무엇인가요?’
- 중지·수정: 명확한 안내가 있는 테스트 작업에서 ‘지금 진행을 멈춰주세요’, 실행 확인 전 ‘작업 내용을 바꿔주세요’라고 요청한다. 최초 조작·도움·중지 뒤 새 자동 동작 여부를 기록한다. 중지 의도 과제는 성공률 비교 6개 과제에 합산하지 않는다.

## 6. 기술 시험: 이번 주의 고정 최소 세트

단위·회귀 검사는 기존 도구를 재사용한다. 아래의 실제 화면·독립 결과 확인을 단위 테스트 통과로 대체하지 않는다. 최종 시험은 버전과 정답을 고정한 뒤 수행하고, 오류 수정 뒤에는 수정 전후 결과를 구분해 남긴다.

| 묶음 | 규모 | 내용 |
| --- | --- | --- |
| 의도 | 36문장 | 명확한 지원 요청 18개: 3작업 × 증가·감소 × 표현 3종. 모호한 요청 9개, 미지원·위험 요청 9개. 정답은 실행·추가 질문·중단으로 구분 |
| 음성 경로 | 위 문장 중 12개 추가 실행 | 기기 내 음성 인식 경로로 입력. 입력 불가·변환 실패·의도 실패를 구분. 원음은 기본적으로 저장하지 않음 |
| 정상 실행 | 24회 | 3작업 × 안내·자동 2모드 × 홈·대상 앞단계 2시작 위치 × 2반복. 실제 전후 값·종료 상태 확인 |
| 필수 반례 | 아래 16개 시나리오 묶음 | 잘못된 안내·완료·중지 처리와 화면·권한 문제 재현 |
| 개인정보·접근 통제 | 아래 6사례 | 실제 개인정보가 아닌 테스트 데이터로 확인 |

36문장은 수정·튜닝에 사용한 문장과 분리된 최종 평가용으로 준비한다. 두 사람이 예측 결과를 보기 전에 정답을 확인한다. 음성 12회는 36문장의 추가 경로 시험이며, 서로 독립인 48개 의도 표본으로 합산하지 않는다. 숫자는 일정 안에서 점검할 범위를 정한 것이며 정확도 보장에 필요한 표본 수가 아니다.

공통 환경은 한 번 기록하고 각 과제 행에는 `environment_id`만 연결한다. 모든 행에 버전을 다시 입력하지 않는다. 연구용 ID는 앱 계정·전화번호와 분리한다. 연결표가 있으면 익명 데이터라고 부르지 않는다.

| 파일·기록 | 단위 | 필수 항목 | 담당·시점 |
| --- | --- | --- | --- |
| `environment.md` | 평가 버전·환경별 1개 | 환경 ID, 앱 버전·APK 해시, 서버 revision, graph·모델·프롬프트 버전 또는 확인 불가 표시, 기종·OS·언어·네트워크, 제한 시간·시작 상태 | B, D2 및 변경 시 |

### 7.2 값과 분류 기준

- `cohort`: PILOT / MAIN. 파일럿·재검증 참가자를 MAIN에 합산하지 않는다.
- `condition`: A_DIRECT / B_CLICK_AUTO. 안내 모드 기술 시험은 별도로 표시한다.
- `ground_truth`: TARGET_REACHED / NOT_REACHED / UNVERIFIABLE.
- `outcome`: INDEPENDENT_SUCCESS / ASSISTED_SUCCESS / TIMEOUT / WRONG_RESULT / USER_STOPPED / SYSTEM_ERROR / UNVERIFIABLE / WITHDRAWN.
- `error_stage`: INPUT / INTENT / TARGET / ACTION / VERIFICATION / RECOVERY / PERMISSION / NETWORK / UI / NONE / UNKNOWN.
- `input_mode`: VOICE / TEXT / MIXED / NOT_APPLICABLE. 직접 조건에서 입력 방식은 해당 없음이다.
- `status`: PASS / FAIL / NEEDS_DATA. 시험할 수 없거나 근거가 없는 사례는 PASS가 아니다.
- `feedback.csv`의 공통 이해·중지·수정 결과는 `condition=SESSION`인 별도 행에 한 번만 기록한다. A/B 행에는 해당 조건의 부담만 기록한다. 특정 문항과 무관한 셀은 빈칸으로 두고 실제 미측정과 구분한다.
- 설정값의 단위는 환경 기록에 고정한다. 글자 크기는 단계, 밝기는 기기가 보고하는 단위, 미디어 음량은 단계로 기록하고 서로 다른 단위를 섞지 않는다.

운영 로그가 D6까지 남아 있을 것으로 가정하지 않는다. 세션 직후 동의 범위의 최소 측정값과 독립 관찰 결과를 대조해 기록한다. 연구 편의를 위해 운영 데이터 보관 기간을 임의로 늘리지 않는다.

원음·전체 화면 녹화·자유 입력 원문은 기본 수집에서 제외한다. 연락처가 필요하면 분석 자료와 분리하고, 접근자·보관 기간·삭제일을 D1에 정해 참여 설명에 포함한다. 기존 ‘클릭 개선 참여’ 동의를 연구 참여 동의로 대신하지 않는다.

## 8. 분석: D6에 끝낼 수 있는 범위

### 8.1 반드시 작성할 표

1. 참가자 수: 모집·파일럿·본실험·완료·미참석·철회. 실제 순서 배정 인원과 버전별 인원.
2. 과제별 결과: A/B 각각 독립 성공 `n/N`, 도움 후 성공·시간 초과·오류·확인 불가 건수. 목표 10명이면 조건당 과제 30회, 전체 60회이며 **참가자는 여전히 10명**이다.
3. 주과제 짝 비교: 둘 다 성공 / 직접만 성공 / 클릭만 성공 / 둘 다 실패의 2×2 표와 성공률 차이(%p).
4. 쉬움·부담: 조건별 분포·중앙값, 같은 참가자의 변화. 자체 문항이라는 한계 명시.
5. 시간: 두 조건 모두 성공한 같은 과제의 참가자 수, 시간 중앙값, 참가자별 시간 차이. 전체 종료 시간·실패 원인도 별도로 보고.
6. 기술 결과: 각 사례의 버전·실행 수·실패·미측정. 사용자 시도, 합성 사례, 동일 사례 반복 수를 합산해 제품 정확도로 부르지 않음.
7. 결함: 재현된 중요 결함, 수정·재검증 완료, 미해결, 근거 부족 항목.

### 8.2 통계 해석

- 이번 주 결론의 중심은 **관측된 개선 폭·짝별 결과·실패 원인과 표본의 한계**다.
- 주과제의 조건별 성공률에는 참가자 단위 95% 이항 정확 신뢰구간을 제시할 수 있다. 이것을 두 조건 차이의 신뢰구간이라고 표기하지 않는다.
- 과제·방법을 D2에 고정한 경우에만 주과제의 정확 McNemar 양측 검정을 참고용으로 계산한다. p값은 탐색 결과이며 효과 확증이나 제품 승격 근거로 단독 사용하지 않는다.
- U2~U4와 다른 과제의 p값을 여러 개 계산해 유의한 항목만 고르지 않는다. 이번 계획에서는 분포·변화량·사례 중심으로 보고한다.
- 실패를 성공 소요 시간 180초로 바꿔 평균 내지 않는다. 두 조건 모두 성공한 사람의 시간 결과를 전체 사용자 시간 단축으로 일반화하지 않는다.
- 0건의 오조작·유출을 모집단 위험 0%로 해석하지 않는다. 동일 기기·화면의 반복을 독립적인 새 사용자 표본으로 세지 않는다.
- 적은 인원·기종 한정·튜토리얼 이후 조건·학습 효과·입력 방식 선택·자체 설문·미측정 환경을 한계에 명시한다.

## 9. 진행·수정·판정 규칙

### 9.1 D2의 본실험 진입 조건

- 실제 참가자가 수행할 세 과제의 정상 경로와 필수 중지 동작을 확인한다.
- 필수 반례에서 잘못된 대상·방향 안내, 변경 없는 완료, 취소된 작업 재개, 개인정보·권한 위반 등 기존 품질 기준의 즉시 실패가 재현되면 본실험 진입을 보류한다.
- 치명적 위반을 시간 단축·높은 평균 성공률로 상쇄하지 않는다.
- 당일 수정으로 해결할 수 없으면 해당 조건의 사용자 실험을 중단하고 파일럿·기술 진단 결과를 제출한다. 검증되지 않은 상태로 인원을 채우지 않는다.
- 범위를 줄여 실험할 필요가 있으면 **주평가 결과를 보기 전에** 제외 작업·이유·변경된 제목을 고정하고 해당 범위만 보고한다.

### 9.2 본실험 중 버전 관리

- APK뿐 아니라 서버·모델·프롬프트·graph·주요 설정을 V1으로 고정한다. 서버 배포와 자동 경로 변경도 평가 중에 섞이지 않게 한다.
- 본실험 도중 중대한 결함이 나오면 관련 실험을 멈추고 재현·수정한다. 수정 버전은 V2로 구분하고 V1/V2 결과를 조용히 합산하지 않는다.
- 이미 같은 과제를 한 사람의 V2 재시험은 회귀 확인으로 기록한다. 새로운 독립 참가자처럼 세지 않는다.
- 기기 고장 등 실험 진행 문제와 제품 오류를 구분한다. 누락·제외·대체 이유를 남긴다.

### 9.3 D7 판정 문구

| 상태 | 허용되는 결론 |
| --- | --- |
| 사용자 개선 관측 + 지정 기술 사례 통과 | ‘지정 기기·작업·참가자 범위에서 개선을 관측했고, 열거한 사례의 재검증을 완료했다.’ |
| 사용자 결과가 혼재하거나 표본·환경·근거 부족 | ‘효과는 확정하지 못했으며 추가 자료가 필요하다.’ 필요한 대상을 구체적으로 기재 |
| 필수 반례·개인정보·접근 통제 위반 재현 | 해당 항목 FAIL. 수정 전후와 미해결 영향을 명시하고 관련 배포·평가를 보류 |

이번 주 시험 전체를 통과해도 ‘모든 사용자·설정·기종에서 검증 완료’, ‘위험 없음’, ‘개인정보를 전혀 수집하지 않음’이라고 쓰지 않는다. 전체 제품의 PASS/FAIL/NEEDS_DATA는 상위 품질 기준과 실제 증거 범위에 따라 판단한다.

## 10. D7 제출물과 완료 체크

- [ ] 계획 대비 실제 참가자·기기·일정·버전 범위와 제외 사유.
- [ ] 주과제의 짝별 결과, 세 과제 전체 성공·실패·시간·설문 표.
- [ ] 튜토리얼 이해·중지·수정의 최초 성공과 재설명 결과.
- [ ] 기술 사례별 결과와 독립 판정 근거, 수정 전후 재검증 목록.
- [ ] 개인정보·계정 접근·철회·삭제의 확인 완료 및 미확인 항목.
- [ ] 미해결 결함과 다음 검증의 우선순위. 장기 이용·다기종·더 큰 사용자 표본은 후속 과제로 명시.
- [ ] 민감정보가 없는 요약 보고서. 원자료는 권한을 제한한 별도 보관 위치와 보관·삭제 책임자를 기록.

## 11. 방법론·기존 문서 참고

- [프로젝트 AI 품질 평가·정답 데이터 기준](./ai-quality-evaluation.md): 독립 정답, 평가 데이터 구분, 필수 반례, 평가 상태. 기존 보류된 임의 정확도·지연 목표를 이 계획에서 다시 합격선으로 사용하지 않는다.
- [통합 검증](./integration-verification.md): 기존 계약 시험 재사용. 실제 권한·화면·설정값 검증을 대신하지 않음.
- [GOV.UK 사용성 벤치마킹](https://www.gov.uk/service-manual/measuring-success/usability-benchmarking-a-website-or-whole-service): 실제 목표 사용자, 정답이 있는 과제, 성공·시간·주관 평가. 본 문서의 인원·시간은 1주 운영 제약에 맞춘 내부 계획이다.
- [NIST McNemar 검정](https://itl.nist.gov/div898/software/dataplot/refman1/auxillar/mcnemar.htm): 동일 참가자의 두 이항 결과 비교. 본실험의 충분한 검정력을 보장하는 인용이 아님.
- [NIST AI 신뢰성 특성](https://airc.nist.gov/airmf-resources/airmf/3-sec-characteristics/): 정확성·신뢰성·통제·개인정보를 함께 평가하는 방법론 참고.
