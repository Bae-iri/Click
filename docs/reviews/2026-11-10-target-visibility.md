# Reveal Settings targets before highlighting

The user reported Display being highlighted while the row was cut off at the screen edge. A native `visibleToUser` flag does not guarantee that its entire clickable row is visible. Guide rendering previously proceeded without checking the enclosing list viewport.

Native Settings tap targets (including proposed tap confirmations) now check their row and vertical scroll ancestor before presentation or automatic execution. A row within 24 dp of the list's top/bottom gets a short 96 dp scroll, capped at one quarter of the viewport. At a confirmed list boundary a fully exposed row may remain without optional padding. Text targets include their clickable parent row; horizontal collections, ranges, mismatched windows/bounds and vision-derived targets are excluded.

The native executor reads the foreground window again and requires the original package, window, target and geometry. The gesture avoids Click overlays, sliders, checkable controls and input fields. Scrolling suppresses highlight, confirmation, narration and target-action binding until a fresh observation is sent. The existing manual-override contract invalidates pre-scroll guidance; scrolling is never submitted as a successful tap or setting change. The server must select new target coordinates. Two failed attempts lead to one explicit retry screen, and paused/cancelled/replaced tasks cannot resume through a delayed callback.

This is shared Settings menu behavior, not a Display label special case. No backend change or redeployment is required. Nine geometry/lifecycle regressions were added; all 554 release Android unit tests pass. Device build, integration checks and native measurements are recorded in the accompanying evidence JSON.

The current app integration passed all 630 unit tests with shared fixtures present and Kakao initialization disabled for JVM tests only. The APK was then rebuilt with the existing real login configuration. Final focused checks cover the final executor diagnostics and preserve the launcher's original gesture lanes.

On the connected phone, the opt-in native test used the actual app observation boundary, placed Display at the top edge, and invoked the new native executor. The target label moved from y=317–369 to y=727–785 and the new geometry required no further reveal. No target was clicked, setting value written, or server request sent. An initial probe based on a separate UiAutomation observation was rejected; the final probe consumes the same native snapshot boundary as production rendering. Bottom-edge direction is covered by a unit regression; it was not physically remeasured. This is a native scroll measurement plus mocked guide lifecycle checks, not a new end-to-end Jev task completion claim.
