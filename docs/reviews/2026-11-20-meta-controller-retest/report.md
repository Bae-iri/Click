# 공통 오류 수정 후 MetaController 재실험 — 2026-11-20

**공통 오류 두 곳은 수정·검증했다. B는 시험 화면에서 복구 가능성을 보였지만 기본 활성화는 여전히 NO-GO다.** 실제 Gemini로 수행한 72회에서 목적 상태 도달은 A 20/36, B 33/36, 네이티브 완료 검증 제시는 A 6/36, B 7/36이었다. 기록으로 확인된 모델 호출은 A 58회, B 79회다. 전송 실패 4건은 공급자 기록이 없어 전체 호출 수를 확정할 수 없다. 공급자 시간 초과·모델 출력 검증 실패·전송 실패가 포함된 기술적 비교이며, 안정적인 속도 개선이나 실제 앱의 범용성 향상을 입증한 결과는 아니다.

이번에는 실기기를 사용하지 않았다. **실제 Android 에뮬레이터의 회귀 검사**, **경로를 아는 테스트 계획기의 72회 통제 검사**, **실제 Gemini와 합성 화면의 72회 비교**를 구분했다. 마지막 비교는 실제 앱의 터치나 실사용자 실험이 아니다. 기존 FE 디자인과 기본 CURRENT 정책을 유지했다.

## 공통 수정

1. **동일한 관찰 조건으로 실행 재검사:** 결과 텍스트의 포함·정렬 조건을 불변의 로컬 ProjectionSpec으로 보관하고 실행기가 같은 조건으로 새 화면을 읽는다. 지문 검사를 생략하지 않는다. 화면·좌표·선택 상태·창·비밀번호 등 실제 변화는 계속 거절한다. 서버 JSON 규격에는 새 필드를 추가하지 않았다.
2. **메뉴 존재와 최종 도착 구분:** 메뉴·버튼이 보이는 사실로 탐색 완료를 선언하지 않는다. 목적 화면의 공개 비조작 텍스트, 필요한 선택·체크 상태 또는 명시적인 검색창 열기 상태를 검사한다. 잘못된 완료 조건만 보류하면서 유효한 다음 동작은 유지한다. 이미 저장된 잘못된 조건도 진행 중 작업에서 해제·재결합할 수 있고 작업 목표·진행·기록과 사용자가 확인한 완료는 보존한다.

실제 Android 접근성 트리에서 같은 시험 화면은 기본/확장 관찰의 지문이 다름을 재현하고, 수정된 실행기로 버튼 조작이 수락되는 것을 확인했다. 이동 전 메뉴는 완료로 인정하지 않고 이동 후 같은 이름의 목적 화면 제목은 인정했다. 최종 APK 검사 1개, AppTask 단위 검사 119개, 관련 Backend 검사 191개와 Android Lint를 통과했다. 테스트 로그와 범위는 아래 산출물에 보존했다.

## 실제 Gemini 비교

고정된 여섯 작업 × 정상/무효/지연 × 두 반복 × A/B = 72회, 36쌍이다. 각 쌍의 실행 순서를 교차했다. A와 B는 공통 수정, 목표, 관찰, 계획기, 보호 정책을 공유한다. B의 MC-v0 정책은 조정하지 않았다. 학습된 UIAnchor reflector 전체 재현은 아니다.

Gemini 3.8 Flash에 매번 현재 공개 관찰과 실제 누적 시도 기록을 전달했다. 정답 경로·합성 상태 이름·주입 조건은 전달하지 않았다. 독립적인 시험 상태 기계의 에피소드 종료 시점 목적 상태와 앱이 제시한 `verified`를 따로 측정했다. 잠깐 도착했다가 다시 이탈한 경우는 독립 목적 상태 성공으로 세지 않는다. 최종 사용자 확인은 자동으로 대신하지 않았다.

| 지표, 전체 36회씩 | A: 공통 수정 + 현재 정책 | B: 공통 수정 + MC-v0 |
|---|---:|---:|
| 독립 목적 상태 도달 | 20/36 | 33/36 |
| 앱의 완료 검증 제시 | 6/36 | 7/36 |
| 거짓 완료 검증 제시 | 0 | 0 |
| 실행 안전 위반 / 관찰 표현 거절 | 0 / 0 | 0 / 0 |
| 기록으로 확인된 실제 모델 호출 | 58 | 79 |
| 기록된 실제 모델 응답 대기 누계 | 254.07초 | 378.97초 |
| 공급자 또는 계획 오류 응답 | 12 | 26 |
| 게이트웨이 실패, 리스너에도 전달됨 | 1 | 3 |
| MC 재관찰 | 0 | 18 |

여기서 모델 호출은 **다음 동작·계획·완료 조건을 제안하는 Gemini 3.8 Flash 요청**이다. MC-v0 자체가 별도의 대형 모델을 부르는 것은 아니다. B의 재관찰에 따른 추가 계획 요청 등이 호출 수에 반영된다. 기록된 호출은 21회, 36.2% 늘었다. 미해결 전송 요청 A 1건/B 3건에 기록 밖의 공급자 호출이 있었는지는 확인할 수 없어 이를 전체 비용 차이로 해석하지 않는다. 거짓 완료 0회는 이번 완료 검증 제시 13회 안의 관찰이며 모든 앱의 안전성 보증이 아니다.

모델 대기 누계는 36회 전체의 실제 API 시간 합이다. 한 작업의 속도나 사용자 소요 시간이 아니다. UI 대기는 Robolectric 가상 시계로 측정해 실제 모델 시간과 분리했다. 가상 UI 시계는 모델 응답을 기다리는 동안 전진하지 않으므로 실제 앱의 네트워크 대기 중 화면 전이를 재현하지 않는다. 완전한 행렬 여부는 `True`, 모든 조건의 데이터 건강성은 `False`다. 사전 고정 기준에 따라 **효율성 우열은 해석하지 않는다.** 오류 응답은 실패 기록에 그대로 남겼고 성공한 요청만 따로 골라 비교하지 않았다.

| 배정 조건, 각 12회 | A 목적 도달 | B 목적 도달 | 완료 검증 A/B | 기록된 모델 호출 A/B |
|---|---:|---:|---:|---:|
| 정상 | 11/12 | 12/12 | 4 / 3 | 21 / 20 |
| 첫 조작 수락·효과 없음 | 0/12 | 9/12 | 0 / 2 | 12 / 30 |
| 첫 화면 전이 5.5초 지연 | 9/12 | 12/12 | 2 / 2 | 25 / 29 |

36쌍 중 둘 다 목적 도달 20쌍, A만 도달 0쌍, B만 도달 13쌍, 둘 다 미도달 3쌍이다. 여섯 구성 과제를 두 번 반복한 소규모 기술 실험이므로 모집단의 통계적 유의성·동등성이나 중장년층 효과로 해석하지 않는다.

오류는 첫 기본 경로를 실제로 실행했을 때만 주입했다. 모델이 다른 경로를 먼저 고른 경우도 원래 배정 분모에 남겼다.

| 배정 오류 | A/B 둘 다 실제 노출 | A만 노출 | B만 노출 | 둘 다 미노출 |
|---|---:|---:|---:|---:|
| 첫 조작 수락·효과 없음 | 12 | 0 | 0 | 0 |
| 첫 화면 전이 5.5초 지연 | 11 | 0 | 1 | 0 |

독립 공급자 로그 137행에 실제 호출 137회, 공급자 오류 26회, 계획·파싱 오류 12회가 기록됐다. 공급자 오류와 계획 오류는 구분한다. 후자는 잘못된 모델 출력 등이 검증 단계에서 거절됐다는 뜻이며 원인 전체가 확정된 것은 아니다. 로그에는 원문 모델 응답이나 개인정보를 저장하지 않았다.

공급자 대조 상태는 `INDETERMINATE_OR_MISMATCHED`다. 계획 요청 141건 중 공급자 기록은 137건이며 기록된 모델 호출 합계 137회는 양쪽 기록이 일치한다. 차이 4건은 `nested_advanced`의 게이트웨이 실패와 대응한다. 정상 조건 반복 1의 A/B, 무효 조건 반복 0의 B, 지연 조건 반복 1의 B에서 발생했다. 같은 오류가 리스너에도 전달되어 두 오류 수를 합산하면 중복이다. HTTP 상태나 실패 요청 본문을 저장하지 않아 정확한 거절 원인과 이 4건의 공급자 호출 여부는 확정할 수 없다. 관찰된 137회가 모든 실제 시도를 포함한다고 주장하지 않는다.

에피소드 행에 요청 ID 해시를 직접 저장하지 않은 한계가 있어, 순차 실행·연속된 작업 그룹·요청 수·호출 수·대기 시간으로 대조했다. 72개 공급자 작업 그룹은 존재하지만 전체 요청의 결합을 완료했다고 주장하지 않는다. 불일치를 숨기거나 해당 시행을 삭제하지 않았으며, 이 한계도 기본 적용과 효율성 해석을 보류한 이유다. 상세한 불일치 여부와 제한은 [공급자 감사](live/provider-audit.json)에 있다.

## 통제 검사는 어디까지 의미가 있는가

경로를 아는 결정적 계획기를 사용한 별도 72회에서 A 22/36, B 36/36이었다. 실제 모델 호출은 0회다. 무효 동작 뒤 우회 경로로 복구하는 구성에서 B의 재관찰이 작동함을 확인한 **기능 적합성 검사**이며 실제 모델의 우수성 근거가 아니다. 지연 조건의 성공한 시행만의 가상 UI 중앙값도 A 5,750ms, B 6,150ms로 B의 속도 우위를 보이지 않는다. 성공한 시행만의 시간과 실패가 포함된 완료율은 서로 다른 지표다.

지연된 원래 전이와 새 복구 동작이 겹치는 구성에서는 목적 상태가 다시 중간 화면으로 바뀌는 경쟁도 관찰됐다. 이는 진행 중인 동작·늦은 이벤트를 관리해야 하는 이유이며, 실앱 일반 효과로 확대하지 않는다. 세부 기록은 [통제 결과](controlled/summary.md)에 있다.

## 다음 구조와 개선 순서

우선순위는 **불변 사용자 GoalContract → 버전 있는 임시 EvidenceSpec → 기존 Planner → 동일 ProjectionSpec의 네이티브 실행 → 로컬 Supervisor → 필요한 경우에만 모델 진단**이다. 정상 경로의 추가 호출을 줄이는 방향이지만 그 효과는 다음 실험에서 측정해야 한다.

다음 모델 비교 전에 실험 계측부터 보완한다. 에피소드에 작업·요청의 해시를 기록하고, 파사드의 제한된 HTTP 상태·거절 이유를 보존해야 한다. 현재 공개 관찰의 허용 목록과 모델이 제안한 미래 완료 증거의 검증을 구분할 필요도 있다. 이것이 이번 4건의 확정 원인이라는 뜻은 아니다. 정확한 원인을 남기고 전체 요청 대조가 가능한 상태를 다음 실행의 준비 조건으로 삼는다.

1. **목표와 증거 후보 분리:** 아직 관찰되지 않은 미래 라벨을 잘못 추측해도 현재는 불변 completion으로 잠길 수 있다. 사용자의 목표는 유지하고, 관찰로 지지되지 않은 증거 후보만 사유·버전과 함께 갱신해야 한다. 결과를 본 뒤 성공 기준을 바꾸는 방식은 허용하지 않는다. 목적 화면 도달과 안정적인 완료 증거 확보를 따로 해결한다.
2. **대기 중 동작의 수명 관리:** 요청 수락·실제 효과·로딩·무반응·내부 계약 오류를 구분한다. 늦은 완료 이벤트가 오면 오래된 제안과 예약된 재시도를 폐기한다. 이미 Android에 전달된 터치를 취소할 수 있다는 뜻은 아니다. 시간 초과마다 새 모델 계획을 요청하는 정책은 속도와 호출 수 모두에 불리할 수 있다.
3. **모델 오류의 구체적 분류와 제한된 복구:** 공급자 시간 초과와 모델 스키마/계획 실패를 분리하고, 원문 개인정보 없이 제한된 오류 코드를 남긴다. 안전한 계획 수선과 전체 시간 예산을 검증한다. 이번 결과를 보고 B를 튜닝해 같은 결과에 재채점하지 않았다.
4. **실제 앱으로 단계 확대:** 각 목표의 양성·음성 대조와 시작 상태 복원을 먼저 통과시킨다. 미사용 앱·다른 기기에서 성공, 거짓 완료, 중복 실행, 호출, 사용자 개입과 실제 경과시간을 함께 비교한다. 이후 기존 화면을 유지하며 중장년층의 대기 이해·반복 클릭·도움 없는 완료를 평가한다. 새 버튼을 추가하는 것은 이번 개선의 해법이 아니다.

목적 텍스트가 실제 목표의 전체 의미를 증명하는 것은 아니다. 같은 이름의 클릭 가능한 배경 아래 제목이 관찰 중복 제거로 사라져 완료를 확인하지 못하는 경우도 남아 있다. 수동 TAP·OCR 경로와 사람이 직접 조작하는 시간은 이번 비교 범위 밖이다.
