# B가 추가 호출만 쓰고 자주 복구하지 못한 이유

**36회 실험의 B v0는 ‘반영을 확인하지 못한 조작을 차단하고, 현재 화면을 같은 플래너에 다시 보내는 정책’이다.** 조작이 아직 처리 중인지, 실제로 무효였는지, 다음에 어떤 조작을 실행할 수 있는지까지 연결된 복구는 구현돼 있지 않았다. 동결 자료의 구체 사례와 모델 없는 통제 검사로 해당 경로를 확인했다. 아래 코드 메커니즘은 분석 대상 v0를 설명하며, 마지막 절의 수정 진행 상황과 구분한다.

이 분석은 [기존 36회 원자료](../2026-11-20-native-settings/episodes.jsonl)와 [서버 terminal 81건](../2026-11-20-native-settings/provider-terminal.jsonl)을 그대로 사용한다. 원인 통제 검사에서도 모델/API와 실제 native 조작을 호출하지 않았다. 입력 파일의 해시, 요청별 분류와 사례별 타임라인은 [findings.json](findings.json)에 있다.

## 비용이 증가한 위치

| 조건 | A 호출 | B 호출 | B − A |
|---|---:|---:|---:|
| 정상 | 17 | 14 | −3 |
| 수락 후 무반응 | 8 | 14 | +6 |
| 5.5초 dispatch 지연 | 12 | 16 | +4 |
| 전체 | 37 | 44 | +7 |

호출 증가는 장애 조건에 집중됐다. 전체 목적 화면 도달은 A/B 각각 6/18, 자동 완료 검증은 각각 0/18이었다. 이 차이를 B만의 인과적 비용으로 볼 수는 없다. 서로 다른 모델 응답·계획·공급자 시간 초과와 관찰 종료 차이가 함께 들어 있다.

## 확인한 코드 메커니즘

**1. 재시도보다 차단 후 재계획을 수행한다.** [AppTaskMetaController.after](../../../Frontend/app/src/main/java/com/click/service/overlay/AppTaskMetaController.java)는 새 공개 관찰에서 조작 반영을 5초 이상 확인하지 못하면 이벤트 대기 조건을 확인한 뒤 해당 화면·도구·대상·앱 조합을 차단하고 `REOBSERVE`를 반환한다. [Controller](../../../Frontend/app/src/main/java/com/click/service/overlay/AppTaskController.java)는 재관찰 후 필요하면 플래너를 다시 호출한다. 같은 화면에서 원래 조작을 그대로 다시 제안하면 B의 차단 규칙에 걸린다. 중복 조작을 막는 안전 의도는 타당하지만, 재계획만으로 실패가 수정되는 것은 아니다. B가 별도의 반성 모델을 호출하는 구조도 아니다.

**2. 실험 당시 플래너가 받는 복구 정보가 제한돼 있었다.** Controller의 `request`에는 일반적인 조작 이력이 들어간다. Backend의 [플래너 context](../../../Backend/app/services/app_task.py)도 도구·대상·결과·같은 화면 여부를 전달한다. 그러나 B가 재관찰을 선택한 이유, 미처리 native dispatch, B가 차단한 대상 집합, 남은 복구 예산은 전달하지 않는다. 이력이 전혀 없는 것이 아니라, 복구 판단에 필요한 상태가 빠져 있다.

**3. 5초 복구 판단과 5.5초 조작 예약이 분리돼 있다.** [실험 driver](../../../Frontend/app/src/androidTest/java/com/click/service/accessibility/MetaControllerSettingsExperimentTest.java)의 `pending`은 추가 조작 승인과 공동 성공을 막는다. B의 판단 함수와 플래너 호출에는 전달되지 않는다. 따라서 원래 조작이 아직 예약돼 있는데도 재계획이 시작될 수 있다. 옛 화면에 대한 응답이 나중에 오면 Controller의 화면 지문 검사에서 버려지고 다시 요청하는 경로도 존재한다. 이 경우 안전 검사는 동작하지만 모델 비용은 이미 발생한다.

**4. 실험 당시 읽을 수 있는 제어와 실행할 수 있는 제어가 일치하지 않았다.** 플래너는 공개 controls와 일반 Android 도구를 받지만, 실험의 정확한 탐색 허용 목록은 계획 입력에 포함되지 않는다. [Facade](../../../Backend/scripts/serve_meta_controller_settings_experiment.py)의 `navigation_action_allowed`가 모델 응답 이후 이를 검사한다. 예를 들어 화면에서 읽을 수 있는 공개 대안이 실험의 허용 경로에는 없을 수 있다. 그 제안을 만들기 위한 모델 시도 후 HTTP 422가 발생할 수 있는 구조다. 실행 검사를 약화하기보다 플래너에게 같은 실행 범위를 제공해야 한다.

**5. HTTP 오류가 복구 판단으로 다시 연결되지 않는다.** 과거 HTTP 422 시행 6개 모두 마지막 표시 상태가 `planning`인 채 약 30초까지 남았다. Controller의 gateway 실패 callback은 busy를 해제하고 listener에 오류를 전달하지만 새 표시 상태나 B 복구 판단을 만들지 않는다. 당시 실험 listener는 오류 횟수만 증가시켜 마지막 `planning` 표시가 유지됐다. 이는 해당 실험의 상태 처리와 복구 피드백의 공백이며, 별도의 생산 UI listener도 똑같이 보였다는 증거는 아니다.

## 무반응에서 실제로 일어난 일

B에서 무반응 TAP까지 도달한 시행은 5개였다. 그 조작 이후의 모델 요청 6건은 다음과 같이 끝났다.

| 요청 결과 | 건수 |
|---|---:|
| 공급자 제한 시간 초과 | 3 |
| 탐색 계약 밖 제안 차단 | 2 |
| 스크롤 제안 | 1 |

Sound 사례가 가장 명확하다. B의 Sound TAP은 **7.669초**에 수락됐지만 효과를 주지 않았다. 다음 요청은 스크롤을 제안했고 **16.021초**에 native 스크롤이 실행됐다. 이후 요청은 제한 시간을 초과했다. 최종 목표에는 도달하지 못했다. A는 같은 조건에서 원래 TAP 뒤 확인하지 못한 상태로 안내를 넘기며 1회 호출에 그쳤고, B는 3회 호출·복구 판단 2회를 사용했다.

확인된 사실은 ‘다음 복구 행동이 스크롤이었고 목표를 달성하지 못했다’는 것이다. 스크롤 뒤의 원시 화면을 저장하지 않았으므로 Sound 항목이 화면 밖으로 사라졌다고 단정하지 않는다. 해당 모델 요청은 `221aca643890e2140aeb6889`, 후속 시간 초과 요청은 `aa7cfea77ce88ff2d8444962`다.

무반응 B 전체의 시간 초과는 4건이다. 이 중 Accessibility의 첫 요청은 TAP 주입 전에 실패했다. 위의 ‘조작 이후 3건’과 전체 조건의 ‘4건’을 혼동하지 않는다.

## 지연에서 실제로 일어난 일

B에서 지연 TAP을 예약한 시행은 5개였다. 예약 이후 모델 요청 7건은 **제한 시간 초과 4건·계약 밖 제안 차단 3건**으로 끝났다. 그 사이 원래 예약된 조작 이외에 목표로 이어진 새로운 native 조작은 없었다.

Display의 원래 지연 TAP은 A **9.325초**, B **9.140초**에 실행됐고 양팔 모두 목적 화면에 도달했다. 호출은 A 2회, B 3회였다. Sound도 원래 TAP이 A **13.334초**, B **13.682초**에 실행됐으며 호출은 2회 대 3회였다. B가 추가로 요청했어도 원래 지연 조작을 더 잘 실행한 결과는 아니었다.

Display·Sound·Bluetooth의 B 두 번째 요청은 첫 응답 기록 뒤 약 **5.35~5.44초**에 시작됐다. 원래 조작의 실제 dispatch는 예약 뒤 약 **5.53~5.55초**였다. 두 시간의 원점은 다르다. 과거 자료에는 같은 원점의 조작·복구 타임스탬프가 없으므로 각 요청이 dispatch보다 먼저였다고 직접 증명할 수는 없다. **5초 판단에 미처리 예약 상태가 입력되지 않는 코드 경로는 확인됐으며, 실제 타이밍도 조기 재계획 가능성과 부합한다.**

또한 A와 B의 종료 후 관찰 기회가 달랐다. 지연 A가 짧게 관찰한 것과 B가 오래 관찰한 것을 B의 안정성 이점이나 A의 속도 이점으로 해석하지 않는다.

## B의 가능성과 공급자 혼입을 함께 봐야 한다

**정상 Language는 B가 도움을 줄 가능성을 보여 준다.** A는 System을 10.098초에 누른 뒤 15.609초에 `needs_input`으로 끝났고 목적 화면에 도달하지 못했다. B는 System 9.335초 뒤 복구 판단을 거쳐 Language & region을 19.915초에 눌러 도달했다. B의 세 번째 요청 전 약 5.35초 공백은 재관찰 정책과 부합한다. 이후 완료 확인 요청은 시간 초과였다. 복구 판단의 개별 발생 시각을 저장하지 않았으므로 이 경로의 세부 연결은 순서와 코드에 근거한 해석이다.

**정상 DateTime의 B 실패는 복구가 발동하기 전이었다.** B는 첫 요청이 시간 초과였고 복구 횟수 0·native 조작 0으로 끝났다. A는 도달했다. 이 차이를 ‘B 복구 알고리즘이 잘못 행동해서 실패했다’고 설명할 수 없다.

따라서 “B는 어느 경우에도 도움이 없었다”는 결론은 근거가 부족하다. 확인된 결론은 **전체 성과 증가가 입증되지 않았고, 추가 복구 요청 상당수가 유효한 다음 행동을 만들지 못했다**는 것이다.

## 이번 분석으로 확정하지 않은 것

- 과거의 차단된 제안 6건은 구체적인 조작 내용을 보존하지 않았다. 플래너·실행기 허용 범위의 차이는 확인했지만, 실제 6건 각각을 그 차이로 설명하거나 설정 변경 시도라고 단정하지 않는다.
- 총 호출 증가 7회를 모두 B 정책 하나의 인과 효과로 배분하지 않는다. 서로 다른 계획과 공급자 응답, 늦은 응답 처리, 종료 관찰 차이가 섞여 있다.
- 공통 완료 경로의 제목 삭제 버그는 [별도 회귀·native 연결 검사](../2026-11-20-completion-title-fix/verification.json)로 확인하고 수정했다. 과거 후보의 정확한 selector는 남지 않아 모든 미검증의 원인으로 소급 지정할 수 없다. 수정 후 연결 검사는 기존 36회 A/B 재실험이 아니다.
- B 복구 정책은 이 분석에서 변경하지 않았다. 기본 적용 GO나 새 A/B 성능 개선을 주장하지 않는다.

## 모델 없는 통제 검사에서 재현한 것

[메커니즘 기록](mechanism-probes.jsonl)과 [실행 로그](mechanism-tests.log)는 생산 Controller 코드·mock gateway·Robolectric 통제 시계를 사용하는 두 시나리오다. 실제 Android 앱 성능 시행이 아니며, 공통 완료 검증 기능도 꺼서 복구 경로를 분리했다.

1. **무반응 뒤 같은 조작 차단:** 새로 관찰한 같은 화면에서 기본 조작 정책은 같은 대상을 허용하지만, B가 기억한 차단 키에는 걸렸다. A의 플래너 요청은 1회, B는 2회였고 추가 교정 조작은 0회였다.
2. **5.5초 조작을 기다리는 중 재계획:** 5.35초 시점에 원래 조작은 아직 실행되지 않았지만 A는 요청 1회, B는 2회였다. 실제 효과를 모사한 뒤 옛 화면의 응답을 전달하자 B는 그 응답을 버리고 세 번째 요청을 만들었다. 같은 효과 이후 A의 요청은 2회였다.

이 검사는 v0에서 해당 메커니즘이 실제로 실행될 수 있음을 보여 준다. 과거 36회의 모든 추가 요청이 그 이유였다고 소급 확정하지 않는다.

[허용 범위 차이의 수정 전 검사](capability-gap-before.log)도 통과했다. 실제 서비스·facade 경계를 사용하되 모델은 fake sender로 대체했다. 공개 `Search Settings`가 모델의 합법 target/tool 선택지에 들어가 정상 제안이 됐지만, frozen 탐색 허용 목록 밖이어서 sender 시도 1회 후 HTTP 422가 됐다. 이는 비용 발생 경로의 통제 재현이며 과거 차단 6건의 실제 행동을 알아낸 결과는 아니다.

## 요청한 두 가지 수정 완료와 남은 문제

수정 대상은 조작 상태, 복구 정보, 실행 범위의 세 경계다. 조작의 수락·실제 처리 중·반영 확인을 구분해 **처리 중인 원래 조작이 끝나기 전에는 재계획하지 않도록 연결**해야 한다. 실패 이유·차단 대상·남은 예산·실행 가능한 행동을 복구 요청에 함께 제공하고, 중복 조작 방지를 유지하면서 안전하고 반복 가능한 탐색의 복구를 별도로 정의해야 한다. 모델 입력의 허용 행동과 실제 실행 검사도 일치시켜 호출 뒤의 불필요한 거절을 줄여야 한다.

사용자 지시에 따른 **두 가지 수정: 복구 context 전달과, 모델 호출 전 신뢰할 수 있는 실행 범위 적용**을 구현하고 검증했다.

- Frontend는 B의 재관찰 이후에만 제한된 복구 이유·판정·대기 시간·시도 횟수·이전 조작·차단 이력을 현재 관찰과 묶어 보낸다. Backend는 닫힌 스키마로 검사하고, 모델에는 현재 control의 별칭으로 변환해 전달한다. 일반 CURRENT 요청과 이전 클라이언트의 요청 형식은 유지한다.
- 실험 facade는 서버에서 신뢰할 수 있는 tool/target/app 쌍을 만들고, 플래너가 모델 호출 전에 같은 실행 상한을 보도록 연결한다. 응답 후에도 정확한 쌍 검사와 기존 조작·화면·완료 검사를 유지한다. 복구 이력은 같은 화면 지문과 앱이 일치할 때 실행 가능한 범위를 제한하는 데만 사용하며 실행 권한을 늘리지 않는다.
- 읽기 전용 제목과 상태는 완료 증거용 controls에 보존한다. 실행 가능한 행동이 없는 경우에도 `result_only` 완료 증거 확인은 유지한다.

[검증 기록](verification.json), [Frontend·빌드 검사 로그](fixed-tests.log), [Backend 검사 로그](backend-tests.log), [Frontend DTO의 Backend 계약 대조](integration-contract.json)를 보관한다. 관련 Backend **272개**, Android **24개 클래스·151개 테스트**가 통과했고 debug/계측 APK 빌드와 lint도 통과했다. Robolectric Controller가 실제로 내보낸 DTO를 Backend의 엄격한 스키마로 읽고 복구 대상 별칭 왕복을 확인했다. 계약 대조의 서버 시계는 해당 통제 프레임에 맞췄으며, 실제 native 관찰을 변경한 검사가 아니다. 이 검증에서는 모델/API 호출과 에뮬레이터 실행을 하지 않았다.

**미처리 dispatch를 기다리는 정책과 같은 화면 재시도 정책은 변경하지 않았다.** 이번 구현·계약 검증은 B의 실제 성공률·호출 수가 개선됐다는 성능 결과가 아니다. 기존 36회나 통제 검사의 수치를 새 B 성능으로 바꾸지 않으며 기본 적용 GO를 선언하지 않는다.

새 선택적 `recovery` 필드는 B 실험 요청에만 사용한다. 새 B 클라이언트를 쓰려면 이를 받는 Backend를 먼저 배포해야 한다. 실행 capability는 클라이언트 입력이 아닌 서버 전용 인자로 전달하며, 상태 인자와 native 실행의 최종 검사는 계속 유지한다.

병행된 런처 변경을 보존한 통합 상태에서도 APK·계측 APK·lint와 관련 4개 클래스 40개 테스트가 통과했다([통합 로그](integration-tests.log)). 완료한 복구·실행 범위 소스의 해시는 통합 전 검증본과 같다.

## 통제 원인 검사 재실행

아래 opt-in 검사는 현재 남아 있는 v0 대기·반복 금지 메커니즘을 재현하는 진단 실험이다. 모델이나 기기를 사용하지 않는다. Backend 수정 검사는 `Backend`에서 `pytest tests/test_app_task_recovery_capabilities.py tests/test_meta_controller_recovery_capability_gap.py`로 실행한다.

```bash
cat > /tmp/click-recovery-probe.init.gradle <<'GRADLE'
gradle.beforeProject { p ->
    p.tasks.withType(org.gradle.api.tasks.testing.Test).configureEach {
        systemProperty 'click.metaRecoveryCauseProbe', 'true'
    }
}
GRADLE
cd Frontend
./gradlew -I /tmp/click-recovery-probe.init.gradle :app:testDebugUnitTest \
  --tests com.click.service.overlay.MetaControllerRecoveryCauseProbeTest \
  --tests com.click.service.overlay.AppTaskRecoveryContextTest
```
