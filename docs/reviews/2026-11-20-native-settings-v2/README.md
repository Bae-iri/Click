# 복구 context·실행 capability 수정 후 실제 Settings A/B 비교

**현재 B는 전체 성공을 늘리지 못했다.** 실제 Android Settings 36회에서 A는 **4/18**, B는 **3/18** 공동 성공했고, 관측한 Gemini API 시도는 **48 대 60회**였다. B의 호출이 25% 많았다. 다만 지연 조건의 화면 설정에서는 양팔 모두 실제 지연에 노출된 뒤 B만 공동 성공한 한 쌍이 있었다. 사전 게이트는 **다른 앱의 제한된 기술 검증으로 진행 GO**, **B 기본 적용은 NO-GO**다. 이 한 쌍도 A의 공급자 timeout을 포함하므로 B 정책의 인과 효과나 우월성을 입증하지 않는다.

실행 소스는 `0ed757454abae3696c4c48d24b51e05d2853f8d3`다. 이후 사용자 원격 변경과 개선 코드가 통합되더라도 이 기록을 현재 HEAD의 측정값으로 바꾸지 않는다. 모델은 설정된 `gemini-3.8-flash`, 기기는 계정 없는 Android 17/SDK 37 에뮬레이터다. 실제 접근성 관찰·native 실행기·앱 Gateway·Gemini 경계를 사용했고, 조작 승인은 스크립트가 제공했다. 사람이나 중장년층 참가자는 없다.

## 비교 기준과 결과

같은 여섯 과제에 정상, 첫 유효 탭 수락 후 무반응, 첫 유효 탭의 실제 dispatch 5.5초 지연을 적용했다. 각 조건의 A/B를 교차 배치한 36회·18쌍이다. 정상 12회 원본을 그대로 보존한 뒤 장애 24회를 추가했다. 실패나 공급자 오류를 제외하거나 좋은 시행을 다시 고르지 않았다.

공동 성공은 **30초 안에 독립 정답이 목적 화면을 700ms 안정 확인하고, 앱의 현재 자동 완료 검증도 존재하며, 미처리 native 조작이 없는 경우**다. 화면 도달, 안정 도달, 완료 검증을 구분한다. 안내가 일찍 handoff돼도 독립 관찰은 공통 30초까지 유지했다.

|---|---:|---:|---:|---:|---:|
| 정상 | 4/6 · 2/6 | 4/6 · 3/6 | 4/6 · 3/6 | 20 · 14 | 1 · 4 |
| 무반응 | 0/6 · 0/6 | 0/6 · 1/6 | 0/6 · 0/6 | 9 · 28 | 1 · 2 |
| 지연 | 0/6 · 1/6 | 5/6 · 3/6 | 5/6 · 3/6 | 19 · 18 | 5 · 8 |
| 전체 | **4/18 · 3/18** | **9/18 · 7/18** | **9/18 · 6/18** | **48 · 60** | **7 · 14** |

요청 108개가 클라이언트·서버와 정확히 결합됐고 미확인 호출은 0개다. API 시도 수는 토큰 수·청구 금액·원격 추론 완료 건수가 아니다. 공급자 timeout도 실제 관측된 시도에 포함한다. 계획/파싱 오류와 실행 계약 밖 제안의 사후 차단은 양팔 모두 0건이었다.

실패에 공통 30초를 부여한 평균 시간은 A **27.026초**, B **27.353초**다. 두 정책 모두 성공한 두 쌍만의 중앙 시간 차이는 B가 0.614초 짧았으나, 다른 과제와 실패를 제외한 단일 반복이므로 전체 속도 이득으로 일반화하지 않는다. 대응 결과는 양팔 성공 2쌍, A만 성공 2쌍, B만 성공 1쌍, 양팔 실패 13쌍이다.

거짓 완료 검증·native guard 위반·설정값 변경은 **각각 0건**이다. 최종 oracle 불명확, 미평가 결과, 정리 후 남은 native 조작·Gateway callback도 0건이다. 36회와 18쌍 모두 측정 검사를 통과했다. 무반응의 실제 양팔 장애 노출은 5쌍, 지연은 4쌍이다. 장애 전에 실패해 노출되지 않은 시행도 배정 분모에 남겼다.

## 수정한 두 전달 경로는 작동했는가

- B의 복구 context는 정확히 결합된 관측 모델 시도 **18회**에 전달됐다. A는 0회다. B의 복구 판단 활성화는 14회이며, 전달된 API 시도 수나 성공 수와 같지 않다.
- 신뢰된 실행 capability는 A 48회·B 60회 모델 시도에 적용됐다. 명시적 `allowed_actions` context는 A 42회·B 56회에 전달됐다. 나머지 관측 호출은 완료 증거 발견 전용으로 조작을 제안할 수 없다.
- B 복구 요청에서 실제 제거한 실행 pair 수의 합은 **10**이다. 요청 사이 중복을 포함할 수 있는 합계이며 고유 조작 10개나 복구 성공 10건을 의미하지 않는다.
- 필요한 전달 진단이 빠지거나 잘못된 관측 호출은 0개였다. 플래그는 전달의 기술 근거이며 모델이 그 내용을 이해·활용했다는 근거는 아니다.

따라서 이전의 “복구 정보가 일반 요청으로 사라짐”, “실행 가능한 조작을 모델에 알리지 않고 사후 차단”은 이번 실행의 남은 실패를 설명하는 근거가 아니다. 전달 수정만으로 현재 복구 정책의 유용성이 보장되지는 않았다.

## 실제로 남은 병목

1. **무반응 복구의 비용 대비 성과가 낮다.** B는 A보다 19회 많은 API 시도를 썼지만 공동 성공은 둘 다 0이었다. B 날짜·시간은 종료 시 목적 화면이 보였으나 안정 시간·완료 검증까지 충족하지 못했다.
2. **실행 수락과 단계 검증 사이에 간격이 있다.** 정상 B Bluetooth는 `Connected devices` native 탭이 수락된 뒤 복구 요청을 보냈다. 정확한 expectation·verifier 이유는 저장되지 않았으므로 “화면이 전혀 이동하지 않았다”고 단정할 수 없다. B의 복구 요청 자체는 실제 전달됐지만 그 호출이 timeout됐다.
3. **완료 후보를 얻는 후속 모델 요청이 병목이다.** 정상 B 날짜·시간은 13.858초에 목적지 안정 도달했으나 후속 `next_action` 요청이 timeout돼 검증 후보를 얻지 못했다. 두 번째 native 프레임을 기다리다 실패한 사례가 아니다.
4. **공통 응답 폐기가 호출을 늘린다.** 정상군에서 `changed_frame`으로 폐기한 응답 5개에 모델 대기 15.369초가 들었다. 그중 읽기 전용 `result_only` 후보 3개는 같은 native window에서 나중에 동일 후보가 실제 검증됐다. 오래된 액션을 실행하는 대신 후보만 현재 증거로 재검증할 여지가 있다.

성공한 정상 6회의 마지막 두 프레임 검증은 416–426ms였다. 완료 지연 전체를 이 짧은 로컬 검증 탓으로 돌릴 수 없다. 세부 요청 hash·시각·후보 이력은 [정상 실패 분석](normal-failure-analysis.md)과 [독립 검토](independent-review.md)에 있다.

지연 화면 설정의 B 단독 공동 성공은 21.239초였다. A도 11.156초에 목적지 안정 도달했지만 후속 모델 요청이 timeout됐다. B는 11.477초에 안정 도달했고 API 3회, A는 2회였다. 따라서 이 차이를 “B만 화면 이동을 복구했다”거나 “B가 항상 더 빠르다”고 표현하지 않는다.

## 연구 질문과 다음 작업

- **B가 더 잘 끝내는가?** 이번 전체 값에서는 아니다. 공동 성공과 도달은 A가 높고, B의 호출은 많았다. 단일 반복·서로 다른 공급자 응답 때문에 정책의 통계적 우월·열등을 확정하지 않는다.
- **복구가 추가 성공을 만드는가?** 실제 양팔 지연 노출에서 B 단독 공동 성공 한 쌍이 있었다. 무반응 공동 성공은 없었다. 제한된 추가 검증의 근거이지 기본 적용 근거는 아니다.
- **범용성과 속도는 입증됐는가?** 앱은 하나이며 중장년층 참여자는 없다. 현재 전체 실패 포함 시간과 호출 수는 속도 개선을 지지하지 않는다.
- **다음 방향은 무엇인가?** 사용자의 우선순위는 범용성, 그다음 속도다. A/B 공통으로 이미 관측된 안전한 완료 후보 재검증을 개선하고, B는 실제 안정된 native 전환을 단계·목표 완료와 분리해 관찰한다. 무작정 같은 버튼을 재실행하지 않고 로컬 관찰·검증을 먼저 수행한다. 다른 앱으로 검증 범위를 넓히되 특정 Settings 이름이나 실험 정답을 생산 정책에 넣지 않는다.

공통 개선을 A/B 양쪽에 동일하게 적용한 다음 B의 조정 효과를 새 cohort에서 비교한다. 최종 요구와 현재 selector 바인딩을 분리하는 더 큰 구조는 검토하되, 미검증 label 힌트나 `allStepsVerified`만으로 목표 완료를 자동 선언하지 않는다. 현재 36회의 점수는 이후 개선 결과로 덮어쓰지 않는다.

## 과거 v1과 등록 기록의 한계

v1은 공동 성공 A/B 0/18·0/18, 도달 6/18·6/18, API 시도 37·44였다. 현재는 두 정책 모두 완료 검증 성공이 생겼다. 다만 공통 제목 증거 수정·context/capability·관찰 창·공급자 응답이 함께 달라졌으므로 특정 수정이나 B만의 인과 효과로 배분할 수 없다. v1 파일과 해시는 바꾸지 않았다.

**등록 기록 조립에 편차가 있었다.** 소스 commit·프로토콜, 두 APK 해시, 환경과 전체 일정은 실행 전에 각각 고정·기록됐지만, aggregate 동결 helper의 import 오류 뒤 정상 instrumentation을 먼저 실행했다. `source-freeze.json` 조립은 시작 이후 끝났다. 당시 terminal 0건은 진행 중 호출 0건을 증명하지 않는다. 이 편차를 완전한 호출 전 aggregate 등록으로 표현하지 않는다. 실행 중 소스·목표·정답·일정·기준은 바꾸지 않았으며, 종료 시 전체 소스 hash 일치와 정상 원본 prefix 보존을 [종료 기록](cohort-closure.json)에 확인했다.

## 검증과 자료

측정 소스의 관련 Backend 249개와 분석 46개, Android 22개 클래스 144개 테스트가 통과했다. debug/계측 APK 빌드와 lint도 통과했다. 분석 검사에는 과거 v1 감사·요약 JSON과 Markdown의 byte 단위 동일성 검사가 포함됐다. 이후 통합·개선 소스의 검사는 별도 기록하며 이 성능 결과와 섞지 않는다.
