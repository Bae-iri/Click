# Settings v2 정상 조건 12회: 호출 증가와 완료 실패 원인

정상 조건에서는 **A가 4/6회, B가 2/6회 공동 성공**했다. B의 날짜·시간 작업은 실제 목적 화면에 도달했지만, 후속 모델 요청이 공급자 제한 시간에 걸려 완료 증거를 확보하지 못했다. 성공한 A의 Bluetooth 6회·날짜·시간 5회 호출에는 실제 이동 단계 외에 **화면 지문 변경으로 폐기된 응답과 완료 증거를 얻는 요청**이 포함돼 있었다.

분석 범위는 동결한 v2 정상 조건 12회다. 이후 장애 조건 결과나 과거 v1 결과를 섞지 않았다. 실행 코드, 판정 기준, 원본 데이터도 수정하지 않았다.

## 1. 근거와 해석 범위

- [정상 조건 에피소드 12개](normal-episodes.jsonl): 실제 native action, 독립 oracle 시각, 현재/과거 완료 상태, 요청 영수증, 완료 증거 이벤트를 확인했다.
- [정상 조건 공급자 종료 기록](normal-provider-terminal.jsonl): `request_ref`로 요청을 연결하고 공급자 오류를 확인했다.
- [요청 직접 대조 결과](normal-request-audit.json): planner 요청·클라이언트 영수증·서버 종료 기록이 **각각 34개**, 직접 연결 34/34, 알 수 없는 모델 호출 0개다.
- [정상 조건 집계](normal-summary.json), [측정 규약](../../../experiments/metacontroller/native-settings-protocol-v2.md), [소스 동결](source-freeze.json)을 함께 참고한다.

여기서 모델 호출은 공급자 경계에서 관찰된 `gemini-3.8-flash` API 요청 시도이며, 제한 시간 실패도 포함한다. 정상 조건의 34개 요청은 각각 관찰된 API 시도 1회로 확인됐다. 이 계측으로 토큰 수·청구 금액·공급자 내부의 처리 여부나 추론 완료를 보장할 수는 없다. native 화면을 두 번 읽고 비교하는 로컬 검증은 이 호출 수에 포함되지 않는다. 각 공급자 시도는 최대 1회이며 요청별 예산은 약 9초다.

`joint_success`는 독립 oracle의 안정적인 목적지 확인과 앱의 현재 `verified` 완료 제안이 함께 성립한 결과다. 화면에 도착한 것과 앱이 완료를 검증한 것을 별도로 보았다. `confirm_result`라는 응답 상태만으로 성공 처리하지 않았다.

| 정상 조건 지표 | A | B |
| --- | ---: | ---: |
| 공동 성공 | 4/6 | 2/6 |
| 독립 oracle의 안정적인 목적지 도달 | 4/6 | 3/6 |
| 실제 모델 호출 | 20 | 14 |
| 공급자 제한 시간 실패 | 1 | 4 |
| 계획/파싱 오류 | 0 | 0 |
| 잘못된 `verified` 완료 제안 | 0 | 0 |

전체 정상 조건에서 실제 적용된 안전 위반과 설정값의 예상 밖 변화는 모두 0회다. **B의 호출 수가 적다는 사실만으로 효율이 좋다고 평가할 수는 없다.** 공급자 오류로 목적지까지 진행하지 못한 작업도 호출 수가 작게 남는다. A/B의 공급자 실패 빈도 차이를 B 정책의 인과 효과로 해석할 근거도 부족하다.

## 2. A Bluetooth: 이동 3단계에 모델 호출 6회가 사용된 이유

에피소드: `settings-native-v2-20261120:settings_bluetooth:normal:A`  
`task_ref`: `cdef4821401957fb49d3672e` — [에피소드 원본 8번째 행](normal-episodes.jsonl)

실제 native 이동은 세 번이었다.

| 실행 시각 | 실제 실행 |
| ---: | --- |
| 6.362초 | `Connected devices` 탭 |
| 12.505초 | `Connection preferences` 탭 |
| 16.487초 | `Bluetooth` 탭 |

독립 oracle은 17.766초에 목적지의 안정적인 도달을 확인했다. 앱의 최초 `verified` 제안은 22.598초, 공동 성공은 22.611초였다. 목적지 안정 확인 뒤 완료 제안까지 4.832초가 추가로 걸렸다.

| 6 | `d2ddc43ea947c6d1b5a73e4f` | `result_only`, 2.404초 | 동일한 완료 후보가 다시 전달됐다. `observed_prediction_refined`로 수용된 뒤 실제 두 프레임에서 일치하여 검증됐다. |

호출 6회의 구성은 **실행된 이동 제안 3회 + 화면 지문 변경으로 폐기된 이동 응답 1회 + 완료 증거 요청 2회**다. 공급자 오류나 계획 오류로 재시도한 사례가 아니다. 마지막 완료 후보의 로컬 검증은 첫 프레임부터 `verified`까지 422ms였고, 두 번째 프레임은 `fresh`였다.

모델 대기 합계는 19.899초로 공동 성공 시간 22.611초의 약 88.0%다. 두 프레임 검증의 대기보다 클라우드 호출과 폐기 후 재요청이 큰 비중을 차지했다.

## 4. B 날짜·시간: 도착했는데 공동 성공하지 못한 이유

에피소드: `settings-native-v2-20261120:settings_datetime:normal:B`  
`task_ref`: `661d32483faea99f70a5ffc5` — [에피소드 원본 10번째 행](normal-episodes.jsonl)

| 시각 | 관찰된 사실 |
| ---: | --- |
| 3.126초 | 목록 스크롤 native 실행 수락 |
| 8.586초 | `System` 탭 native 실행 수락 |
| 12.607초 | `Date & time` 탭 native 실행 수락 |
| 13.858초 | 독립 oracle이 목적지의 안정적인 도달 확인 |
| 22.219초 | 네 번째 모델 요청의 공급자 실패 응답 후 앱 상태 `unavailable` |
| 30.080초 | 공통 관찰 창 종료. 목적지는 여전히 안정적으로 도달했지만 현재/과거 `verified` 제안은 없음 |

네 번째 요청 `37a280b40ee9169a9c2c5ca2`는 클라이언트와 서버 양쪽에 다음과 같이 남았다.

```text
planning_mode = next_action
model_calls = 1
model_wait_ms = 8628
response_status = unavailable
failure_kind = provider
failure_stage = provider
reason_code = provider_deadline_exceeded
provider_error = true
plan_or_parse_error = false
```

따라서 이 사례를 “`result_only` 요청이 실패했다”고 적으면 부정확하다. 실제 기록은 **목적지 도착 뒤 후속 계획·완료 증거 확보 과정에서 발생한 `next_action` 요청의 공급자 제한 시간 실패**다. HTTP 200은 정상적인 오류 봉투 전달을 의미하며, 모델이 정상 결과를 만들었다는 뜻은 아니다.

앞선 두 번째 요청 `f00edd38eb5a87e1a1a9d53e`에서 받은 초기 후보 `8d0e0b36892acfba5a06e3d3`는 `not_met`을 거친 뒤 `unsafe_prediction_discarded`로 폐기됐다. 세 번째 응답은 `deferred_actionable_proof`였고 후보가 없었다. 네 번째 응답에도 후보가 없었다. 완료 이벤트에는 `matched`, `first_frame`, `waiting_second_frame`, `verified`가 **한 번도 없다**.

즉, 완료 후보를 일치시킨 뒤 두 번째 프레임을 기다리다 멈춘 사례가 아니다. 목적지에 도착한 상태에서 사용할 완료 후보가 남지 않았고, 그 뒤 모델 요청도 실패했다. oracle의 unknown 샘플은 0회이며 정리 후에도 목적지는 존재했다. 물리적 목적지 도달 실패나 관찰 불가로 분류할 근거는 없다.

이 한 쌍에서 B의 목적지 안정 확인은 A보다 4.824초 빨랐다. 다만 모델 응답 시간·내용이 다른 단일 반복이므로 이를 B 정책의 속도 개선 효과로 일반화하지 않는다.

## 5. 정상 조건 전체에서 분리해야 할 실패

공급자 제한 시간 실패는 총 5회이며 모두 서버 종료 기록과 직접 연결된다.

| 작업·조건 | 실패 요청 `request_ref` | 모델 대기 |
| --- | --- | ---: |
| 접근성 A | `8f63b0ac8d3a8a9f0ef4c738` | 8.626초 |
| 접근성 B | `d4a0d0361be3634a7ea2545a` | 8.625초 |
| Bluetooth B | `5906ddab042bf95cd3fcf1ab` | 8.627초 |
| 날짜·시간 B | `37a280b40ee9169a9c2c5ca2` | 8.628초 |
| 언어 B | `f97299a3980523028f87625c` | 8.627초 |

이 다섯 호출의 모델 대기 합계는 43.133초다. 계획/파싱 오류나 native 실행 거부로 옮겨 분류하지 않는다.

언어 A는 다른 사례다. 스크롤과 `System` 탭이 native에서 수락됐고 공급자 오류는 0회지만, 13.862초에 `needs_input`으로 전환됐으며 언어 화면에 도달하지 않았다. 현재 아티팩트에는 해당 실행의 전체 expectation과 verifier 판정 이유가 저장되지 않아 정확히 어느 검증 조건이 handoff를 만들었는지는 확정할 수 없다. `performAction` 수락 자체를 목표 달성으로 해석해서도 안 된다.

정상 조건의 공동 성공 6회는 모두 실제 두 번째 프레임에서 `fresh` 판정을 거쳤다. 마지막 후보의 로컬 검증은 **416–426ms**였다. 성공 6회의 목적지 안정 확인 뒤 완료 제안까지 걸린 시간은 2.201–7.483초다. 완료 지연을 모두 “두 프레임 검증 대기”로 설명할 수 없다.

## 6. 확인된 낭비와 아직 모르는 원인

`discarded / changed_frame`은 정상 조건에서 5회다.

| 작업·조건 | 폐기된 요청 | 모드 | 해당 호출의 모델 대기 |
| --- | --- | --- | ---: |
| 디스플레이 A | `b5b2e0282836a87be5ce0c21` | `result_only` | 2.612초 |
| 디스플레이 B | `2669ae42f3eef578547322ae` | `result_only` | 4.113초 |
| Bluetooth A | `d7e04cd2b1c6ef02b1de410e` | `next_action` | 2.696초 |
| Bluetooth A | `6bf6135e4bcd34012ea5d2e6` | `result_only` | 2.749초 |
| 날짜·시간 A | `6fc339a3b88d20fab5f1da2b` | `next_action` | 3.199초 |

이 응답들에 소비된 모델 대기는 총 **15.369초**다. 이는 실제 관찰된 비용이며, 어떤 개선으로 그 시간을 전부 절약할 수 있다는 추정치는 아니다.

확인된 사실은 요청 시점과 응답 처리 시점의 화면 지문이 달라 응답을 버렸다는 것이다. 원본 화면·응답 본문을 저장하지 않았으므로 어떤 노드 변화가 지문을 바꿨는지는 이 로그만으로 확정할 수 없다. 전환 애니메이션, 스크롤 중간 프레임, 후속 AX 변경 같은 설명은 추가 검증이 필요한 가설이다. 현재 로그를 근거로 과거의 특정 관찰 투영 버그가 재발했다고 단정하지 않는다.

## 7. 범용성과 속도를 위한 다음 방향

우선순위는 완료 증거를 얻는 경로와 불필요한 재계획을 줄이는 것이다. 실제 실행의 화면·window·대상 신선도 검사는 유지한다.

1. **요청 전 안정 프레임 확인과 AX 이벤트 병합을 별도 실험한다.** 실제 화면 전환이 진행되는 동안 모델 요청을 중복 생성하는지 계측하고, 같은 의미의 연속 이벤트를 짧게 병합한다. 안정 확인에 추가된 시간과 줄어든 `changed_frame` 호출을 함께 평가해야 한다. 이것이 위 5회 폐기를 얼마나 줄이는지는 아직 검증하지 않았다.
2. **목표 수준의 완료 계약을 재사용하고 현재 native 증거로 검증한다.** 이동 중 보이는 버튼과 목적 화면의 수동 제목·상태를 구분하는 계약을 보존하고, 도착 시 새 모델 요청 없이 현재 화면의 두 프레임에서 검증 가능한지 실험한다. 앱·메뉴별 성공 규칙을 추가하는 방식 대신 package, 역할, resource, 요청된 상태와 목표 요구를 묶는 공통 계약을 사용한다. 계약은 불확실하거나 안전하지 않으면 폐기하고, 충족하지 않은 목표를 완료 처리하지 않는다.
3. **완료 후보의 재검증과 오래된 액션의 실행을 분리할 수 있는지 검증한다.** 예를 들어 Bluetooth A의 두 `result_only` 응답은 후보 key가 동일했다. 액션은 기존 지문·window 가드로 계속 차단하면서, 읽기 전용 완료 후보만 현재 native 화면에서 다시 검증하는 경로를 검토할 수 있다. 원래 요청·목표 계약의 연결, 기존 요구 보존, 안전성, 유일한 증거 대상, 두 프레임 신선도를 모두 통과해야 한다. 현재 결과만으로 이 변경의 안전성이나 절감 효과를 입증한 것은 아니다.
4. **공급자 제한 시간 실패는 별도 가용성 실험으로 분리한다.** 이번 정상 조건의 5회 실패를 B의 복구 정책 개선이나 완료 selector 수정으로 해결됐다고 주장할 수 없다. 동일한 요청 예산 아래 공급자 응답 성공률과 p95 지연을 반복 측정하고, 호출 횟수·모델 대기·사용자 성공을 함께 비교해야 한다. 시간 예산을 늘리거나 자동 재시도를 추가하는 것만으로 속도 목표가 개선됐다고 평가하지 않는다.

다음 변경은 한 번에 하나의 요인으로 검증하고, 현재 동결 코호트의 점수는 그대로 보존한다. v1과 v2는 관찰 창과 실행 시점의 코드가 다르므로, 두 코호트의 차이를 단일 수정이나 MetaController의 인과 효과로 해석하지 않는다. 최종 B Go/No-Go는 이 정상 조건 원인 분석이 아니라 전체 v2 36회와 사전 판정 기준으로 판단한다.
