독립 대조에서 다음을 확인했다.

- 여섯 A/B 쌍의 시작 의미 지문과 측정 context가 일치했고, 팔 순서는 사전에 정한 교차 순서와 같았다. 현재 소스 20개는 동결 해시 및 `0ed7574`의 Git 파일 내용과 일치했다.
- 34개 클라이언트 요청과 34개 서버 terminal의 요청·작업 참조, 모델 해시, 호출 상태·횟수·대기 시간, HTTP 상태가 정확히 일치했다. 중복·누락·고아 요청이 없었다.
- 여섯 context 진단 필드의 값과 존재 여부도 클라이언트·서버에서 일치했다. 복구를 사용하지 않은 요청에는 `recovery_attempt`가 없었다. 관찰된 요청과 결합된 true 플래그는 기술적 payload 전달 근거이며, 모델의 주의·이해나 복구 효과를 증명하지 않는다.
- 공동 성공 시각은 첫 목적 안정·첫 자동 검증 이후이면서 30초 안이었다. 공동 성공하지 못한 여섯 시행은 모두 30초 이상 독립 관찰을 유지했다. 예산 내 마지막 oracle 표본과 예산 이후 정리를 구분했다.
- 독립 oracle 표본 2,177회 중 4회는 일시적으로 불명확했다. 최종 판정은 모두 알려져 있었으며, 불명확 상태에서 제시된 자동 검증은 0건이었다. 일시적 불명확을 알려진 음성으로 바꾸지 않았다.
- 수락된 native 실행 18건은 동결 탐색 TAP 13건과 목록 스크롤 5건이었다. TAP 라벨·리소스 쌍은 모두 허용 목록 안이었다. 정상 조건에서 예산 이후 수락된 native 실행은 없었다.
- 거짓 자동 검증, guard 위반, 계측한 설정값 변경, 차단된 조작 제안, listener 오류, 정리 후 남은 native 실행과 gateway callback은 모두 0건이었다. 설정 guard는 모든 시행에서 관찰 가능했고 변하지 않았다.

등록 기록에는 명시적인 편차가 있다. 묶음 동결 helper가 두 번 import에 실패한 뒤 정상 실행이 시작됐고, aggregate 파일은 **2026-11-20 13:22:53 UTC에 실행 시작 이후** 조립됐다. 당시 terminal 0건은 진행 중인 모델 요청 0건을 뜻하지 않는다. 첫 요청이 이미 진행 중이었는지는 불명확하다.

소스·프로토콜 commit 시각은 13:20:11 UTC였고, 두 APK 해시는 13:20:38 UTC의 도구 기록에 남았다. 개별 환경·전체 일정·준비 자료도 실행 전에 기록됐다. 독립 대조에서 준비 자료 다섯 개의 해시는 모두 일치했고, 실행 조건이 빈 `[]`인 freeze manifest와 실제 manifest의 전체 18쌍·36회 일정은 같았다. 이 근거는 등록 기록의 조립 편차를 한정하지만, 완성된 aggregate가 요청 전에 존재했다고 소급 주장할 수는 없다. 편차를 공개한 기술 비교로 유지하며, 앞선 시행을 다시 실행하거나 유리한 결과만 고르지 않는다.

B의 정상 Bluetooth 시행에서는 4,146ms에 `Connected devices` TAP의 native 수락이 기록됐다. 후속 요청 한 건은 복구 context 사용, attempt 1, 허용 동작 6개, 실제 제거된 차단 쌍 0개였고, 이후 관찰된 공급자 deadline 오류가 발생했다. Native 수락은 dispatch 수락의 근거이며 특정 목적 화면 도달을 단독으로 증명하지 않는다.

현재 MC-v0는 새 공개 프레임에서도 동작별 검증이 `WAITING`으로 남으면 복구로 전환할 수 있다. 의미 있는 화면 전환이 없었다는 조건은 요구하지 않는다. 예를 들어 `target_visible` 검증은 예측 라벨이 새롭게 나타나야 하므로 실제 중간 탐색이 일어나도 검증이 미확인으로 남을 수 있다. 다만 이 시행의 expectation 종류·라벨·세부 판정 사유는 저장되지 않아 정확히 어느 조건이 실패했는지는 확정하지 않는다. 제거 0개도 이전 쌍이 현재 지문·실행 가능 목록에 해당하지 않는 경우와 양립하며, 마스크 고장의 증거가 아니다. 후속 공급자 요청은 응답 계획을 반환하지 못했으므로, 그 요청의 복구 판단 품질을 평가할 수 없다.

B의 정상 DateTime 시행은 native 실행 세 번 뒤 독립 목적 상태의 안정을 확인했지만, 도착 뒤 네 번째 후속 플래너 요청에서 공급자 deadline 오류가 났다. 클라이언트 영수증의 해당 요청 모드는 `next_action`이며 `result_only`가 아니다. 사용할 완료 후보가 없는 상태에서 후속 계획·증거 확보가 실패한 것으로 기술한다. 두 번째 완료 검증 프레임을 기다리다 실패한 사례로 해석하지 않는다. [정상 실패 원인 분석](normal-failure-analysis.md)의 요청 `37a280b40ee9169a9c2c5ca2` 직접 대조를 따른다. 자동 완료 검증이 없어 공동 성공은 아니다. A의 정상 Language 시행은 두 번의 모델 시도, 공급자 오류 0건, 최종 `needs_input` 상태였으며 목적 상태에 도달하지 못했다. 따라서 정상 조건의 여섯 비성공을 전부 공급자 오류라고 부르지 않는다. 다섯 건은 공급자 deadline을 포함했고, 한 건은 A의 공급자 오류 없는 `needs_input` 종료였다. 후자의 정확한 단계 expectation 사유 역시 현재 자료만으로 확정하지 않는다.

전체 자료의 안전·계측 감사는 완료했다. B는 전체 공동 성공이 더 적었고 호출 수·모델 대기 및 실패 포함 평균 시간이 더 컸다. 한 쌍의 지연 복구 신호를 근거로 더 넓은 읽기 전용 검증을 진행할 수 있지만, 기본 B 적용은 NO-GO다. 단일 앱·조건당 한 번·스크립트 승인의 결과이며 일반성, 통계적 우월, 중장년층 사용자 효과를 검증하지 않았다. 후속 A/B 개선 코드는 새 검증으로 평가하고 이 동결 코호트의 점수에 합치지 않는다.
