# 설정 작업 시작 20초 초과: 재현 검사와 구간 계측

**과거 504 세 건의 원인은 아직 확정하지 못했다.** 이번 변경은 성공률을 높였다는 결과가 아니라, 지연 재현 검사와 다음 시간 초과를 구분할 수 있는 계측 보완이다. 실기기는 사용하지 않았다. 20초 제한과 Jev 신뢰도 기준을 바꾸지 않았다. 운영 배포도 수행하지 않았다.

## 확인한 사실

[기존 재검사](../../../experiments/task-success/2026-11-22/recheck.md)의 설정 시작 네 건 중 세 건은 약 20초에서 504가 났고, 한 건은 정상 응답 뒤 목표에 도착했다. 당시 기록에는 워커 준비·화면 처리·모델 HTTP 시간을 구분할 정보가 없다. 모델이 느렸다고 단정할 수 없다.

현재 로컬 서버 코드의 격리 런타임을 실제 Jev와 연결해 재생했다. 합성 설정 홈에는 공개 제목·메뉴 세 개만 넣었다. 저장된 삼성 화면은 개인정보 필터를 거친 디스플레이·연결 화면 56·62노드다.

| 조건 | 재생 횟수 | 전체 런타임 중앙값 | 최소~최대 |
|---|---:|---:|---:|
| 계측 전 합성 홈 | 6 | 0.264초 | 0.251~0.564초 |
| 최종 코드 합성 홈 | 6 | 0.261초 | 0.258~0.477초 |
| 최종 코드 저장 삼성 화면 | 6 | 0.265초 | 0.261~0.463초 |

모두 런타임이 반환됐으며 이 조건에서 20초 초과는 재현되지 않았다. 합성 홈의 최종 여섯 건은 탭 대상으로 선택됐다. 삼성 화면 여섯 건은 네 건이 선택되고 Wi-Fi 두 건은 보류됐다. 빠른 반환은 올바른 안내·과제 완료와 다르다. 이 재생 횟수를 실기기 도착률이나 새 148회 설계의 분모로 사용하지 않는다.

이 검사는 **프로세스 시작부터 런타임 결과 반환까지**다. HTTP 진입, 인증·요청 큐, DB 선점, 목표 준비, Android 화면 수집·표시는 포함하지 않는다. 과거 실패 요청의 원본 화면·당시 부하를 그대로 재현한 것도 아니다. 소표본·시간대가 다른 호출이므로 전후 속도 개선으로 주장하지 않는다.

## 코드 보완

격리 워커가 다음과 같은 고정된 단계 이름만 부모 프로세스에 전달한다.

| 단계 | 확인하는 구간 |
|---|---|
| `worker_startup` | 프로세스 준비·모듈 로드·작업 전달 |
| `checkpoint_restore`, `engine_init` | 상태 복구·엔진 구성 |
| `request_translation`, `runtime_selection` | 요청 변환·엔진 전처리와 선택 경로 |
| `selection_candidates` | Jev 화면 후보·질문 구성 |
| `provider_http` | Jev 요청·연결·응답 대기. 모델 계산만의 시간이 아님 |
| `selection_validate` | 제공자 응답 검증 |
| `response_build`, `execution_event` | 결과·실행 기록 구성 |
| `checkpoint_capture`, `result_delivery` | 다음 상태 저장 자료와 결과 전달 |

부모가 종료를 기다리는 동안 단계별 시간을 기록한다. 기록은 부모가 단계 메시지를 받은 시각에 따른 근사치이며, 세부 함수별 CPU 프로파일은 아니다. 호출당 메시지는 64개로 제한하고 기존 네 개 동시 실행 제한·강제 종료·슬롯 회수 규칙을 유지한다.

시간 초과에는 `X-Click-Runtime-Phase` 헤더로 마지막 작업 단계를 추가한다. 워커가 스스로 `TimeoutError`를 반환한 경우도 오류를 직렬화하는 마지막 단계가 아니라 원래 멈춘 단계를 유지한다. 실패 로그는 WARNING, 정상 구간 로그는 INFO다.

예: `outcome=504 phase=provider_http`는 제공자 요청 구간에서 한도에 도달했다는 의미다. 이것만으로 원격 모델, DNS, 연결, 응답 스트림 중 하나를 단정하지 않는다. 헤더가 없는 504도 원인을 임의로 추론하지 않는다.

단계·숫자·요청 ID의 해시 참조만 기록한다. 화면 문구, 사용자 입력, 키, 제공자 오류 본문은 기록하지 않는다. 로그 출력이 고장 나도 원래 결과·프로세스 정리·슬롯 반환에 영향을 주지 않도록 보호했다.

실험 중계는 이 헤더의 허용된 단계만 `calls.jsonl`에 남기고, 집계기는 `runtime_turns`로 보존한다. 기존 결과 파일은 재작성하지 않았다. 새 구간을 수집하려면 이 서버 코드를 실제 검사 서버에 적용해야 한다.

## 검증

- 실프로세스 검사 10개 통과: 강제 시간 초과·자체 시간 초과의 단계 식별, 종료 후 슬롯 회복, 프로세스 간 격리, 제한된 진행 메시지, 로그 고장 보호.
- API 회귀 검사 110개 통과: 작업 시작·승인·상태 저장·캐시·실행 근거·개인정보 경계.
- HTTP/중계 검사 2개 통과: 단계 헤더 전달, 실패 후 버전 증가 없이 재시도, 알 수 없는 단계·인증 헤더 비기록.
- Jev 선택·삼성 화면 관련 검사 42개 통과. `phase-regression.log`의 51개 중 나머지 9개 프로세스 검사는 최종 10개와 중복이므로 합산하지 않는다.
- Python 구문과 공백 검사 통과.

## 재현과 다음 확인

저장소 루트에서 현재 Backend 의존성을 사용한다. 실제 Jev를 호출하며 지정된 공개 화면만 전달한다. 새 출력 파일을 사용해야 한다.

```sh
Backend/.venv/bin/python Backend/scripts/probe_runtime_start_latency.py --output /private/tmp/settings-synthetic-probe.json
Backend/.venv/bin/python Backend/scripts/probe_runtime_start_latency.py --scene recorded --output /private/tmp/settings-recorded-probe.json
```

다음 실제 설정 시작 실패가 발생하면 동일 요청의 API 시간, `X-Click-Runtime-Phase`, 해시 참조의 서버 구간 로그, 후보 수·Jev 호출 시간을 함께 확인한다. 그 자료로 지연된 구간을 특정한 뒤 해당 처리·호출을 수정한다. 제한 시간을 늘리거나 보류 기준을 낮춰 성공률을 높인 것처럼 만들지 않는다.

원자료: [계측 전 합성 재생](runtime-replay-baseline.json), [최종 합성 재생](runtime-replay-final.json), [저장 화면 재생](recorded-screen-replay.json). 최종 두 재생의 단계 시간은 각각 `.log` 파일에 있다.
