# 완료 증거 관리와 실패 계측 보완

**미관찰 완료 조건의 고착과 실패 요청 기록 누락을 보완했다.** Android 검사 142개와 관련 Backend 검사 226개, Lint 및 통제 검증 72회를 통과했다. 실제 Gemini 연결 점검 12회에서는 요청 20건과 서버 기록 20건을 요청 ID로 직접 결합했다. 누락·중복·고아 기록·호출 여부 불명확 건은 0이다.

이것은 구현과 계측의 검증이다. 실제 앱의 범용성, 속도 개선 또는 중장년층 사용자 효과를 입증한 실험은 아니다. 기존 FE 배치·버튼과 기본 CURRENT 정책을 유지했고, 결과 확인 중 안내 문구만 상황에 맞게 조정했다.

## 완료 증거 관리

- 사용자 목표와 작업 ID는 로컬 `goal_contract`에 해시로 결합한다. 저장된 증거를 다른 목표·작업에 그대로 옮길 수 없다.
- 미래 화면 이름은 `provisional` 후보로 보관한다. 아직 보지 못한 후보는 서버의 잠긴 `state.completion`으로 보내지 않는다. `app-task.v2` 통신 규격은 유지한다.
- 후보 교체는 현재 공개 관찰에서 확인된 증거에만 허용한다. 절 수를 줄이거나 다른 앱으로 바꾸거나 필요한 선택·체크 상태를 버리지 못하도록 검사한다. 같은 네이티브 대상의 라벨·리소스 별칭을 서로 다른 증거로 중복 계산하지 않는다.
- 후보 버전·상태·변경 사유와 해시 이력을 최대 8개 보관한다. 후보 버전이나 키가 바뀌면 이전 후보의 첫 관찰은 재사용하지 않는다.
- 같은 후보를 서로 다른 새 네이티브 관찰에서 최소 350ms 간격으로 확인한 뒤 `supported`로 확정한다. 사용자 확인 결과와 확정된 조건은 유지하고, 다시 완료를 제시할 때에도 현재 화면을 재검사한다.
- 단계가 모두 끝났어도 최종 증거가 없으면 **추가 조작 없는 증거 탐색**을 허용한다. 연속해서 같은 기본 화면이면 자동 요청을 반복하지 않으며 기존 전체 요청 상한도 유지한다. 이 경로에 도구가 반환되어도 실행하지 않는다.
- 기존 미완료 작업의 조건은 임시 후보로 이관하고 목표·진행·기록을 유지한다. 명백히 잘못된 `selected=false` 방향만 해제할 수 있고, 다른 네이티브 조건과 절 수는 보존한다. 사용자가 확인한 완료는 이관 과정에서 바꾸지 않는다.

핵심 회귀 사례는 ‘틀린 미래 제목 저장 → 단계 수행 완료 → 실제 다른 제목 관찰 → 후보 교정 → 새 관찰 두 번 → 완료 증거 확정’이다. 관찰되지 않은 다른 추측으로 교체, 조건 축소, 원하는 상태 반전, 같은 대상의 중복 증거, 서로 다른 후보의 관찰 혼합도 거절했다.

## 실패 계측

앱의 디버그·후보 빌드는 실행을 시작한 요청의 결과를 `noBackupFilesDir/app-task-diagnostics`에 기록한다. 요청·작업·관찰 ID는 SHA256 앞 24자로 저장하고, HTTP 상태·제한된 오류 코드·대기 시간·서버 진단의 제한된 분류를 남긴다. 원문 목표·화면·응답 본문·예외 메시지·토큰은 기록하지 않는다. 최대 256KiB 파일 두 개로 회전하며 UI 버튼은 추가하지 않았다. 앱 종료 시 큐에서 실행 없이 폐기된 요청까지 보장하는 영구 장부는 아니다.

시험 전용 파사드 v2는 수신·처리한 POST의 최종 결과를 기록한다. 인증·경로 오류, 공개 화면 거절, JSON 규격 오류, 본문 시간 초과, 서비스 예외와 응답 전송 실패를 포함한다. 각 요청은 클라이언트와 같은 `request_ref`·`task_ref` 및 서버의 `server_ref`로 직접 대조한다.

| 상황 | 기록 원칙 |
|---|---|
| 서비스 진입 전 거절 | HTTP 상태·고정 거절 이유, 확인된 모델 호출 0회 |
| 서비스의 정상 반환 | `called`의 명시적 값과 제한된 모델 대기 시간 |
| 서비스 진입 후 예외 | 호출 여부 `unknown`, 호출 수·대기 시간 `null` |
| 다른 요청·작업·화면의 응답 | 메타데이터를 현재 요청에 귀속하지 않음. 파사드는 `502 / service_identity_mismatch`로 기록 |
| 응답 전달 실패 | 서버에서 관찰한 호출과 클라이언트의 전송 실패를 함께 보존 |
| 공급자·파싱·계획 검증 실패 | 서로 다른 단계·종류·고정 코드. Pydantic 오류는 제한된 필드 경로와 타입만 저장 |

미래 완료 라벨의 검증도 현재 화면 허용 목록과 분리했다. 동일 시험 패키지의 제한된 공개 예측 선택자는 새로운 별칭이라는 이유만으로 거절하지 않는다. 실제 관찰 노드는 계속 고정된 공개 시험 컨트롤만 허용한다. 앞선 4건의 거절 원인을 소급 확정하거나 이전 자료를 수정하지 않았다.

## 검증 결과

| 검증 | 결과 |
|---|---|
| Android 검사 | 142개 통과, 실패·오류·건너뜀 0. 통제 72회 행렬 검사 1개 포함 |
| Backend 관련 검사 | 226개 통과 |
| Android Lint | 통과 |
| 모델 없는 통제 검증 | 72회, 잘못된 완료·안전 위반·표현 차이 실행 거절 0 |
| 실제 Gemini 연결 점검 | 정상 6개 작업 × 1반복 × A/B = 12회 |
| 직접 요청 대조 | 20/20건, `DIRECT_JOIN_RECONCILED`, 누락·중복·고아 기록 0 |
| 호출·대기 시간 불확실성 | 불명확한 요청 0, 기록된 호출 20회 모두 대조 |
| 남은 모델 실패 | 공급자 시간 초과 7건, 완료 계약 검증 실패 1건. 모두 원인 분류와 요청에 연결됨 |

연결 점검의 목적 상태는 A 4/6·B 5/6, 완료 검증 제시는 각 1회였다. 이 작은 정상 조건 점검을 이전 72회와 비교해 개선 효과로 계산하지 않는다. 공급자 시간 초과와 모델의 완료 조건 오류도 아직 해결된 것이 아니다. 이번에는 해당 실패를 누락 없이 확인할 수 있게 됐다.

전체 72회 성능 행렬이 아니므로 `preflight_subset`으로 기록하고 기존 성능 판정 게이트는 통과시키지 않았다. MC 기본 활성화 보류는 유지한다. 가상 UI 대기와 실제 API 응답 시간도 계속 분리한다.

자연어 별칭의 의미가 완전히 같다는 것을 구조 검사만으로 증명하지는 못한다. 현재 방어는 목표·앱·조건 수·네이티브 상태·관찰 대상의 보존이며, 실제 앱과 복합 목표에서의 검증은 별도 단계다. 서버 경험 재사용도 확정된 완료 조건만 받도록 보수적으로 제한되며, 속도 개선을 측정한 변경으로 보지 않는다.
