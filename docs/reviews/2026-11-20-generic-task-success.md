# 범용 요청 성공 판정 점검

2026-11-20, Asia/Seoul. 기준 코드는 `0c5f509`이다. 설정 한 종류의 실패가 아니라 요청 → 계획 → 조작 → 관측 → 결과 확인의 공통 경로를 점검했다.

기존 범용 앱 실행에는 전체 요청의 완료 조건이 없었다. `TaskExpectation`은 다음 조작의 변화만 표현했고, 서버는 `screen_changed` 이외의 기대 결과가 있으면 `advances_subgoal`을 자동으로 켰다. 기기 내 단순 실행은 화면 변화만으로도 하위 목표를 완료할 수 있었다. 반대로 마지막 상태에 직접 도달했거나 처음부터 원하는 상태인 경우, 이를 조작 기록과 별도로 확인할 경로가 없었다. 기존 AI-Agent의 조건 평가기와 설정별 성공 계약은 별도 경로이며, 그 테스트 통과가 범용 앱의 완료 판정 연결을 보장하지 않았다.

관측에도 공통 결함이 있었다. 결과가 일반 TextView에 표시되면 버튼·목록·일부 제목만 남기는 관측에서 빠졌다. 입력·선택 검증은 일시적인 노드 ID와 좌표에 매여 재그리기 뒤 같은 대상을 놓쳤다. 조작 뒤 관측 시각을 검사하지 않았고, 읽지 못한 화면과 실제로 변화가 없는 화면을 모두 대기 끝에 실패로 기록했다. 수동 누르기 또한 선택한 행의 텍스트 자식에서 발생한 이벤트를 놓쳤다. 결과 종료 UI는 기억·학습 관련 서버 API 지원 여부에 종속되어 있었다.

| 공통 단계 | 변경한 기준 |
| --- | --- |
| 요청 전체의 결과 | 계획과 별도로 `TaskCompletion`의 최대 8개 조건을 보관한다. 하나의 최종 앱에서 관측할 공개 라벨, 네이티브 리소스·역할, 명시한 checked/selected 상태의 논리곱이다. 수락한 조건은 다음 모델 응답이 바꾸거나 제거할 수 없다. |
| 결과 관측 | 버튼 실행이나 과거 완료 비트와 관계없이 현재 상태를 검사한다. 이미 도달한 상태, 사용자가 직접 도달한 상태, 복원한 작업도 같은 경로를 사용한다. 서로 다른 새 관측에서 350ms 이상 조건이 유지되어야 결과 확인을 제시한다. |
| 단계 진행 | 모델이 하위 목표 달성을 명시하고 검증 가능한 결과가 있어야 진행한다. 일반 화면 이동, 목록 이동, 원하는 상태를 지정하지 않은 토글 변화로 하위 목표를 완료하지 않는다. |
| 결과 텍스트 | 요청한 공개 결과 라벨과 정확히 일치하는 정적 텍스트만 추가 관측한다. 화면 본문 전체나 입력값을 추가 전송하지 않는다. OCR만으로 네이티브 결과를 확정하지 않는다. |
| 대상과 시각 | 동일 앱의 유일한 리소스·역할·라벨로 재그리기 뒤 대상을 다시 찾는다. 중복 후보, 다른 항목, 조작 이전 관측은 성공 근거로 쓰지 않는다. 정확한 입력값 확인도 다시 찾은 필드에서 기기 내 검사한다. |
| 수동 조작 | 기존 `GuidedActionTracker`를 공통으로 사용해 대상 행의 비조작 텍스트 자식 이벤트를 연결한다. 다른 항목의 이벤트는 연결하지 않는다. |
| 관측 불가 | 새 화면·대상을 읽지 못하면 unknown/waiting으로 남긴다. 실제 조건 불충족과 구분하고 실패 횟수에 누적하지 않는다. |
| 기억 경로 | 과거 동작 재사용이 현재 요청의 완료 조건 작성을 건너뛰지 않도록 한다. 기억한 선택 변화도 저장된 도착 화면 해시와 일치해야 한다. |
| 사용자 확인 | 결과 확인을 기본 화면에 표시하고, 기억 API 지원 여부와 분리한다. 기기에서 조건을 관측한 사실과 사용자가 결과에 만족해 종료한 사실은 구분한다. 결과 판정의 상태·사유·출처·조건 수만 진단 로그에 남긴다. |
| 이전 서버 | 연결한 OpenAPI의 요청·응답 양쪽에 완료 조건 지원이 있을 때만 새 필드를 전송한다. 복원 데이터에 조건이 있어도 이전 서버에는 전송하지 않는다. |

주요 구현은 `Backend/app/services/app_task.py`, `Backend/app/schemas/app_task.py`, Android의 `AppTaskCompletion`, `AppTaskController`, `AppTaskVerifier`, `AppTaskObservation`이다. 기존 설정별 검증의 증거 기준은 유지한다.

검증 결과는 다음과 같다.

- Backend: `test_app_task`, `test_app_task_learning`, `test_app_guide`, `test_task_outcomes`, `test_system_api`, `test_android_install_gate`의 146건 통과.
- AI-Agent: `test_verification_conditions`, `test_engine_flow`, `test_runtime_reliability`, `test_success_selection`의 121건 통과.
- Android: 범용 작업·기억·관측·서버 계약·결과 UI, 기존 설정 성공 계약과 `ClickOverlayServiceExecutionTest`를 포함한 439건 통과, 실패·오류·건너뜀 0건.
- `:app:assembleDebug`, `:app:lintDebug` 통과. 기존 빌드 산출물의 파일 읽기 대기를 피하려고 저장소의 `validation-gradle.init.gradle`로 `/tmp/click-success-build-20261120`에 분리 빌드했다.
- OpenAPI를 `Backend/scripts/export_openapi.py`로 재생성했다. 작업 중 develop에 추가된 기존 수정도 보존한 상태에서 Android 통합 검사를 수행했다.

앱 이름을 바꿔 같은 엔진을 실행하는 테스트는 합성 관측을 사용하며 실제 앱 사용 시험을 뜻하지 않는다. 연결된 Android 기기가 없어 이번 작업에서 실기기 시험은 수행하지 못했다. 실제 모델이 요청에 맞는 최종 조건을 작성하는 품질, 접근성에 드러나지 않는 결과, 거래·인증 완료의 독립 증명은 이 회귀 테스트만으로 보장되지 않는다. 관측할 조건을 만들지 못한 요청은 사용자 결과 확인 경로를 사용한다. 서버의 최종 사용자 결과 기록은 기존 `user_confirmed` 의미를 유지한다.
