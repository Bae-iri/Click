# A 통합본의 Gemini·JeV 완료 경로 시간 비교

**JeV terminal 완료 경로의 기본 도입은 NO_GO다.** 응답은 빨랐지만 실제 JeV 요청3회가 모두 보류돼 완료 후보를 제공하지 못했다. 정책별 공동 성공은 Gemini9/12·JeV5/12였고 실패 포함 평균도15.686초에서20.447초로 늘었다. A/CURRENT와 기본 Gemini 경로는 유지하며 B는 실행하지 않았다.

두 정책의 다음 화면·조작 계획은 모두 같은 Gemini다. 따라서 전체 성공4건의 차이를 모두 JeV 탓으로 돌리지는 않는다. 완료 경로에 실제 노출되지 않은 시행의 Gemini 탐색 오류와 응답 변동도 포함돼 있다. 이 보고서는 종료된24회 원자료와 동결 분석의 결과를 사용한다.

## 실제로 비교하는 부분

| 배정 조건 | 다음 화면·조작 계획 | 마지막 완료 증거 선택 |
| --- | --- | --- |
| Gemini 완료 정책 | Gemini `gemini-3.8-flash` | Gemini `gemini-3.8-flash` |
| JeV 완료 정책 | 같은 Gemini `gemini-3.8-flash` | 적격한 단일 이동 목표에서 JeV `jev-1.14.0` |

JeV는 현재 공개 관찰에서 이미 만들어진 증거 계약 중 하나를 고르거나 보류한다. 새 selector·조작·계획·진행 상태를 만들지 않는다. 단일 긍정 화면/탭 이동만 적격이며, 복합·입력·구체적인 값·변경 요청 등은 JeV 호출 전에 기존 Gemini 경로를 사용한다. JeV를 한 번 호출한 뒤 낮은 신뢰도·보류·오류가 발생하면 같은 요청에서 Gemini를 추가 호출하지 않는다. 안전한 현재 후보가 없으면 임의 완료 대신 사용자 확인으로 전환한다.

배정된 “JeV 정책”과 실제 “JeV 요청”은 다르다. Clock처럼 미리 받은 조건을 로컬에서 확인해 마지막 모델 호출이 없는 시행도 전체 배정 분모에 남긴다. JeV의2초는 I/O 예산과 늦은 응답 거절 기준이며 Gemini의 killable worker와 같은 OS 종료 보장이 아니다. 실제 초과 시간과 보류도 결과에 포함한다.

## 출처와 사전 배정

실행 소스는 **`0ee53cf98b36ccd1d3e59640432e3f1c1beb0421`**이다. [동결 기록](source-freeze.json)은 2026-11-21 11:23:58 KST에 소스·APK·환경·준비 자료와 전체 일정을 고정했다. 이때 facade는 미시작, 포트는 닫힘, 모델 시도는0회였다. 실행 중 runtime·기준·목표·준비 자료는 수정하지 않았다. [종료 기록](cohort-closure.json)은11:34:28 KST에 소스69개·준비 자료10개의 해시 불변과 포트 닫힘, 실제24회 종료를 확인했다.

세 앱(Settings·Clock·Files)의 기존6개 정상 목표를 정책2종×반복2회, **24회**로 배정했다. 목표가24개인 것은 아니며, 동일6개 목표를 반복한다. 블록 순서는 다음과 같다.

| 순서 | 반복 | 완료 정책 | 예정 시행 |
| --- | --- | --- | ---: |
| 1 | r1 | Gemini | 6 |
| 2 | r1 | JeV | 6 |
| 3 | r2 | JeV | 6 |
| 4 | r2 | Gemini | 6 |

G→J→J→G 순서를 사용하지만 각 블록의 목표 순서는 고정돼 있어 무작위 실험으로 부르지 않는다. 양쪽 실제 완료 provider에 모두 노출된 같은 목표/반복 쌍이4개 미만이고 안전·계측 조건을 만족할 때만, 미리 고정한 r3 Gemini6→JeV6을 전부 추가할 수 있다. 품질 회귀나 계측 오류를 더 유리한 표본으로 덮기 위한 확장은 허용하지 않는다. 조건부12회가 실행되지 않으면 NOT_RUN이며 실패로 채우지 않는다.

상세 ID와 조건은 [manifest](manifest.json), [사전 프로토콜](../../../experiments/metacontroller/goal-first-integrated-timing-protocol-v1.md)을 따른다. [앞선 A 정상6회](../2026-11-21-goal-first-completion/README.md)는 다른 소스의 종료 코호트다. 이번24회에 합치거나 무작위 대조군으로 취급하지 않는다.

## 성공과 시간의 기준

공동 성공은30초 안에 독립 목적 상태700ms 안정, 현재 runtime의 native 두 프레임≥350ms 검증, 조작 후750ms 대기·미처리 native0·false verified0을 모두 만족한 경우다. 모델 신뢰도·클릭 수락·계획 완료 비트만으로 성공을 만들지 않는다. 메뉴·보호 입력·오래된 화면을 완료 증거로 인정하지 않는다.

주 시간 지표는 공동 성공 시각 또는 실패30초를 사용한 **전체 배정 실패 포함 평균**이다. 성공 사례만 빨라지고 실패가 늘면 개선으로 판정하지 않는다. 공급자 실패·보류·설정 미비도 배정 분모와 실제 호출 기록에 남긴다. 다음을 함께 보고한다.

- 정책별·앱별 공동 성공과 실패 포함 시간.
- Gemini 탐색·Gemini 완료·JeV 완료의 실제 요청 시도와 unknown.
- 모델 경계 대기, 큐 대기, client work−model wait의 잔여시간.
- 목적 상태 첫 안정 도달 뒤 공동 성공까지 시간과 추가 native 조작.
- 양쪽 완료 provider에 실제 노출된 같은 목표/반복 쌍의 기술 비교.

oracle은700ms, native 증거는 최소350ms를 기다려 첫 native 검증−첫 안정 도달의 차이가 음수일 수 있다. 모델 경계 시간은 worker·HTTP·공급자 처리 등을 포함하며 순수 모델 CPU 시간과 같지 않다. 호출 시도나 알려진 토큰 소계를 실제 청구 금액으로 환산하지 않는다.

## 사전 검증 범위

[검증 기록](unit-verification.json)에 따라 Android 관련269개·Backend 관련469개 검사가 오류 없이 통과했다. 앱 APK·계측 APK 빌드와 **앱 모듈 lint**도 통과했다. [실제 native 구성요소9개](native-component.json)는 모델 호출 없이 통과했으며, 완료한 상태의 pending 계획·메뉴·오래된 관찰·보호 화면을 구분했다. 이는 탐색 성능 결과와 합산하지 않는다.

저장소 전체 lint에는 이번 변경 밖의 design-preview 모듈이 API29의 `setMinHeight/Width`를 minSdk26에서 사용하는 기존 문제가 남았다. 전체 lint 통과로 보고하지 않는다. 전체 단위 검사 시도도 관련 검사 범위로 전환했으므로 모든 저장소 검사를 완료했다고 주장하지 않는다. 인증 회복의 오래된 static mock 문제는 테스트만 실제 `RefreshSender` 주입 경로에 맞춰 수정했고 관련 검사에 포함했다. FE 디자인이나 production 인증 동작을 바꾸지 않았다.

표의 JeV 열은 **완료 정책 배정**이다. Display의 두 JeV 정책 시행도 실제 마지막 완료 선택은 Gemini를 사용했고 성공했다. Clock은 마지막 provider 호출 없이 로컬 조건으로 완료하거나 첫 Gemini 탐색 요청이 실패했다. 이 결과를 JeV가 해당 앱에서 직접 성공·실패한 횟수로 읽으면 안 된다.

실제 JeV 요청은 Recent r1·r2와 Documents r2의3회였다. 세 시행 모두 목적 상태에는 도달했지만 `jev_completion_abstained`로 완료 후보0건·runtime verified0건이었다. 기록은 보류를 확인하지만 `insufficient` 선택과 신뢰도 미달 중 어느 원인인지를 구분할 원문/점수는 보관하지 않았으므로 그 비율을 추정하지 않는다. 낮은 신뢰도에서 추가 Gemini를 호출하지 않는 사전 정책도 유지했다.

반면 Settings와 Clock의 정책 간 성공 차이에는 **Gemini 탐색 중의 미도달·공급자 오류**가 있었다. JeV 정책 Documents r1의 실패도 Gemini 계획 단계의 `ungrounded_result_state`였고 JeV를 호출하지 않았다. 따라서 전체4건의 성공 감소가 모두 JeV 때문에 발생했다고 단정할 수 없다. 직접 양쪽 완료 provider에 노출된 짝은 Recent r1·r2의2쌍이며, 두 쌍 모두 Gemini는 완료했고 JeV는 보류했다.

## 실제 시간 병목

| 실제 요청 경로 | 시도 수 | 모델 경계 대기 중앙값 | 범위 |
| --- | ---: | ---: | ---: |
| Gemini 탐색 | 35 | **4.186초** | 2.962~8.631초 |
| Gemini 완료 | 6 | **4.290초** | 3.172~6.564초 |
| JeV 완료 | 3 | **0.240초** | 0.193~0.289초 |

JeV의 세 응답은 빠르게 돌아왔지만 모두 보류여서 **빠른 응답을 빠른 작업 완료로 바꾸지 못했다.** 서로 다른 목표·공급자 경계의 작은 표본이며 모델 순수 연산 성능의 배수 비교로 사용하지 않는다. Gemini 탐색의 공급자 오류4회도 지연 분포와 제품 결과에서 제외하지 않았다.

로컬 두 fresh frame 확인의 중앙값은 Gemini 정책425ms·JeV 정책426ms였다. client queue 대기는44회 합계9ms·중앙값0ms, client work−model wait 차이는중앙값7ms였다. 이 잔여시간은 CPU 시간이나 실제 모바일 네트워크의 전체 왕복 시간이 아니다. 현재 loopback 자료에서는 로컬 확인보다 모델 경계 대기가 더 큰 부분이다.

첫 안정 도달 후 추가 native 조작은 두 정책 모두0건이었다. 분모는 도달한 Gemini9회·JeV8회이며 미도달7회를0회 재탐색으로 위장하지 않았다. 다만 JeV 정책에서 목적 상태에 도달한3회가 완료 검증 없이 끝났으므로, 재탐색이 없다는 사실만으로 완료 인식이 충분하다고 할 수 없다. 성공 사례에 한정한 안정 도달→공동 성공 중앙값3.225초·0초도 실패를 포함한 성능으로 일반화하지 않는다.

## 판정과 실험 종료

사전 gate 중 안전·계측은 통과했지만 전체와 세 앱 모두 성공이 감소했고, 실패 포함 평균은 증가했으며, 시도 수는 같았다. 실제 양쪽 완료 provider에 노출된 짝도 요구한4개에 못 미치는2개다. **JeV terminal 완료 선택을 기본값으로 도입하는 판정은 NO_GO**다. A/CURRENT는 유지하고 기본 완료 공급자도 Gemini로 둔다.

조건부12회는 **NOT_RUN**이다. 노출 쌍이 부족하다는 이유만으로 확장할 수 없으며, 이미 관측한 품질 회귀가 있는 상태에서 더 유리한 표본을 얻기 위한 확장은 사전 프로토콜이 금지했다. `conditional_extension_eligible=false`에 따라24회에서 종료했다. 기존 첫 A6 코호트를 합치거나 성공·실패를 재분류하지 않았다.

최종 수치의 근거는 episode의 `joint_success`, 직접 연결한 provider 기록과 동결 분석기다. 실행 중 보조 진행 표시가 존재하지 않는 `primary_success` 필드를 읽었던 문제는 최종 집계에 사용하지 않았고 원자료·판정 기준을 수정하지 않았다.

다음 개선에서는 JeV의 보류 원인을 닫힌 진단값으로 분리하고, 같은 목적 상태의 독립 검수로 후보 구성·신뢰도와 실제 완료 증거를 함께 평가해야 한다. 이번 결과만으로 신뢰도 기준을 낮추거나 모호한 화면을 완료로 인정하지 않는다. 단일 accountless Android17 에뮬레이터·고정 앱/목표 순서·반복 소표본·scripted approval이며 중장년층 참여자는 없다. 모든 기기·앱의 범용성, 사용성, B 재도입 또는 운영 전체에 대한 결론으로 확대하지 않는다.
