## 결론

- **T(완료 단계화)는 GO 후보다.** 6번 작동했고 모두 맞는 페이지 제목("디스플레이", "알림")을 모델 없이 묶었다. 거짓 완료는 0이다. 설정 과제에서 도착 후 완료 인정까지 B 4.3–7.1초가 C 0.5–0.9초로 줄었다. B가 같은 자리에서 쓰던 결과 확인 호출(5회, 회당 3.6–6.7초)이 C에서는 0회다.
- **Gemini 호출이 25회에서 19회로 24% 줄었다**(서버 기준, 같은 16회씩). 목표 도달은 13/16으로 같고 거짓 완료는 두 팔 모두 0이다.
- **첫 단계 기억은 평가 회기 2회에 쓰였고, 그 회기는 모델 호출 0회로 약 1.2초에 목표에 도달했다**(알림, 세계시각). B는 같은 기억이 회수됐지만(`remembered` 4회) 완료 조건 게이트 때문에 한 번도 쓰지 않았다.
- **R, M1, M3은 이번 실행에서 판단할 수 없다.** 화면이 바뀌어 버려진 응답이 두 팔 모두 0건이라 R이 작동할 기회가 없었다. 실행기 거절(`rejected`)도 0건이라 M1이 작동할 일이 없었다. 팀 수정(`recaptureLike`)으로 원래 문제가 줄었을 수 있다. M3 상황(기억 재실행이 `screen_changed`로 기록)은 1건 생겼지만, 그 뒤 회기가 없어 효과를 볼 수 없다.

## 자체 인정이 C에서 하나 적은 이유

C 알림 평가 회기는 기억 탭(264ms) → 목표 도달(516ms) → T가 서버에서 2ms 만에 완료 조건을 돌려준 흐름이었다. 그런데 기기에서 `IOException`이 기록되면서 하네스의 인정 대기가 끝났고, 모의 사용자가 바로 확인했다. 그래서 자체 인정이 기록되지 않았다. 어떤 요청이 실패했는지는 이번 로그로 확인하지 못했다. 팀원 실험에서도 기억 탭 직후의 후속 요청이 2/2 실패했으므로, **기억 경로 직후의 요청 실패**를 따로 추적해야 한다.

## 두 팔 공통의 문제 (장치와 무관)

1. **시계 과제의 자체 인정 0/16.** 삼성 시계의 탭은 접근성에서 `tab`이 아니라 `button`(selected=true)으로 나온다. 모델이 이것을 완료 조건으로 묶지만 기기가 인정하지 않는다. T도 `tab` 역할만 받으므로 작동하지 않았다. 선택된 버튼형 탭을 어떻게 다룰지 정하는 별도 수정이 필요하다.
2. **설정 디스플레이 도달 1/4.** 실패 6회 중 4회가 첫 호출의 공급자 시간 초과(약 8.65초)나 `unavailable`이었다. 이전 두 실험에서도 같은 패턴이 있었다.
3. 서버 `ConnectionAbortedError` 8건은 회기 종료 시 진행 중이던 요청이 끊긴 것으로 보인다. 두 팔 모두에서 났다.

## 다음 단계

1. **T 분리 검증 후 운영 반영 검토.** 이번에는 다른 장치와 한 팔에 묶었다. T만 켠 팔과 B를 비교해 거짓 완료 0과 호출 감소를 다시 확인한다. 범용성 확인을 위해 다른 앱 과제도 넣는다.
2. **시계형 탭(button + selected) 처리.** T와 기기 완료 인정 양쪽에 같은 기준을 적용한다.
3. **기억 경로 직후 요청 실패 추적.** 첫 단계 기억의 실사용 전 필수다.
4. **R, M1, M3은 그 상황을 만드는 조건에서 다시 측정한다.** 지연 주입(`eval_delayed`) 조건이나 다단계 과제가 필요하다. M1은 실행기 거절이 실제로 남아 있는지부터 확인한다.
