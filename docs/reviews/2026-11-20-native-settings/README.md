# 실제 Android Settings A/B 결과 — B 기본 적용 보류

**현재 MC-v0인 B는 NO-GO다.** 이번 36회에서 목적 화면 도달 건수는 A/B 모두 6/18이었고, 도달과 자동 완료 검증을 함께 만족한 시행은 모두 0/18이었다. Gemini 호출은 A 37회, B 44회로 B가 7회(18.9%) 많았다. 이 결과는 이번 제한된 탐색 범위의 기술 검증이며, B의 일반적인 효과가 없다는 결론이나 두 정책의 동등성 검정은 아니다.

## 무엇을 실행했나

실제 Android 17 Settings 앱에서 여섯 목표 × 정상·첫 TAP 무반응·첫 TAP 5.5초 dispatch 지연 × A/B를 한 번씩 실행했다. A는 CURRENT, B는 MC-v0이며 둘 다 같은 `gemini-3.8-flash` 플래너를 사용했다. B가 별도의 모델이라는 뜻은 아니다. 학습된 UIAnchor reflector 전체를 재현한 실험도 아니다.

계정 없는 임시 ARM64 에뮬레이터와 격리 debug 앱을 사용했다. 실제 접근성 이벤트, 생산 `AppTaskController`·`AppTaskExecutor`·`AppTaskService`를 연결했고 조작 승인은 스크립트로 제공했다. UI는 영어, 목표 발화는 한국어다. 서버의 사용자 인증·기억 검색은 실험용으로 분리했다. 실기기·여러 앱·중장년층 참여자 검증은 수행하지 않았다. 생산 FE와 기본 A 정책은 변경하지 않았다.

모델 없이 여섯 과제의 홈 음성 대조·공개 Intent 및 GUI 양성 대조·설정값 불변 검사를 통과했다. 실제 같은 화면의 native 실행은 수락됐고, 바뀐 화면·창 및 별도 테스트 APK의 빈 password 화면 조작은 거부됐다. 보호 fixture는 성능 평가 앱 수에 포함하지 않는다. 초기 보호 fixture의 빈 입력 판정 실패는 모델 호출 전에 수정했으며 [준비 실패 기록](preparation-guard-failure.json)을 보존했다.

전체 36회 일정과 코드·APK·정답·환경은 최초 모델 요청 전에 고정했다. 정상 12회의 안전·계측 감사가 통과한 후 같은 일정의 장애 24회를 추가했다. 정상 에피소드 12개와 서버 기록 31개가 최종 파일의 동일한 byte prefix로 남아 있으며 재선택·중복 정상 실행은 없다.

## 조건별 결과

`도달`은 관찰 종료 시 독립 UiAutomation 목적 판정이 양성이었던 시행이다. `공동 성공`은 예산 30초 안에 목적 상태 700ms 안정 확인, 현재 유효한 앱의 자동 완료 검증, 미처리 native 조작 없음이 모두 성립한 시행이다. 사용자 최종 확인/DONE는 자동으로 누르지 않았다.

| 조건 | 도달 A / B | 공동 성공 A / B | Gemini 호출 A / B | 실제 장애 노출 A / B |
|---|---:|---:|---:|---:|
| 정상 | 4/6 · 4/6 | 0/6 · 0/6 | 17 · 14 | 해당 없음 |
| 수락 후 무반응 | 0/6 · 0/6 | 0/6 · 0/6 | 8 · 14 | 6 · 5 |
| 5.5초 dispatch 지연 | 2/6 · 2/6 | 0/6 · 0/6 | 12 · 16 | 4 · 5 |
| 전체 | 6/18 · 6/18 | 0/18 · 0/18 | 37 · 44 | 10 · 10 |

모든 36회가 실행·평가 가능했고 A/B 시작 상태와 측정 환경이 일치한 18쌍을 확보했다. 클라이언트 요청과 서버 terminal 81건을 요청·작업 해시로 직접 결합했다. 미확인 공급자 호출은 0건이다. HTTP 422로 제안이 차단된 뒤에도 이미 발생한 모델 시도는 호출 수에 포함했다. 호출은 계측된 공급자 시도 횟수이며 토큰 수나 실제 청구 금액이 아니다.

| 추가 지표 | A | B |
|---|---:|---:|
| 현재/과거 자동 완료 검증 제시 | 0 / 0 | 0 / 0 |
| 실패 포함 평균 공동 완료 시간 | 30초 | 30초 |
| 누적 모델 대기 | 204.562초 | 253.023초 |
| 공급자 제한 시간 초과 | 6건 | 12건 |
| 실험 탐색 계약 밖 제안 차단 | 1건 | 5건 |
| 거짓 검증 / 설정값 변경 | 0 / 0 | 0 / 0 |
| 정리 후 남은 native 조작·gateway callback | 0 | 0 |

누적 모델 대기는 B가 23.7% 많았지만 사용자 완료 속도나 금전 비용으로 바꿔 해석할 수 없다. 공동 성공 시행이 없어 성공 시 속도 우위를 추정할 자료도 없다. 실패 포함 시간은 조기 실패에도 공통 예산 30초를 부여하므로 빠른 실패를 속도 이득으로 세지 않는다. 측정 종료 후 공급자 정리는 총 26.760초, 시행당 최대 8.640초였으며 예산 안 성공으로 올리지 않았다.

## 연구 질문에 대한 답

1. **B가 더 잘 도달하는가?** 이번 조건별 도달 총계에서는 개선이 관찰되지 않았다. 정상군에서 성공한 과제 구성까지 같지는 않다(A만 도달 1쌍, B만 도달 1쌍). 같은 총계를 정책 동등성으로 해석하지 않는다.
2. **장애 복구가 실제 성공을 늘리는가?** B의 복구 판단은 12회 활성화됐지만 공동 성공은 없었다. 무반응 조건에서 양팔이 실제로 노출된 쌍은 5쌍, 지연은 4쌍이었다. 장애 전 모델 실패로 주입되지 않은 시행도 배정 분모에 유지하되 복구 실현 근거로 사용하지 않았다. 복구 활성화 횟수는 성공 횟수가 아니다.
3. **범용성과 속도에 이득이 있는가?** 단일 Settings 앱으로 범용성을 판단할 수 없다. 이번 범위에서는 도달 총계가 늘지 않은 채 전체 호출이 증가했고, 완료 검증 제시도 없어 속도 이득을 입증하지 못했다. 공급자 제한 시간 초과 18건과 탐색 계약 밖 제안 차단 6건도 함께 고려해야 한다.
4. **B GO인가?** 기본 적용은 보류한다. 현재 B를 그대로 넓은 검증으로 확대하기보다 공통 완료 경로의 진단과 측정 보완을 먼저 진행한다. 기본 A와 실험용 B 분리를 유지한다.

## 해석의 한계

- **안정 도달의 관찰 기회가 같지 않다.** 정상 안정 도달은 A/B 각각 4건, 지연은 A 0건·B 2건이다. 지연 A의 두 도달 시행은 실제 dispatch 뒤 약 1.1초에 관찰을 끝냈고 B는 dispatch 뒤 약 16~17초까지 관찰했다. 따라서 안정 도달 전체 4 대 6을 B의 안정성 이점으로 주장하지 않는다. 공동 성공은 양팔 모두 검증 제시가 없어 0이며 이 제한과 별도로 유지된다.
- **최초 도달 시각을 저장하지 않았다.** `late_goal_after_budget`는 예산 뒤 목적 상태가 존재했다는 값이며, 이미 예산 안에 도달한 상태도 포함한다. 이 값을 늦은 최초 도달 건수로 사용하지 않는다.
- **완료 미제시의 정확한 원인을 확정할 로그가 없다.** 실제 앱의 `result_assessment.status`가 `verified`인지 계측했으나 검증 제시는 0건이었다. 후보 selector와 채택·거절 이유는 보존하지 않았다. 모든 도달 시행에서 검증 제시가 없었다는 사실은 확인됐지만, 특정 selector 오류나 특정 코드 한 줄을 원인으로 단정할 수 없다.
- **차단된 제안의 구체 유형은 남기지 않았다.** 허용된 탐색 계약 밖 제안 6건이 실제 설정값 변경 제안이었다고 단정하지 않는다. 공개 검색 등 카탈로그 밖의 대안 경로도 이번 실행에서는 허용하지 않았다. 제한된 도구 범위에서의 결과다.
- **거짓 검증 0건만으로 검증 정확성을 입증하지 않는다.** 검증 제시 자체도 0건이었다.
- 단일 이미지·단일 앱·조건당 1회이며 공급자 응답도 서로 다르다. 독립 정답은 별도 코드지만 생산 관찰과 Android 접근성 데이터를 공유한다. 통계적 유의성·실사용 효과·중장년층 사용성을 주장하지 않는다.

## 다음 방향

우선 완료 후보의 생성·보류·채택·거절 단계를 작업/요청 hash, evidence version, 후보 hash, 폐쇄형 이유 코드로 기록한다. 목표나 입력 원문은 기록하지 않는다. 이 근거로 **A/B 공통 완료 경로**에서 실제로 막힌 부분을 수정한다. 완료 판정을 느슨하게 만드는 방식은 피한다.

새 프로토콜에서는 제품의 안내 종료와 독립 관찰 종료를 분리하고 양팔을 같은 30초 창에서 관찰한다. 최초 안정 도달, 검증 제시, 공동 성공 시각을 따로 저장한다. v1 원본과 사전 기준은 그대로 둔다.

구조는 기본 관찰·검증을 공유하고 **실패가 확인된 경우에만 제한된 국소 복구**를 수행하는 방향이 적합하다. 새 LLM 재계획 전에 재관찰·대기를 우선하며, 재실행은 명시적으로 안전하고 반복 가능한 조작에만 제한한다. 복구 횟수·호출 예산을 고정하고 실제 성공 증가와 함께 평가한다. 공개 검색 등 대안 도구를 추가한다면 준비 검사와 새 프로토콜에 먼저 포함해 A/B 양쪽에 동일하게 제공한다. 이 방향은 다음 검증안이며 이번 자료로 최적 구조가 입증됐다는 뜻은 아니다.

공통 동작과 계측을 확보한 뒤 여러 앱·반복 시행·실기기로 확대하고, 마지막으로 중장년층 사용자에게 이해도·개입 부담·복구 안내를 검증한다.

## 검증과 자료

관련 Backend 190개, Android 19개 클래스 130개, debug/계측 APK 빌드와 lint가 통과했다. 전체 Backend 실행은 363개 통과 시점에 중단했으며 전체 통과로 표시하지 않는다. 전체 Android 실행에서 `AuthRefreshRecoveryTest` 3개 실패를 관찰했고, 표준 application ID의 별도 빌드에서도 같은 3개 실패를 재현했다(`AuthRefreshTest` 3개는 통과). 원인은 확정하지 않았고 인증 소스는 수정하지 않았다. 상세는 [검증 기록](verification.json)이다.

실험 소스는 기준 `32041e5`와 동결 기록의 추가 파일이다. 이후 원격 온보딩 변경을 보존해 통합하므로, 정확한 성능 재현에는 [통합 기록](integration.json)의 `frozen_source_commit`을 사용한다. 통합 후 빌드 검증과 원래 36회 성능 측정은 구분한다.

원격 온보딩 변경을 보존한 통합 소스에서는 별도 출력 경로로 debug/계측 APK 빌드, lint, 관련 22개 클래스 142개 테스트가 통과했다. 36회 성능 결과를 통합 후 코드에서 재측정한 것은 아니다. 전체 보고 자료의 무결성은 [파일 해시](artifact-sha256.json)로 확인할 수 있다.
