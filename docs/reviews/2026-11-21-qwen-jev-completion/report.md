## 조건

- 기기는 SM-N981N이고, 친구 2차 실험의 계측 APK(`com.click.metamemoryexperiment.uitestdriver`)를 썼다.
- 서버는 `develop` 08e67737에 Jev 결과 확인을 플래너와 분리하는 수정을 더한 것이다.
- 두 팔 모두 Qwen(`qwen/qwen3.8-flash`)이 계획하고, `APP_TASK_COMPLETION_PROVIDER=jev`이다.
  - A는 서버 규칙 검사 T를 켜고, B는 T를 껐다.

**해석 주의.** 이 브랜치의 2차 수정 전 코드에서는 `goal_first` 요청의 완료 판단을 Qwen이 직접 했다. 그래서 Jev는 24회 중 1번만 호출됐다. 이 비교는 사실상 **T를 켰을 때와 껐을 때의 차이**이고, Jev의 완료 판단 성능을 평가한 결과가 아니다.

## 이후 수정 (같은 브랜치)

역할을 이렇게 나눈다. **Qwen은 다음 동작을 계획한다. T와 Jev는 현재 완료 근거를 확인한다. 기기가 최종 검증한다.**

- 완료 근거는 T를 먼저, 그다음 Jev가 확인한다. `result_only`와 `goal_first` 모두 같다. Jev는 단일 목적지 이동 목표에서만 쓰고, 로컬 모델 실행에서는 부르지 않는다.
- T와 Jev가 근거를 찾지 못하면 Qwen은 다음 동작을 고른다. 이때 `goal_status`는 `not_satisfied`나 `uncertain`만 낼 수 있다. Qwen이 낸 완료 근거는 현재 근거든 미래 예측이든 묶지 않는다.
- Jev가 다루지 못하는 목표(예: "블루투스 켜줘")는 기존처럼 Qwen의 근거를 쓴다.

수정 후 실기기 재확인과 앱 알림 판정기의 로딩 대기 보완이 남았다.
