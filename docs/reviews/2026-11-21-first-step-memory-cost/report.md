## 요약

- **A 정책에서 기억 출처 동작이 처음으로 실제 제안·승인됐다.** C군(첫 단계 회수 허용) 평가 6회 중
  2회(알림 eval1·eval2)다. 기존 정확 일치 기억 B군은 0/6, 디스플레이 과제는 세 군 모두 0회다.
- 기억이 쓰인 2회는 첫 제안 285·305ms, 목표 도달 625ms였다. 같은 과제에서 플래너를 쓴 성공 회기는
  첫 제안 4,850~7,491ms, 도달 5,154~7,759ms였다. 첫 플래너 호출 한 번(입력 1,159~1,350,
  출력+생각 136~416토큰)을 건너뛰었다.
- **회기당 호출 비용 절감은 확정하지 못했다.** 기억 동작 뒤의 후속 호출이 두 번 모두 공급자 시간 제한
  (약 8.63초)으로 실패해 토큰 사용량이 없다. 호출 수는 회기당 2→1이지만 후속 호출의 정상 비용은 모른다.
- **기억이 스스로 근거를 쪼개는 운영 코드 결함을 찾았다.** 이 결함 때문에 eval3에서는 회수가 다시
  `needs_data`가 됐다(아래 "eval3에서 기억이 꺼진 원인").
- 42/42회 완료, 누락·중복 키 0, 시작 준비 실패 0, 매칭 안 된 호출 0. 이번 일정의 보고된 토큰 기준
  추정 비용은 약 $0.090(78회 호출 중 71회만 usage 보유)이다.

## 실행 조건

SM-N981N / Android 13, Gemini 3.8 Flash, 기준 커밋 `8b480bb`, MC 정책은 CURRENT(A)로 고정했다.
과제는 공개 설정 탐색 두 개(settings_display, settings_notifications)다. 세 비교군을 돌렸다.

| 군 | 기억 | 첫 단계 회수 |
|---|---|---|
| A | 끔 | — |
| B | 정확 일치(운영 규칙) | 운영대로: 완료 조건이 정해진 뒤에만 |
| C | 정확 일치(B와 같은 서버 규칙) | 평가 회기에서만 최초 동작 전 최대 2초 대기 후 허용 |

과제·군마다 학습 4회와 평가 3회를 돌려 총 42회(학습 24, 평가 18)다. 오류 주입 없는 정상 조건만
돌렸다. 회기 예산은 25초, 목표 관찰 뒤 검증 대기는 1.5초다. 군마다 별도 기억 저장소를 쓰고,
순서는 고정 회전/역전 방식이다. 모의 사용자는 독립 UiAutomation 정답이 700ms 유지될 때만 확인한다.
실행 APK 해시는 [source-freeze.json](source-freeze.json)과 일치한다. 실행 중 조건은 바꾸지 않았다.

A·B의 실패 1회씩은 첫 플래너 호출의 공급자 시간 제한으로 25초 예산을 다 쓴 회기다(A 알림 eval2,
B 알림 eval1). 기억과는 무관하며 분모에서 빼지 않았다. 군 간 토큰 합계는 usage 누락 수가 달라서
직접 비교하지 않는다. C의 경과 시간이 짧은 이유는 기억 회기 2회(625ms)와 실패 회기가 없다는 점이
섞여 있다.

### 기억이 쓰인 회기와 쓰이지 않은 회기

| 알림 과제 C | 첫 제안 | 목표 도달 | 호출 | 결과 |
|---|---:|---:|---:|---|
| eval1 | 285ms (기억) | 625ms | 1, 오류 | 확인 |
| eval2 | 305ms (기억) | 625ms | 1, 오류 | 확인 |
| eval3 | 5,645ms (플래너) | 5,917ms | 2, 정상 | 확인 |

정상 성공 회기는 모두 호출 두 번이다. 첫 플래너 제안(입력 1,159~1,350, 출력+생각 136~416토큰)과
완료 조건을 묶는 `confirm_result`(입력 776~889, 출력 32~212토큰)다. 기억 회기는 첫 플래너 호출을
건너뛰었지만, 기억 탭 뒤 완료 조건이 묶이지 않은 상태로 후속 플래너 호출(`completion_bound=false`)이
나갔고 두 번 모두 8.63초 시간 제한으로 실패했다. 따라서 절감은 "첫 호출 한 번 생략, 약 $0.0014~0.0026"
수준까지만 말할 수 있고, 후속 호출이 정상 응답했을 때의 회기 전체 비용은 측정하지 못했다.
후속 호출 실패 2/2는 표본이 둘뿐이라 기억 경로 때문인지 판단하지 않는다.

### eval3에서 기억이 꺼진 원인: 기억 재실행이 근거를 쪼갠다

서버 회수 로그에서 C 알림 과제의 첫 화면 후보는 learn3부터 `remembered`였다. eval2에서 근거가
두 묶음(지지 4건 + 1건)이 됐고, eval3에서 4건 + 2건이 되자 `needs_data`로 바뀌었다.
일곱 번의 시도 모두 같은 화면·같은 대상이었고, 기대값만 달랐다. 플래너 실행 5회는 `target_visible`,
기억 실행 2회는 `screen_changed`였다.

- [app_task_experience.py:207](../../../Backend/app/services/app_task_experience.py#L207)은 회수한
  동작을 내보낼 때 `target_visible`을 `screen_changed`로 바꾼다.
- [app_task_experience.py:174](../../../Backend/app/services/app_task_experience.py#L174)의 묶음 키에는
  expectation이 들어 있어서, 재실행 기록이 원래 후보와 다른 후보로 쌓인다.
- 두 번째 묶음도 지지 2건에 도달하면 선택지가 둘이 되고, `len(choices)==1`일 때만 회수하는 규칙
  ([:214](../../../Backend/app/services/app_task_experience.py#L214)) 때문에 기억이 꺼진다.

이 경로는 실험 옵션이 아니라 운영 서버 회수 코드다. 기억을 한 번 쓸 때마다 다음 회수를 막는 방향으로
작동하므로, 반복 사용에서 기억 재사용률이 스스로 떨어진다. 이번 실행에서는 고치지 않았다(실행 중
조건 변경 금지). 수정안은 묶음 키에서 `target_visible`/`screen_changed`를 같은 값으로 정규화하거나,
내보낼 때 원래 기대값을 유지하는 것이다. 수정 뒤에는 운영 회귀 검사와 같은 일정을 다시 돌려야 한다.

### 디스플레이 과제에서 기억이 쓰이지 않은 이유

C 디스플레이 과제의 회수는 learn1~eval3 내내 `needs_data`였다. 사용자 확인 경로로 인정된 분석이
B·C 합산 14건 중 3건(route_steps=1)뿐이라 주 후보의 `supporting_tasks_after_adverse`가 0으로 남았다.
도달은 했지만 분석이 재사용 가능한 경로로 인정하지 않은 것이며, 원인은 이번에 더 추적하지 않았다.

### B가 기억을 쓰지 않은 이유

B의 회수 기록은 모두 `completion_known=false`였다. 운영 기기 빠른 경로는 완료 조건이 묶인 뒤에만
기억을 쓰고, 이 한 동작 과제에서는 첫 동작 전에 완료 조건이 정해지지 않는다. 이전
[통합 보고서](../2026-11-21-meta-memory-integration/report.md)에서 본 게이트가 그대로 재현됐다.

## 공급자 오류

78건 중 7건이 공급자 오류였고, 모두 8,627~8,634ms 시점에서 `ProviderError`로 끝났다. 서버 플래너의
약 9초 시간 예산에 걸린 것으로 보이며 이전 통합 실행에서도 같은 패턴(7건)이 있었다. 이번 실행의
7건은 모두 알림 과제에서 났다(디스플레이 0건). 원인은 확인하지 않았다.

## 해석 한계

- 기기 한 대, 과제 두 개, 군당 평가 6회, 그중 기억 사용 2회다. 통계적 효과나 일반 앱 성능을 주장하지 않는다.
- usage가 없는 요청은 0이 아니라 미상으로 둔다. 비용은 공개 단가([pricing-reference.json](pricing-reference.json))
  기반 추정이며 실제 청구서를 확인하지 않았다.
- C의 첫 단계 회수는 평가 회기에만 켜는 실험 옵션이다. 기존 생성자와 운영 기본값은 바꾸지 않았다.
  회수한 동작도 실행 직전 화면 재검사·매 동작 사용자 승인·네이티브 검증을 그대로 거친다.
- 네이티브 `verified` 제시가 0/42이므로 완료 판정 안전성의 근거로 쓰지 않는다.
- 성공한 학습 기억을 인위로 보충하거나 완료 조건을 미리 주입하지 않았다.
