# Qwen 화면별 선택 — 파일 앱 두 과제 — 2026-11-21

[호출별 결과](replay.jsonl) · [재생 스크립트](replay.py)

## 배경

첫 에뮬레이터 실험에서 설정·시계 네 과제는 완료됐지만 파일 앱 두 과제는 멈췄다.

- **최근 파일**: 메뉴(서랍)를 연 뒤 다음 단계로 이어지지 않았다.
- **문서**: 서버가 Qwen의 계획을 거절했다.

Qwen 짧은 선택은 "처음 보는 순수 버튼 메뉴" 한 번에만 쓰였다. 그다음 화면, 그리고 체크 가능한 칩이 있는 파일 앱 홈은 Qwen 일반 계획으로 갔다. 이 일반 계획은 완료 근거의 상태값 때문에 서버 검증에서 자주 거절된다([지연 보고서](../2026-11-21-gemini-call-latency/report.md)의 다운로드·이미지 2건과 같은 원인).

## 실기기에서 찾은 원인 (SM-N981N, DocumentsUI)

파일 앱 서랍의 행(최근, 이미지, 문서 …)은 `행 > [아이콘 프레임, 글자 열 > "최근"]` 구조다. 행 이름이 **손자** 노드에 있다. `AppTaskObservation`은 직속 자식 글자만 라벨로 붙이므로 서랍 행이 모두 **이름 없는 버튼**으로 나갔다. 이 상태에서는 어떤 모델도 "최근"을 고를 수 없다.

## 변경

1. **서버** `APP_TASK_OPENROUTER_SHORT_MENU=screen`(새 값, 옵트인). 목적지 하나로 가는 과제에서는 매 화면마다 Qwen이 ID 하나를 고른다. 고르는 대상은 둘 중 하나다.
   - 지금 누를 컨트롤
   - 이미 도착했음을 보여주는 앱바 제목. 목적지 이름이나 그 짧은 형태여야 한다.

   제목 후보에는 가드가 있다.
   - 목적지 이름 전체가 아직 버튼으로 남아 있는 화면에서는 제목을 주지 않는다. 예: "알림" 화면에 "앱 알림" 행이 있는 경우.
   - 행 영역 안의 글자는 제목으로 주지 않는다.
   - 고른 제목은 기존 완료 근거 검증과 기기 검증을 그대로 거친다.

   여러 단계 과제("열고 … 해줘")와 복구 요청은 기존 플래너를 쓴다. `=1`(첫 메뉴만)의 동작은 바꾸지 않았다.
2. **기기** `AppTaskObservation`: 클릭 가능한 행에 라벨이 없으면 손자 노드의 공개 글자까지 본다. 손자까지만 보므로, 다섯 단계 아래에 있는 파일 카드의 파일 이름은 계속 읽지 않는다.

## 실제 Qwen 호출 재생

기기에서 캡처한 파일 앱 화면 4개(홈, 서랍, 최근, 문서)를 새 관측 규칙으로 투영했다. 이를 `AppTaskService`에 넣어 OpenRouter `qwen/qwen3.8-flash`를 실제로 호출했다. 과제는 2개이고 화면은 8개다. 이 중 미도달 화면 2개는 도착 근거를 고르면 안 되는 경우다.

| 프롬프트 | 정답 | 호출 중앙값 | 평균 입력/출력 토큰 |
|---|---:|---:|---:|
| v1 (첫 문구) | 5/8 | 1.89초 | 411 / 11 |
| v2 (짧은 이름 규칙, 메뉴 열기 규칙, 온도 0) | **24/24** (3회) | 1.83초 | 468 / 12 |

v1이 틀린 3건은 모두 `none`이었다. 홈에서 "루트 표시"를 누르지 않았고, 서랍에서 "최근"을 "최근 파일"로 보지 않았고, 문서 화면의 제목 "문서"를 도착으로 보지 않았다. 거짓 도착은 0건이었다.

## 한계

- 캡처는 uiautomator 덤프를 기기 관측 규칙에 맞춰 흉내 낸 것이다. 기기 안의 실제 `AppTaskObservation` 결과와 끝까지 실행한 결과는 아니다. 설정·시계 과제와 함께 에뮬레이터 하네스로 다시 확인해야 한다.
- 원본 캡처에는 계정 이메일이 있어 커밋하지 않았다. 결과 파일에는 공개 라벨만 남았다.
- 기기 1대, 앱 1개, 과제 2개다.
