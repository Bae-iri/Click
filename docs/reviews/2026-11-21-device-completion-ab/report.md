# 실기기 완료 판정 A/B: 도착 후 모델 없이 완료 확인

[프로토콜](protocol.md) · [소스 해시](source-freeze.json) · [회기 원자료](live/episodes.jsonl) · [서버 호출 기록](live/facade-logs/provider-calls.jsonl)

## 요약

- **현재 운영(C)은 도착한 순간 기기에서 바로 완료를 확인했다.**
  - 판정기가 정상인 과제 6회 중 6회가 네이티브 `verified`였다.
  - 모든 회기에서 목표 도달과 같은 시점에 확인됐다. 도착 후 추가 호출은 0건이고, 회기당 모델 호출은 1회다.
- **기준선(A)은 6회 모두 도착했지만, 1.5초 안에 기기가 완료를 확인한 회기는 0회였다.**
  - 도착 후 확인 전용 모델 호출을 5번 기다렸다(2.4~5.3초).
  - 회기당 모델 호출은 2.17회다.
  - 오늘 아침 첫 단계 실험의 0/42와 같은 문제다.
- **서버 triage만 켠 B는 6회 중 5회가 확인됐고, 도착 후 0.6~0.8초가 걸렸다.**
  - 모델 대신 서버 왕복 한 번(모델 호출 없음)이 필요했다.
  - 1회는 첫 호출의 공급자 시간 초과로 실패했다. B는 재시도가 꺼져 있다.
- **실패를 포함한 평균 소요 시간:** A 7.98초, B 10.04초(시간 초과 1회 포함), **C 5.94초**.
- **거짓 완료는 판정기가 정상인 과제에서 세 군 모두 0건이다.** "소리 및 진동" 과제의 판정기 문제는 아래에 따로 적었다.

## "소리 및 진동" 과제: 판정기 결함

- **증상:** 세 군 모두 9회 중 8회가 "기기는 `verified`, 판정기는 미도달"로 기록됐다(A 2, B 3, C 3). 나머지 1회(A)는 예산 소진으로 실패했다.
- **확인:** 실험 뒤 폰에서 소리 설정 화면을 직접 열어 UI를 덤프했다. 실제 화면은
  `소리 및 진동 / 소리 / 진동 / 무음 / 벨소리 / …`이고, 판정기가 찾는 랜드마크 **"소리 모드"는 이 One UI 화면에 없다**.
- **결론:** 판정기가 이 기기에서는 도착을 판정할 수 없다. 이 과제는 목표 도달과 거짓 완료 집계에서 뺐다.
  - 기기의 `verified`가 실제 도착이었는지는 이 판정기로 증명하지 못한다.
  - 변경이 전혀 없는 A에서도 같은 패턴이 나왔으므로, 이번 변경 때문에 생긴 것은 아니다.
- 프로토콜에는 거짓 verified가 나오면 중단한다고 적었다. 하지만 하네스는 이 모드에서 자동으로 멈추지 않았고, 결과를 본 뒤
  원인을 위와 같이 확인했다. 다음 실행 전에 랜드마크를 실제 화면 기준(예: "벨소리")으로 고치고, 사전 점검에 판정기 점검을 추가한다.

## 해석 한계

- 기기 한 대, 판정기가 정상인 과제 2개, 군당 6회다. 효과의 방향과 크기를 보는 탐색 결과다.
- 군 순서는 고정 회전이고, 공급자 지연은 시간대마다 달라진다. 첫 호출 대기 중앙값은 A 4.6초, B 5.1초, C 4.2초였다.
- 1회 재시도는 C에서 시간 초과가 나지 않아 이번에 검증되지 않았다.
- 시계 타이머는 사전 점검에서 시작 상태를 만들지 못해 결과를 보기 전에 뺐다.
