# 공개 앱 B2: 구현 변경과 검증 범위

**이번 변경은 A/B의 공통 완료 경로와 요청 낭비를 줄이고, B가 실제 화면 전환을 관찰한 경우에만 제한적으로 다음 판단을 이어가도록 구성했다.** 우선순위는 범용성, 그다음 속도와 비용이다. 이 문서는 구현과 실행 전 검사만 설명한다. 현재 진행 중인 공개 앱 실험의 성공률·속도·토큰 절감 효과는 아직 주장하지 않는다.

실행 소스는 **`63ecb80a3ae22582bf37570df480ec95035b1fd2`**로 동결됐다. [소스·APK 동결 기록](source-freeze.json)에 commit/tree, 코드·APK·준비 자료의 해시, 동결 전 관측 모델 시도 0회, facade 미시작과 loopback port 닫힘이 기록돼 있다. 이후 결과 문서가 추가돼도 이 실행 소스와 혼동하지 않는다. [사전 프로토콜](../../../experiments/metacontroller/native-public-apps-protocol-v1.md)의 목표·시간·성공 기준도 실행 중 바꾸지 않는다.

## 1. 이전 v2가 드러낸 문제

[실제 Settings v2 보고서](../2026-11-20-native-settings-v2/README.md)에서 전체 공동 성공은 A 4/18, B 3/18이었다. 관측 Gemini API 시도는 A 48회, B 60회였다. 복구 context와 실행 capability 전달은 확인됐지만, 그 전달만으로 B의 성공률이나 효율이 좋아지지는 않았다.

| v2에서 확인한 사실 | 이번 변경의 목표 |
| --- | --- |
| 무반응 조건에서 B는 API 28회, 공동 성공 0/6회였다. A도 0/6회지만 API는 9회였다. | 같은 경로에서 진전 없는 복구 요청을 반복하지 않도록 실제 전송 경계에 예산을 둔다. |
| 정상 조건의 `changed_frame` 폐기 5회에 모델 대기 15.369초가 들었다. | 화면 전환 직후 자동 재계획을 짧게 병합하고, 읽기 전용 완료 후보는 현재 증거로 재검증한다. |
| 위 폐기 중 `result_only` 후보 3개는 같은 native window였고, 이후 동일한 후보 key가 실제 검증됐다. | 오래된 액션과 현재에도 유효한 완료 후보를 같은 방식으로 버리지 않는다. |
| 목적지 도달 뒤 후속 공급자 요청이 실패해 완료 후보를 얻지 못한 사례가 있었다. | 이미 존재하는 로컬 완료 증거를 먼저 사용한다. 후보가 없는 공급자 실패까지 해결됐다고 주장하지 않는다. |

세부 요청·후보 hash와 시각은 [v2 정상 실패 분석](../2026-11-20-native-settings-v2/normal-failure-analysis.md)에 있다. 15.369초는 폐기된 응답에 실제 소비된 모델 대기 합계다. 이번 변경으로 그 시간을 모두 절약할 수 있다는 예측값은 아니다. 무반응의 28회도 토큰·청구 금액이나 공급자 내부 추론 완료 건수가 아닌 관측 API 시도 수다.

## 2. A/B 공통: 읽기 전용 완료 후보 재검증

기존에는 요청을 보낸 뒤 화면의 전체 지문이 달라지면 응답 전체를 폐기했다. 이제 다음 조건을 모두 만족하는 **로컬 `resultOnly` 요청**에 한해 완료 후보만 현재 화면에서 다시 검증한다. 모델 응답의 자칭 모드나 실험용 정답으로 이 경로를 활성화하지 않는다.

- 원래 요청과 응답의 protocol·request·task·관찰 ID·지문 연결이 유효해야 한다. 원래 목표와 현재 task identity도 같아야 한다.
- 요청 당시와 현재의 앱 선택 generation이 같아야 한다. 앱을 바꿨다가 되돌아온 경우도 이전 generation의 응답은 버린다.
- 응답에 액션이 없어야 한다. 오래된 응답의 액션이나 계획을 새 화면에 이식하지 않는다.
- 원래 화면과 현재 화면은 같은 package, 같은 유효한 native window여야 한다. 현재 화면은 공개 상태여야 한다.
- 현재 native 프레임은 미래 시각이 아니고, 15초 이내이며, 원래 요청 프레임보다 오래되지 않은 새 관찰이어야 한다.
- 후보는 현재 실제 native 화면에서 이미 `MATCHED`여야 한다. 증거 대상이 중복되지 않고 목표에 안전해야 한다. 보이지 않는 미래 selector를 이 예외 경로로 새로 받아들이지 않는다.
- 기존 `memory.offerCompletion`을 통해 요구 조건 보존과 지원된 증거의 불변성을 그대로 검사한다. 맞는 제목 하나를 찾았다는 이유로 기존 checked/selected 등 다른 요구를 삭제하지 않는다.

수용하더라도 즉시 완료 선언하지 않는다. 이전 검증 프레임을 버리고 현재 프레임부터 **두 새 native 프레임**으로 검증을 다시 시작한다. 같은 package/window에서 관찰 ID가 달라야 하고, 캡처 시각 간격과 단조 시계 경과가 각각 350ms 이상이어야 한다. window가 바뀌면 첫 프레임부터 다시 확인한다. 캡처 시계가 앞으로 움직였다는 이유만으로 최소 관찰 시간을 통과할 수 없다.

앱 선택이 요청 도중 바뀌면 일반 응답 경로에서도 오래된 계획·액션·후보를 적용하지 않는다. 폐기 후 현재 화면을 새로 관찰하므로 새로 선택한 앱이 다음 AX 이벤트 없이 멈춰 있는 문제도 방지한다. 이 경우에도 앱 열기 등 새 조작에는 기존 승인이 필요하다.

관련 코드: [Controller](../../../Frontend/app/src/main/java/com/click/service/overlay/AppTaskController.java), [완료 계약](../../../Frontend/app/src/main/java/com/click/service/overlay/AppTaskCompletion.java), [요구 조건·증거 이력](../../../Frontend/app/src/main/java/com/click/service/overlay/AppTaskMemory.java).

## 3. A/B 공통: 자동 재계획 전 안정 프레임 확인

최초의 명시적 요청은 기존처럼 바로 진행한다. 이미 가능한 로컬 완료 검증, 안전한 로컬·캐시 제안도 유료 계획 대기보다 먼저 처리한다. **실제 `screenChanged` 알림이나 수락된 조작 이후의 자동 유료 재계획**에만 짧은 대기 경로를 적용한다.

이 대기 경로는 같은 package/window에서 두 새 프레임의 조작 대상·상태·좌표가 250ms 안정되는지 확인한다. 대기용 key는 조작 대상의 역할·resource·공개 라벨·좌표와 selected/checked/value 존재 상태를 사용한다. 수동 제목·시계 같은 비행동 텍스트, raw viewport 내용과 수동 스크롤 컨테이너의 상속 라벨은 대기 판단에서 제외한다. 반복되는 화면 내용만으로 계획이 계속 미뤄지지 않도록 하기 위한 범위다.

AX 이벤트는 별도의 한 번 예약된 wake로 병합한다. 250ms보다 잦은 이벤트가 와도 같은 타이머를 계속 취소·연장하지 않는다. 유료 계획이 처음 대기한 시점부터 상한은 1,000ms이며, 화면이 계속 바뀌면 새 관찰을 확보한 최신 프레임으로 요청한다. 새 프레임을 확보하지 못하거나 창·신선도 조건이 불명확하면 요청하지 않고 기존 안내 경로로 전환한다. 앱 변경·보호 화면·명시적 도구 선택·종료는 남은 대기를 취소한다.

대기 중에는 `submitted`와 `resultDiscoveryScreen`을 전송 완료처럼 먼저 저장하지 않는다. 실제 요청을 보내거나 제안을 확정하는 시점에 기록하여, 다음 재관찰이 같은 화면이라는 이유로 예정된 요청 자체를 생략하지 않게 했다.

**대기용 key는 실행 허가나 성공 판정에 쓰지 않는다.** 요청 이후의 원래 전체 지문 검사와 native 실행기의 package·window·대상·resource·class·bounds 검사, 단계별 승인은 그대로 유지한다. 독립 관찰 poll이나 타이머를 실제 AX 이벤트처럼 B에 전달하지 않는다.

이 대기는 자동 요청에 약 250ms를 추가할 수 있다. 일찍 보낸 요청이 폐기돼 다시 수초를 쓰는 일을 줄이려는 절충이다. 실제 절감 여부와 대기 비용은 새 실험에서 함께 측정해야 한다.

## 4. B2: 안정된 전환과 단계 성공을 분리

A는 `CURRENT`를 유지한다. B2는 `META / mc_v1`이며, [native 전환 검출기](../../../Frontend/app/src/main/java/com/click/service/overlay/AppTaskTransitionDetector.java)와 [MetaController](../../../Frontend/app/src/main/java/com/click/service/overlay/AppTaskMetaController.java)를 사용한다.

전환 검출은 후보에 따라 추가된 텍스트나 OCR JSON이 아니라 **실제 전체 native snapshot의 기본 공개 투영**에서 조작 대상·상태의 의미 경로를 비교한다. 다음 조건이 필요하다.

- 관찰 가능한 공개 상태이고 privacy masking이 준비돼 있어야 한다. 입력기·System·overlay 창은 전환 근거로 쓰지 않는다.
- 조작 전후 package가 같아야 한다. 전환 전후 window가 달라지는 정상적인 탐색은 허용하지만, 이후 두 관찰은 같은 native window여야 한다.
- 이후 두 관찰 ID가 다르고, 캡처 시각과 단조 시계가 각각 350ms 이상 진행해야 한다.
- ID·좌표·수동 텍스트만 바뀐 것은 의미 경로 전환으로 인정하지 않는다. 현재 native 프레임의 신선도도 확인한다.

기존 단계 verifier가 여전히 `WAITING`이더라도 위 조건으로 안정된 새 경로를 확인한 허용 탐색은 `REOBSERVE_PROGRESS`가 될 수 있다. 이는 **화면이 달라졌다는 관찰**이며 단계나 최종 목표가 검증됐다는 뜻이 아니다. Controller는 해당 시도를 `waiting`으로 기록하고 subgoal을 pending으로 유지한다. 로컬 목표 검증을 확인한 뒤 필요하면 최신 화면으로 새 계획을 요청한다.

이때 `mc_v1 / observed_transition_unconfirmed`가 실제 요청에 전달된다. 이전 액션 참조와 기존 실패 차단 이력을 제공하지만, 전환 관찰만으로 이전 액션을 새 실패 차단 목록에 넣거나 도구 권한을 넓히지 않는다. 서버도 전환은 검증된 단계·목표가 아니며 현재 허용 조작 안에서만 판단해야 한다고 명시한다.

복구 결정이 이전 TAP을 직접 반복하는 국소 수리는 추가하지 않았다. 새 모델 제안이 나오더라도 새 승인과 현재 전체 지문·native 대상 검사를 거쳐야 한다. 입력·토글·뒤로가기 등을 복구 정책이 임의로 자동 실행하지 않는다.

## 5. B2의 대기와 요청 예산

| 항목 | 동결된 동작 | 해석 |
| --- | --- | --- |
| 안정 전환 재관찰 | 미검증 subgoal별 최대 2회, 의미 경로 순환 제한 | 단계 진행 비트를 올리지 않는 별도 제한이다. |
| 효과가 불확실한 수락 조작 | 로컬 읽기만 절대 8초 상한까지 유지 | 이벤트가 계속 와도 이 상한을 연장하지 않는다. |
| 진전 없는 같은 의미 경로·미검증 subgoal | 실패 복구용 유료 재계획 예약 최대 1회 | 실제 전송 직전 예약하여 이벤트·응답 폐기가 추가 호출을 만들지 못하게 한다. |
| 작업 전체 | 실패 복구용 유료 재계획 예약 최대 3회 | 앱 선택이나 국소 상태 초기화가 작업 전체 상한을 새로 주지 않는다. |
| 읽기 전용 최종 증거 발견 | 조작 실패 복구 예산과 분리 | 이미 관측 가능한 안전한 완료 증거를 찾는 요청을 조작 재시도 한도 때문에 차단하지 않는다. |

`progress_rescue_count`, `recovery_count`, `failure_replan_reservations`는 각각 전환 재관찰, 복구 판단, 전송 기회 예약의 진단 카운터다. 실제 API 시도 수나 복구 성공 수와 같지 않다. 실제 호출 비용은 요청 hash로 직접 연결한 공급자 기록으로 집계한다.

**진짜 무반응에서는 B2가 기존 5초보다 최대 8초까지 기다릴 수 있다.** 지연된 효과를 성급히 실패 처리하지 않으려는 변경이지만, 효과가 끝내 없으면 사용자의 기다림이 늘어나는 비용이 있다. 이 대기를 무조건 속도 개선이라고 부르지 않는다. 실제 단계 검증이나 안정된 전환이 먼저 성립하면 그 전에 다음 처리로 이어갈 수 있다. 실험의 공통 30초 관찰 예산은 별도이며 이 8초 상한 때문에 늘어나지 않는다.

## 6. 범용성·증거·비용의 경계

이번 공통 변경과 B2 전환·예산 판단에는 특정 앱 package, 메뉴 이름, 실험 목표의 정답 selector로 분기하는 생산 규칙을 넣지 않았다. 회귀 검사는 등록되지 않은 여러 가상 package와 다른 전환·지연 조건도 사용한다. 이는 코드가 일반적인 공개 관찰·역할·native 상태 계약을 사용한다는 근거이며, 미관측 앱 전체에서 잘 작동한다는 증명은 아니다.

실험 카탈로그의 앱별 탐색 허용 범위와 독립 정답은 준비·안전·평가용이다. 목표를 빨리 달성시키려고 정답 경로를 플래너 힌트로 주입하거나, `allStepsVerified`·조작 수락·화면 전환만으로 최종 완료를 선언하지 않는다. 최종 완료는 목표 계약과 현재 native 증거로 별도 검증한다.

API 시도는 공급자 경계에서 관찰한 요청 시도이며 timeout도 포함한다. 공급자가 보고한 입력·출력·추론·총 토큰은 유효한 값이 실제 응답에 있을 때만 별도 기록한다. timeout 등으로 빠진 토큰은 0으로 바꾸지 않고 미확인으로 남긴다. API 시도 수는 토큰 수·금액·공급자 내부 처리나 추론 완료를 보장하지 않는다. 단가·캐시 청구를 연동하지 않아 금액 절감으로 표현하지 않는다.

## 7. 남아 있는 제한

**목표 증거를 action verifier의 `WAIT`보다 먼저 검사하는 변경은 하지 않았다.** 현재 `verifyNow`는 단계의 verifier와 MetaController 판단이 `WAIT`이면 먼저 읽기 대기를 이어가고, 그 뒤에 `observeResult`로 목표 증거를 확인한다. 따라서 단계가 계속 불확실한 일부 경우에는 올바른 목표 계약이 현재 화면에서 참이더라도 lease 처리까지 기다릴 수 있다.

관찰·재계획 경로에서는 기존 완료 증거가 유료 모델 요청보다 먼저 검증된다. 다만 이것을 “수락된 조작을 검증하는 모든 시점에서도 목표 증거가 먼저 처리된다”로 확대해서 설명하지 않는다. 대기 도중 목표를 먼저 검증하려면, 미검증 액션을 성공으로 올리지 않는 기록·종료 처리와 전용 회귀 검사가 추가로 필요하다.

이전 목적지 도달 후 공급자 timeout 사례처럼 사용할 후보 자체가 없는 경우도 이번 읽기 전용 후보 재검증만으로 해결되지 않는다. 이번 구현이 모든 공급자 실패를 복구하거나 B의 실제 성공을 이미 늘렸다고 주장하지 않는다.

## 8. 실행 전 검증과 계측 수정

동결된 Android 코드의 관련 **28개 클래스·204개 테스트가 실패·오류 0개로 통과**했다. debug/계측 APK 빌드와 lint도 통과했다. Backend 관련 **344개 테스트가 통과**했다. 마지막 분석 gate 수정은 이 전체 실행 뒤에 이뤄졌고, 아래 별도 14개 검사로 검증했다. 344개 전체가 그 마지막 수정 뒤 다시 실행됐다고 표현하지 않는다. 이 숫자는 구현의 회귀 검사이며 실제 사용자·앱 성공률이 아니다.

일부 기존 단위 테스트의 가상 대기는 새 lease·계획 병합 시각에 맞췄다. 자동 요청 대기를 300→550ms, 복구 요청 확인을 8,350→8,800ms로 조정했고, META의 과거 6초 검사는 9초로 옮겨 8초 상한 뒤를 검사했다. 조작 횟수·반복 금지·subgoal pending·복구 횟수·안전 assertion은 유지했다. 기존 UI 요청 context 변경도 보존했다.

계측·판정 검사 수정은 생산 정책 변경과 구분한다.

- [클라이언트 진단](../../../Frontend/app/src/main/java/com/click/data/remote/AppTaskDiagnostics.java)은 원래 요청에 연결된 응답에서만 닫힌 정책·이유·횟수 조합과 유효한 토큰을 복사한다. 임의의 앱 이름·목표 본문·선택자 내용을 추가 기록하지 않는다. 메타데이터 전달 여부는 실제 시도와 연결해 확인하며 모델이 이를 이해·활용했다는 의미로 확대하지 않는다.
- 동결 commit `63ecb80`은 분석 gate가 실제 양팔 장애 노출 후 B만 공동 성공한 쌍을 세면서, 예전 `recovery_count > 0`까지 불필요하게 요구하던 조건을 수정했다. B2는 `progress_rescue_count > 0`이면서 `recovery_count == 0`일 수 있기 때문이다. 필드는 `b_only_exposed_success_pairs`로 명확히 했다. 이는 runtime에 성공을 주입하는 변경이 아니며, 실제 장애 노출과 공동 성공 조건은 그대로 필요하다.
- 해당 경계는 [progress-only 반례 회귀](../../../Backend/tests/test_meta_controller_public_apps_analysis.py)로 검사했다. [별도 gate 검증 로그](gate-verification.log)는 **14개 검사 통과**를 기록한다. 이 검사 수를 위 Backend 344개에 추가 합산하거나 실제 성능 시행 수로 세지 않는다.

전체 목표는 안전한 로컬 증거 재사용으로 불필요한 클라우드 요청을 줄이고, 실제 전환을 관찰한 경우에만 제한된 복구 판단을 이어가는 것이다. 효과와 상충은 동결된 새 코호트의 앱별·전체 성공, 실패 포함 시간, 실제 API 시도와 확인 가능한 토큰 결과로 평가한다. 그 결과는 이 구현 설명과 분리해 보고한다.
