# 완료 판정 비교 프로토콜 — 내 결속 규칙 vs develop 완료 판정 (본 실행 전 고정)

## 질문

기억 재사용과 맞닿는 지점은 **완료 판정**이다. 성공 경로는 완료로 인정된 작업에서만 저장되고, 기억은 완료 조건이 결속된 뒤에만 쓰인다. 두 완료 판정 중 어느 쪽이 (1) 더 정확하게 완료를 인정하고 (2) 기억 저장·재사용으로 더 잘 이어지는지 비교한다.

## 비교군

| 비교군 | 기억 | 완료 판정 |
|---|---|---|
| B | 정확 일치 기억 | develop 그대로: `_unsafe_goal_check`(메뉴·버튼·탭 라벨을 완료 근거로 쓰지 않음)와 `_observed_goal_check`(결과만 확인 단계는 지금 관측된 유일한 대상만) |
| C | 정확 일치 기억 | 312ff36의 결속 규칙: 새로 결속하는 완료 조건 **전체가** 결속 화면에서 이미 성립하면 거절(`satisfied_at_binding`). develop의 두 검사는 끈다. 결과만 확인 단계에는 이 규칙을 적용하지 않는다 |

프롬프트, 모델, 기억 구현, 기기 코드, 경로 키는 두 비교군이 같다. 실험 서버 `--completion-comparison`이 비교군별로 완료 판정만 바꾼다(`serve_memory_experiment.py`의 `completion_policy`, `apply_binding_rule`).

## 실행

- 기기·하네스: 기존 `MemoryDeviceExperimentTest#runMemoryExperiment`, 25초 예산, 모의 사용자는 독립 정답(UiAutomation, 700ms 유지) 확인 뒤에만 결과를 확인한다.
- 과제: 정답 양성 대조가 확인된 7과제 — settings_display, settings_notifications, clock_timer, chrome_menu, chrome_new_tab, youtube_subscriptions, youtube_search.
- 회기: learn1, learn2, learn3, retain (4회기). 과제·회기마다 B/C 순서를 결정적으로 회전·반전한다.
- 총 7 × 4 × 2 = 56회. 비교군별 기기 저장소와 서버 저장소는 분리한다.

## 주 지표 (비교군별)

1. **거짓 완료**: 독립 정답이 없는데 기기가 VERIFIED 결과 확인을 제시한 회차 수. 적을수록 좋다.
2. **놓친 완료**: 독립 정답이 성립했는데 VERIFIED를 제시하지 못한 회차 수. 적을수록 좋다.
3. **기억 저장**: 확인된 작업 중 AI2 경로 조건을 통과한 수.
4. **기억 재사용**: 기억 출처 제안 수와 그 회차의 독립 성공.
5. 독립 성공률, 플래너 호출 수.

보조: 완료 조건 결속 비율, 거절 사유(`completion_rejected`, `completion_grounding`) 분포.

## 판정

- 거짓 완료가 적은 쪽을 우선한다. 거짓 완료가 같으면 놓친 완료가 적은 쪽, 그다음 기억 저장·재사용이 많은 쪽.
- 56회는 작은 표본이다. 과제별 대응 차이로 보고, 차이가 과제 1~2개에서만 나면 "우열 판단 불가"로 기록한다.
- 순차·결정적 순서이며 무작위 배정이 아니다. 시간대·제공자 지연 변동이 섞일 수 있다.

## 변경 기록 (재실행 전에 기록)

1. **1회차 결과(raw-completion):** 양쪽 모두 자동 완료 인정 0회. 원인은 두 비교군이 공유하는 기기 규칙이었다. 목적지 안의 메뉴 항목은 도착 증거로 받지 않는데, 페이지 제목은 화면 정보에 없었다. 비교군 차이와 무관하므로 판정 불가로 기록한다.
2. **기기 수정(두 비교군 공통):** 앱바/툴바 안의 누를 수 없는 페이지 제목을 제목 노드로 내보낸다. 읽을 수 있는 화면에서 판단 불가로 나온 예측 완료 조건은 버리고, 도착 화면에서 다시 정하게 한다.
3. **2회차(raw-completion-v2):** 자동 인정 B 4 / C 3. 모두 유튜브 구독 과제였다. 설정 과제는 서버가 도착 후 제목("디스플레이", "알림")을 묶었지만, 하네스가 목표 유지 0.7초 직후 사용자 확인을 눌러 기기 인정보다 먼저 끝났다(raw-completion-probe2로 확인).
4. **하네스 수정(3회차):** `verifyWaitMs=8000`. 독립 정답 성립 뒤 최대 8초 동안 기기 자체 인정을 기다린 다음 사용자 확인을 누른다. 인정까지 걸린 시간(`runtime_verified_after_goal_ms`)을 기록한다. 거짓 완료 판정 기준과 비교군 정의는 바꾸지 않는다.
