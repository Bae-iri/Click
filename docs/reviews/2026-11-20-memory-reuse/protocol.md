# 기억 재사용 실기기 실험 프로토콜 — 2026-11-20

이 문서는 본 실행 전에 고정했다. 결과를 본 뒤 과제, 정답, 비교군, 지표를 바꾸지 않는다.

## 질문

1. 현재 운영 기억(기기 검증 경로 캐시와 AI2 회수)은 같은 예산에서 성공률, 모델 호출, 소요 시간을 개선하는가? (MemGUI-Bench의 장기 기억, AutoDroid-V2의 경로 재사용)
2. 표현만 다른 요청(미러 요청)에서도 기억이 전이되는가? 목표 정규화를 더하면 달라지는가?
3. 실패 기억(거절·미확인 이후 성공만 인정)과 지지 2회 조건은 기억 제안을 얼마나 막는가?

## 환경

- 기기: Galaxy Note20 SM-N981N, Android 13. 실제 Gemini 설정 모델(gemini-3.8-flash).
- 앱 ID `com.click.memoryexperiment.uitestdriver` debug 빌드, loopback facade `Backend/scripts/serve_memory_experiment.py`.
- 실행 경로: 실제 `AppTaskController`·`AppTaskExecutor`·`AppTaskService.step`·`analyze_app_task`·`AppTaskExperienceService._ground`. DB 저장만 비교군별 메모리 저장소로 대체했다.
- 시작 상태·독립 정답·탐색 허용 목록은 MetaController v4 파일럿과 같다. 시계 앱은 회기 종료 후 알람 탭으로 되돌리는 하네스 정리만 추가했다.

## 비교군

- **A 기억 없음:** 학습 끔, 기기 저장소 없음, 서버 회수 없음.
- **B 현재 운영 기억:** 학습 켬. 기기 경로 캐시(같은 요청 문장·앱 버전, 확인 2회)와 AI2 회수(같은 목표 해시·화면·하위 목표, 확인된 작업 2개 이상, 실패 이후 성공만 인정).
- **C B + 목표 정규화:** 서버 회수와 AI2 분석에서 미러 요청을 원래 과제의 목표 키로 매핑한다. 고정 카탈로그 매핑이므로 정규화 성능의 상한이다. 기기 경로 캐시는 B와 같이 정확한 문장 키를 쓴다.
- 비교군마다 기억 저장소(기기·서버)를 분리했다.

## 회기

과제마다 6회기다. learn1~learn3과 retain은 원래 요청, mirror1~mirror2는 미러 요청이다. 비교군 순서는 과제·회기마다 결정론적으로 회전·역순 배치한다. 12과제 × 6회기 × 3비교군 = 216회를 예약한다. 회기 예산은 25초다.

모의 사용자는 독립 UiAutomation 정답이 700ms 유지된 경우에만 결과를 확인한다. runtime의 VERIFIED 제시는 정답으로 쓰지 않는다. 확인하지 않은 회기는 기억의 확인된 경로가 되지 않는다.

## 지표

- 독립 정답 성공률(회기별·단계별), 학습 단계 pass@3, 실패 회복률(learn1 실패 후 learn2~3 성공)
- 실패 포함 시간(실패는 25초), 회기당 모델 호출 수와 대기 시간
- 기억 출처 제안 수(서버 AI2, 기기 AI2 회수, 기기 경로 캐시)와 그 회기의 성공
- 그림자 평가: 매 회수 시점에 exact, normalized, 실패 기억 제거, 지지 1회 변형이 각각 무엇을 제안했을지 기록한다. 실제 응답에는 영향을 주지 않는다.
- 잘못된 VERIFIED 제시

## 판정 기준

- **기억 기본 적용 GO:** B가 A 대비 retain 회기 성공률을 떨어뜨리지 않고, 모델 호출 또는 실패 포함 시간을 줄이며, 기억 출처 제안이 실제로 발생하고, 기억 출처 제안 뒤 잘못된 결과 확인 제시가 없을 때.
- **정규화 GO(개발 착수):** C의 미러 회기에서 기억 출처 제안이 B보다 늘고 성공률이 떨어지지 않을 때.
- 단일 기기·작업군 12개의 탐색적 실험이다. 효과가 작거나 기억 제안이 거의 발생하지 않으면 NEEDS_DATA로 판단한다.
