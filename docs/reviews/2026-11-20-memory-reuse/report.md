# 기억 재사용(MemGUI-Bench·AutoDroid-V2 적용) 실기기 실험 결과 — 2026-11-20

**결론: 완료 판정과 경로 증거 규칙을 고친 뒤 독립 성공이 36/216에서 72/216으로 두 배가 됐고, 재사용 경로가 실제로 쌓이기 시작했다. 그러나 기억이 동작을 직접 제안한 회기는 두 실행 모두 0회다. 오히려 오염된 실패 기억이 플래너 프롬프트를 통해 성공을 막는 사례가 재현됐다. 두 수정은 GO, 기억의 기본 적용은 계속 NO-GO다.**

Galaxy Note20(SM-N981N, Android 13)과 실제 Gemini 3.8 Flash로 같은 프로토콜을 두 번 실행했다. 실행마다 12개 공개 탐색 과제 × 6회기 × 3비교군 = 216회다. 운영 코드(`AppTaskController`, `AppTaskService.step`, AI2 `analyze_app_task`, 회수 `_ground`)를 그대로 호출했고 DB 저장만 비교군별 메모리 저장소로 대체했다. 범위는 [protocol.md](protocol.md)와 [protocol-v2.md](protocol-v2.md)에 실행 전에 고정했다.

## 비교군과 실행

| 비교군 | 구성 |
|---|---|
| A | 기억 없음 |
| B | 현재 운영 기억: 기기 경로 캐시 + AI2 회수(정확한 목표 키, 확인된 작업 2개, 실패 이후 성공만 인정) |
| C | B + 목표 정규화(미러 요청을 원래 과제 키로 매핑하는 상한 조건) |

- **1차:** 수정 전 코드.
- **2차:** 같은 하네스·과제·정답에 아래 세 가지 제품 수정만 반영.
  1. **완료 조건 결속 규칙.** 결속하는 화면에서 이미 성립하는 완료 조건은 거절하고, 프롬프트에 지금 보이는 라벨을 완료 조건으로 쓰지 말라는 지시를 추가했다.
  2. **경로 키 v2.** 상호작용 컨트롤과 그 상태만으로 화면 키를 만든다. 증거용 정적 텍스트와 스크롤 viewport는 제외한다.
  3. **사용자 확인에 의한 마지막 동작 인정.** 사용자가 마지막 동작이 만든 화면에서 결과를 확인하면, 그 동작의 검증이 미확인이어도 경로 단계로 인정한다.

과제마다 원래 요청으로 학습 3회와 유지 1회, 바꿔 말한 미러 요청으로 2회를 실행했다. 독립 UiAutomation 정답이 700ms 유지될 때만 모의 사용자가 결과를 확인했다. 1차와 2차는 같은 날 순차 실행이므로 시간대·제공자 지연 차이가 섞일 수 있다.

|---|---:|---:|---:|
| A | 15/72 | 27/72 | 7 |
| B | 12/72 | 20/72 | 7 |

- **완료 판정 수정의 효과가 가장 크다.** 설정 앱 성공은 비교군별 1~3/18에서 11~12/18로 올랐다. 서버의 결속 거절 규칙은 2회만 작동했고, 개선 대부분은 프롬프트 지시로 모델이 처음부터 도착 화면 라벨을 고른 결과다. 거절 규칙은 모델이 지시를 어길 때의 안전장치다.
- **남은 잘못된 VERIFIED 23회는 모두 소리 설정 11회와 Chrome 설정 12회다.** MetaController 사후 양성 대조에서 이 두 과제의 정답 조건은 확인되지 않았다. 실제 오판인지 정답 조건 문제인지 먼저 가려야 한다.
- **경로 형성이 살아났다.** 2차에서 형성된 경로 32개 중 15개가 사용자 확인으로 마지막 동작을 인정한 경우였다. 나머지는 경로 키 v2가 결과 화면의 미세한 차이를 흡수한 경우다.

## 기억 비교 (2차)

| 단계 | A | B | C |
|---|---:|---:|---:|
| 학습(learn1~3) | 11/36 | 11/36 | 12/36 |
| 유지(retain) | 4/12 | 3/12 | 4/12 |
| 미러(mirror1~2) | 12/24 | 6/24 | 9/24 |

**기억 출처 제안은 두 실행 모두 0회다.** 경로가 쌓였는데도 쓰이지 않은 이유는 구조적이다. 기기와 서버 모두 첫 플래너 응답으로 완료 조건이 정해진 뒤에만 기억을 쓴다. 이번 432회 중 두 번째 동작을 실행한 회기가 하나도 없었으므로, 기억이 개입할 차례가 오지 않았다. 모델 호출도 비교군 모두 회기당 약 1.0회로 같았다.

B는 유지+미러 단계에서 A보다 21%p 낮았다(작업군 bootstrap 95% 구간 [−39, −6]%p). 1차에서는 C가 가장 낮았다. 기억이 동작을 제안하지 않았는데도 차이가 난 경로는 아래와 같다.

### 오염된 실패 기억의 역효과

학습 비교군은 기억을 동작으로 쓰지 못해도, 같은 화면의 과거 증거와 전술을 플래너 프롬프트의 `prior_experience`로 넣는다. 프롬프트는 거절·미확인 대상을 반복하지 말라고 지시한다.

| 시계 미러 회기 (2개 과제 × 2회 × 2실행) | A | B | C |
|---|---:|---:|---:|
| 독립 성공 | 7/8 | 1/8 | 0/8 |

- 원래 요청의 시계 회기에서는 세 비교군 모두 거의 실패했다. 실행기가 탭을 `observation_or_policy_changed`로 거절했다. MetaController 감사가 지적한 관찰·실행 투영 불일치 결함과 같은 증상이다.
- 이 거절이 기억에 "탭 대상 거절"로 저장됐다. C의 미러 회기 플래너 호출 12회 모두 같은 목표의 탭 거절 증거 2~5건을 받았다. B는 일부 회기에서 증거를, 나머지에서는 목표와 무관한 전술 신호를 받는다.
- 기억이 없는 A는 미러 회기에서 같은 탭을 눌러 성공했다.

시스템 결함 때문에 생긴 거절이 대상 자체의 실패로 기억되고, 다음 회기에서 올바른 대상을 피하게 만든 것으로 해석한다. 프롬프트 원문과 전술 목록은 개인정보 보호 정책상 기록하지 않았으므로, 개별 회기의 모델 판단까지 직접 확인한 것은 아니다.

## 논문 아이디어별 판단

| 항목 | 판단 | 근거와 다음 조건 |
|---|---|---|
| 완료 판정 수정(GoalContract) | **GO** | 잘못된 VERIFIED 63 → 23, 검증 7과제에서 30 → 0 |
| 경로 증거 규칙 수정(경로 키 v2, 사용자 확인 인정) | **GO** | 경로 형성 2/21 → 32/45 |
| 현재 기억의 기본 적용 | **NO-GO** | 동작 제안 0회. 프롬프트 경로로는 역효과 사례 재현 |
| 실패 기억을 지금 형태로 프롬프트에 노출 | **NO-GO, 수정 필요** | 실행기·정책 거절을 대상 실패와 구분하지 않아 올바른 대상을 회피 |
| 첫 단계 기억 사용(완료 조건을 경로와 함께 저장) | **GO(설계)** | 한 동작 과제에서 호출을 줄일 수 있는 유일한 지점. 쌓인 경로 11개 목표가 대상 |
| 목표 정규화 | **보류** | 2차 미러에서 C가 B보다 높았지만(9 vs 6/24), 정규화된 실패 증거가 시계 회기를 막기도 함 |
| AutoDroid식 다단계 경로·앱 문서 재사용 | **NEEDS_DATA** | 모든 회기가 한 동작이라 측정 불가 |
| 소형 온디바이스 모델 학습 | **NO-GO** | 검증된 학습 데이터가 아직 적음 |

## 추가로 해야 할 일

1. **실행기 투영 불일치 수정(P0).** 컨트롤러가 완료·기대 라벨로 재정렬·추가한 관찰을 실행기가 기본 관찰과 비교해 같은 화면을 거절한다. 같은 ProjectionSpec을 양쪽에 쓰게 한다. 시계·YouTube 탭 실패의 공통 원인으로 보인다.
2. **실패 증거 출처 분리.** 실행기·정책·실험 허용 목록의 거절은 대상 실패가 아니라 시스템 거절로 기록하고, 회수 증거와 프롬프트 전술에서 제외한다.
3. **첫 단계 기억 사용.** 확인된 경로에 완료 조건을 함께 저장해, 같은 목표·화면이면 첫 플래너 호출 없이 제안한다. 현재 화면 검증은 유지한다.
4. **정답 조건 재검증.** 소리 설정·Chrome 설정·세계시각·Shorts는 모델 없는 양성 대조로 정답을 다시 확인한 뒤 성능 집계에 쓴다.
5. **다단계 과제 카탈로그.** 2~4단계 과제와 미러 쌍을 만들어 MemGUI식 정보 보존과 AutoDroid식 경로 재사용을 측정한다.
6. **재실험.** 1~3을 고친 뒤 같은 프로토콜로 반복한다. 유지 회기의 모델 호출과 시간이 줄고 성공률이 떨어지지 않으면 기억 기본 적용 GO다.

## 한계

- 기기 1대, 과제 12개, 비교군당 실행별 72회의 탐색적 실험이다. 성공 사례가 적어 비교군 간 구간이 넓다.
- 1차와 2차는 무작위 배정이 아닌 순차 실행이다.
- 모의 사용자는 독립 정답을 본 뒤에만 확인한다. 실제 사용자의 확인 행동이나 시간은 측정하지 않았다.
- C의 정규화는 고정 매핑이라 실제 정규화기의 오류를 포함하지 않는 상한이다.
- 실험 서버는 DB 대신 메모리 저장소를 썼다. 동의·만료·삭제 경로는 검증 범위 밖이다.
- 1차 직후 YouTube가 검색 화면에 남아 있어, 2차 시작 전 뒤로 가기로 홈에 복원했다. 시계 앱은 1차 전 알람 탭으로 복원했고 하네스가 회기마다 같은 복원을 수행했다. 준비 실패는 모든 집계에 실패로 남겼다.

## develop 반영 시 통합

2차 실행 중 같은 영역의 팀 수정(`a19bd5a`, `95c757d`)이 develop에 먼저 반영됐다. 실행기 투영 불일치(`recaptureLike`)와 목표별 완료 조건 안전성 검사, 완료 증거 버전 관리가 들어 있다. 통합하면서 아래와 같이 정리했다.

- **완료 조건:** 이번 실험의 "결속 화면에서 이미 성립하면 거절" 규칙은 제거하고 팀의 역할 기반 안전성 검사를 따른다. 팀 설계는 이미 도착한 화면의 제목이나 검색 열기 요청의 검색창처럼, 지금 성립하는 증거를 의도적으로 허용한다. 프롬프트 문장은 "누를 대상이나 결과로 가는 메뉴 항목을 완료 조건으로 쓰지 말라"로 바꿔 팀 설계와 맞췄다.
- **경로 키 v2와 마지막 동작 인정:** 그대로 반영했다.
- 따라서 develop의 현재 코드는 2차 실행에서 측정한 코드와 완료 조건 부분이 다르다. 실행기 투영 수정이 들어갔으므로 위 "추가로 해야 할 일" 1번은 팀 수정으로 일부 해소됐을 수 있고, 재실험으로 확인해야 한다.

## 검증
