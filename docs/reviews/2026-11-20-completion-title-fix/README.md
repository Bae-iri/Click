# 완료 제목 누락 수정과 집중 검증

**완료 검증용 관찰을 만들 때 실제 화면 제목이 사라지는 결함을 재현하고 수정했다.** 수정 전 회귀 테스트는 제목 보존과 A/B 완료 연결의 세 항목에서 실패했다. 수정 후 실제 Settings 화면에서 A/B 모두 두 번의 새 관찰 뒤 자동 완료 검증을 제시했다.

이것은 공통 완료 연결의 복구 확인이다. B의 성능 우위나 이전 36회 전체 실패 원인을 입증한 결과는 아니다. [이전 36회 원자료](../2026-11-20-native-settings/README.md)는 수정하지 않았다.

## 확인한 원인

실제 Display 화면에는 같은 이름을 가진 두 native 요소가 있다.

- 스크롤 영역: `Display & touch`, role=`list`
- 그 안의 실제 화면 제목: `Display & touch`, role=`text`

기본 관찰에는 둘 다 남아 서버가 실제 제목을 완료 후보로 고를 수 있었다. 그러나 후보의 label을 포함해 결과 검증 관찰을 다시 만들면, 기존 중복 제거 코드가 같은 이름의 **모든 조상**을 소유자로 간주했다. 그 결과 스크롤 영역이 제목을 대신한다고 판단해 진짜 제목을 삭제했다.

따라서 서버가 정확한 `role=text`·제목 resource 조건을 반환해도, 앱의 재관찰에는 그 요소가 없어 조건이 맞지 않았다. 최초 후보는 provisional 상태로 수락될 수 있으므로, 후보 수락만 확인해서도 이 결함을 발견할 수 없다. 이후 화면 일치와 두 번째 관찰까지 확인해야 한다.

수정은 [AppTaskObservation](../../../Frontend/app/src/main/java/com/click/data/snapshot/AppTaskObservation.java)의 중복 제거 소유자 판단에 한정했다. **클릭·입력이 불가능한 수동 스크롤 컨테이너는 내부 제목을 대체하지 않는다.** 앱 이름·화면 제목·Settings resource를 생산 코드에 하드코딩하지 않았다. 버튼·탭·토글·입력 요소 내부의 중복 문구, 별도 행의 모호한 제목, 보호 화면과 기존 지문 검사는 유지했다.

이 결함은 실제 관찰 구조를 사용한 테스트로 확정했다. 이전 실험은 후보 selector 전체를 남기지 않았으므로, 과거 7개 후보 응답 각각의 원인이 이 결함이었다고 단정하지 않는다.

## 수정 전후와 실제 화면 결과

| 검사 | 결과 |
|---|---|
| 수정 전 회귀 검사 | 13개 중 3개 실패: 제목 누락, A/B 후보 수신 뒤 검증 실패 |
| 최소 수정 후 제목·목표·근거 교체·지문 보호 | 34개 통과 |
| 최종 관련 단위 테스트 | 22개 클래스 146개 통과 |
| debug/계측 APK 빌드 및 lint | 통과 |
| 실제 Settings 관찰·controller 양성 대조 | A/B 모두 검증 |
| 실제 홈 메뉴·빈 보호 입력 화면 음성 대조 | 네 경우 모두 자동 검증 없음 |

모델 없는 실제 화면 검사에서는 native 제목 selector를 현재 공개 접근성 관찰에서 만들고, 실제 `AppTaskMemory`와 `AppTaskController(remote=false)`에 전달했다. 합성 snapshot이나 합성 화면 이벤트는 사용하지 않았다. 독립 UiAutomation 제목 확인과 실제 기본/결과 관찰을 함께 검사했다.

| 실제 Display 집중 검사 | A | B |
|---|---:|---:|
| 모델 없이 관찰한 후보의 두 새 프레임 간격 | 448ms | 449ms |
| 자동 검증 제시 | 확인 | 확인 |
| 조작 실행 / 모델 호출 | 0 / 0 | 0 / 0 |

사용자의 마지막 확인/DONE는 누르지 않았다. 자동 검증 제시와 사용자 최종 확인은 계속 구분한다.

## 실제 모델 후보 연결 검사

Gemini `gemini-3.8-flash`를 팔당 한 번, 총 두 번만 호출했다. Settings Display에 이미 도착한 상태를 만들고, 검증된 하위 목표 하나를 가진 **명시적인 controlled result_only 상태**를 사용했다. 가짜 조작 이력은 만들지 않았다.

검사 경로는 **실제 Gateway 응답 → 같은 메모리에 테스트가 직접 `offerCompletion` 호출 → 실제 로컬 controller의 새 프레임 두 번 확인**이다. 자동 탐색 전체나 실제 remote controller callback 전체를 실행한 시험은 아니다. 자동 callback 경로는 별도 회귀·진단 단위 테스트로 확인했다.

| 모델 연결 검사 | A | B |
|---|---:|---:|
| 실제 공급자 시도 | 1 | 1 |
| 완료 후보 수신·메모리 채택 | 확인 | 확인 |
| 두 새 프레임 간격 | 428ms | 435ms |
| 자동 검증 제시 | 확인 | 확인 |

클라이언트·서버의 요청/작업 hash 두 쌍, 모델 시도 수와 대기 값이 정확히 일치했다. 미확인 호출은 0건이며 재시도·추가 호출은 없다. 이 두 사례의 간격을 A/B 속도 우위로 해석하지 않는다.

## 이제 남기는 진단

완료 진단은 기존 요청 원장과 분리된 `no_backup/app-task-completion-diagnostics/{current,previous}.jsonl`에 기록한다. 각 파일은 256KiB로 회전하며 debug/명시적 후보 진단이 켜졌을 때만 저장한다.

- 응답 수신과 현재 화면 변경에 따른 폐기
- 후보 채택·거절 및 고정된 이유 코드
- 목표 조건 일치 여부와 관찰 신선도
- 첫 프레임·두 번째 프레임·검증 제시

작업·요청·후보·관찰·창의 hash, 근거 버전, 제한된 코드·개수·시간만 남긴다. 목표·selector·화면 내용·입력·토큰·예외 원문은 생산 진단에 저장하지 않는다. 진단 저장 실패는 작업 판정을 바꾸지 않는다. 메모리의 마지막 후보 판단 이유는 transient 값이며 wire schema나 저장된 작업 계약에 추가되지 않는다.

수정 전에는 후보가 수락돼도 매칭이 실패하는 경우가 숨을 수 있었다. 이제 `candidate_accepted` 다음 `goal_check=not_met`처럼 어디에서 끊겼는지를 구분할 수 있다. 실제 native 집중 검사의 로컬 controller 이벤트는 요청 ref가 null이며, 모델 연결은 같은 task/candidate hash 및 별도의 수동 전달 trace로 결합했다.

## B가 반드시 더 높아지는 것은 아닌 이유

A/B는 같은 완료 관찰·검증을 공유한다. 이 공통 연결이 깨지면 B가 재계획을 더 해도 검증 성공으로 이어지지 않을 수 있다. 추가 모델 판단은 시간 초과나 잘못된 제안도 늘릴 수 있어, MetaController를 붙였다는 이유만으로 성능이 오르지는 않는다.

이번에는 공통 결함 하나를 제거하고 해당 연결의 작동을 확인했다. B의 우위는 수정된 공통 기준으로 정상·무반응·지연을 다시 비교해야 판단할 수 있다. 기존 36회의 GO/NO-GO나 수치를 소급 변경하지 않았다. 생산 FE나 기본 A 정책도 이번 수정에서 변경하지 않았다.
