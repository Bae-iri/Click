# A 정책 현재 병목 감사 (기존 실기기 자료 재분석)

새 실행이나 모델 호출은 없다. 동료가 남긴 두 실기기 코호트를 다시 집계했다.
- [goal-first 6회](../2026-11-21-goal-first-completion/README.md): 소스 `a89168d`
- [통합 시간 비교 24회](../2026-11-21-a-integrated-timing/README.md): 소스 `0ee53cf`

둘 다 Android 17 에뮬레이터, Settings·Clock·Files 6개 목표, Gemini 3.8 Flash로 실행됐다. 운영 기본값과 같은
**Gemini 완료 정책 18회(요청 34건)**를 주 대상으로 하고, JeV 정책 12회(요청 22건)는 참고로만 쓴다. 기억은 두 코호트
모두 꺼져 있었으므로 이 자료로 기억 효과는 말할 수 없다.

## 결과 (Gemini 완료 정책 18회)

| 항목 | 값 |
|---|---|
| 공동 성공 | 14/18 |
| 계획기 요청 | 34건, 정상 응답 대기 중앙값 3,562ms (3,103~8,157) |
| **서버가 완료 예측을 버린 회기** (`deferred_actionable_proof`) | **8/18** (Display 3, Recent 3, Documents 1, Language 1) |
| 그 뒤 도착 확인 전용 호출 (`result_only`) | **7건, 대기 3,172~6,564ms (합계 32,888ms)**: 전체 요청의 21% |
| 목적 상태 도달 → 네이티브 검증 간격 | 예측을 버린 회기 중앙값 **4,289ms**, 나머지 회기 중앙값 **−133ms** |
| 공급자 시간 초과 (8,627~8,629ms) | 3/34건. **실패 4회 중 3회**의 직접 원인 |

JeV 정책에서도 같은 패턴이 보였다. 예측을 버린 회기 5/12, 시간 초과 3/22건이고, 시간 초과가 실패 7회 중 3회와 겹쳤다.

## 원인

1. **서버가 완료 예측을 버린다.** 도착 화면 제목이 지금 화면에 클릭 가능한 메뉴로 보이면(예: 메뉴 "디스플레이" →
   화면 제목 "디스플레이"), `_unsafe_goal_check`가 그 예측을 보내지 않는다. 메뉴를 증거로 오인하지 않으려는
   안전장치다. 하지만 결과적으로 도착 후 검증할 조건이 없어서, `result_only` 호출 한 번(약 3~7초)을 더 기다린다.
   - 기기에 넣은 예측 보관(`b569e68`의 `reofferPrediction`)은 서버가 예측을 보내지 않으므로 이 경우에 작동하지 않는다.
2. **공급자 시간 초과에 재시도가 없다.** 약 9초 예산에서 한 번 시간 초과가 나면 그 회기는 그대로 실패한다.
3. 기억은 이 자료에서 측정 불가다(꺼져 있음).

## 우선순위 제안

| 순위 | 변경 | 근거 | 예상 효과 (이 자료 기준) |
|---|---|---|---|
| 1 | 서버가 "지금은 메뉴라서 증거가 아님"인 예측을 버리지 않고 **미래 전용 후보**(`deferred_completion`)로 보낸다. 기기는 이를 보관했다가, 메뉴가 아닌 제목으로 네이티브 일치할 때만 쓴다. | 회기 8/18, 요청 7건 | 도착 확인 호출 7건 제거 가능, 해당 회기 약 4.3초 단축. 라벨이 실제 도착 제목과 맞는지는 실기기에서 확인 필요 |
| 2 | 공급자 시간 초과 시 남은 예산 안에서 1회 재시도 | 실패 4회 중 3회 | 성공 회기 최대 +3. 재시도 비용과 지연은 실측 필요 |
| 3 | 기억 우선·다단계 계획 실기기 A/B (현재 기본 끔) | 실기기 자료 없음 | 미정 |

1번의 안전 조건은 기존과 같다. 기기는 `checkForGoal`이 메뉴·클릭 가능 컨트롤을 증거로 인정하지 않을 때만, 두 프레임
네이티브 검증을 거쳐 쓴다. 역할 자체가 버튼·탭·토글이거나 선택 해제(`selected=false`) 규칙에 걸린 예측은 지금처럼 버린다.

## 한계

- 에뮬레이터 한 대, 목표 6개, 목표당 1~3회다. 통계적 효과가 아니라 병목의 위치를 보는 자료다.
- 예상 효과는 "도착 화면 제목이 예측 라벨과 네이티브로 일치한다"는 가정에 기댄다. 이번 자료로는 확인하지 못했다.

## 1·2순위 구현 (운영 기본값에 포함)

- **1. 미래 전용 후보.**
  - 서버: 지금 화면 때문에만 위험한 예측(메뉴로 보이는 도착 제목)을 `deferred_completion`으로 보낸다. 역할이
    버튼·탭·토글인 예측이나 선택 해제 규칙에 걸린 예측은 지금처럼 버린다. `result_only`, 실패 응답,
    이미 결과가 묶인 상태에서는 보내지 않는다.
  - 기기: 받은 후보는 보관만 한다. 메뉴가 아닌 제목으로 네이티브 일치하는 화면에서만 후보로 올리고,
    두 프레임 검증을 거친다.
- **2. 공급자 실패 1회 재시도.** 응답이 `unavailable`이면서 원인이 `provider_timeout`, `provider_deadline_exceeded`,
  `provider_transport_error`일 때만, 같은 화면에서 한 번 다시 묻는다.
- 스위치: `SpeedOptions.reofferPrediction`, `SpeedOptions.retryProviderFailure`.
- 수정 중 발견한 버그도 고쳤다. 기억한 결과와 모델 예측이 같아 보관값을 비울 때 "기억에서 온 값" 표시가 남아,
  그 뒤 버려진 예측을 보관하지 못했다.

### 기기 없는 폐루프 (315회, 모델 호출 0, [원자료](synthetic/episodes.jsonl))

통제 계획기 fixture는 위 서버 규칙을 그대로 따른다. 도착 제목이 현재 화면에 메뉴로 보이면 `deferred_completion`으로
보낸다. 표의 숫자는 1·2·3·4단계 과제의 계획기 요청 수다.

| 조건 | 기본(전부 끔) | 운영 기본값 |
|---|---|---|
| 처음, 정상 | 2·3·3·5 | **1·2·2·4** |
| 처음, 화면 흔들림 | 3·5·5·9 (4단계 실패) | **1·2·2·4** |
| 처음, 첫 요청 시간 초과 | 성공 0/4 | **성공 4/4** (요청 2·3·3·5) |
| 반복, 정상 | 2·3·3·3 | **1·2·2·2** |

315회 전체에서 거짓 도착 판정, 정책 거부, 엉뚱한 탭은 0이다.
- 목표 미도달 40회는 모두 재시도를 끈 군의 시간 초과 조건이다.
- 도달했지만 45초 안에 검증되지 못한 8회는 다음과 같다. 운영 기본값 군에는 없다.
  - 화면 흔들림 4단계 4회
  - 기억 우선 단독 군의 시간 초과 조건 4회

### 검증

- Backend: 계획기·goal-first·JeV·다단계 계획·미래 전용 후보 검사 201개 통과(새 4개). OpenAPI를 갱신했다.
- Android: 컨트롤러·완료·goal-first·통신 관련 검사 106개 통과. 합성 검사 9개 포함(행렬은 opt-in).
- 실기기에서는 아직 실행하지 않았다. 폰을 연결하면 도착 확인 호출 비율(현재 7/34)과 시간 초과 회복을 확인한다.
