# Qwen3.8-Flash 주 플래너 속도 실험

2026-11-21에 친구의 완료 검증 수정이 들어간 `ea80b1b`에서 시작해 앱 과제 경로의 모델을 OpenRouter `qwen/qwen3.8-flash`로 고정했다. Android의 승인·실행·완료 검증을 유지했다. 복구 요청과 복합 작업도 Qwen이 처리한다. 같은 모델을 사용하며 답변 형식을 줄였을 때 사용자 대기와 정확도가 함께 개선되는지를 확인했다.

## Android에서 여섯 과제를 직접 수행한 결과

Settings, Clock, DocumentsUI의 공개 화면을 사용하는 Android 에뮬레이터에서 A 정책으로 각 조건을 한 번씩 실행했다. 같은 기기, 같은 여섯 목표, 같은 순서와 30초 제한을 사용했다. 첫 조건도 버튼 메뉴와 완료 확인에는 이미 짧은 응답을 사용한다. 두 번째 조건에서는 하나의 목적 화면으로 이동할 때 탭과 파일 목록처럼 여러 종류의 요소가 섞인 화면에도 Qwen이 다음 동작이나 현재 도착 근거의 ID 한 개로 답할 수 있다. 순서는 고정됐고 실기기나 동시 접속 부하는 측정하지 않았다. [과제·호출별 결과](./qwen-primary-native.jsonl) · [공개 과제 목록](../../../experiments/metacontroller/native-public-apps-catalogue-v1.json)

HTTP 왕복은 요청 전송 직전부터 전체 응답을 읽을 때까지다. OpenRouter와 제공자의 대기·생성·네트워크 시간이 함께 들어간다. 최종 조건에서 호출 수가 증가한 데에는 파일 탐색이 첫 단계에서 멈추지 않고 다음 화면까지 진행된 영향도 있다. 두 조건의 호출 구성과 성공한 과제 구성이 다르므로 집계 중앙값을 모든 과제의 고정된 속도 차이로 해석할 수 없다.

|---|---:|---:|---:|

| 시계 · 스톱워치 | 3.99초 | 4.74초 | 2.99초 |

| 파일 · 문서 | 실패, 30.07초 종료 | 6.60초 | 5.16초 |

파일의 첫 실행에서는 최근 파일로 가는 탐색 메뉴만 열리고 후속 계획 요청이 이어지지 않았다. 문서 과제에서는 모델이 반환한 하위 계획이 검증에 실패했다. 최종 실행에서는 두 과제 모두 메뉴 열기, 대상 선택, 도착 근거 확인을 마쳤다. 시계의 두 탭은 더 일찍 열렸지만 최종 조건에서 각각 모델 호출이 한 번 추가되어 완료 안내가 늦어졌다. ‘언어 및 지역’은 최종 실행에서 영어 제목이 보였지만 Qwen이 제안한 완료 근거가 조작 가능한 요소로 판정돼 보류됐다. 다음 실험은 이처럼 목록과 제목이 함께 보이는 복합 이름 화면의 근거 선택, 탭의 선택 상태를 기기가 검증하기까지의 시간을 우선한다.

## 같은 화면에서 호출 자체를 비교한 결과

에뮬레이터에서 기록한 공개 화면과 한국어 알림 회귀 사례를 일반 앱 과제 API로 재생했다. 최초 14개 사례에서 화면마다 기존 형식과 단축 형식의 호출 순서를 번갈아 배치했다. 완료 근거를 보완한 뒤 도착·미도달 여덟 화면을 다시 실행했다. 표의 시간은 호출한 요청의 중앙값이며 정답 수에는 실패한 요청도 포함한다. 앱의 동일 입력 비교와 위 에뮬레이터의 실제 연속 조작은 별도 실험이다. [화면별 원자료](./qwen-primary-screen.jsonl)

| 화면 | 기존 형식의 HTTP / 앱 응답 | 단축 형식의 HTTP / 앱 응답 | 정답 수 |
|---|---:|---:|---:|
| 후속 메뉴 3개 | 2.96 / 3.08초 | 1.60 / 1.72초 | 2/3 → 3/3 |
| 도착 근거 3개 | 2.04 / 2.16초 | 1.24 / 1.39초 | 1/3 → 3/3 |
| 도착 전 화면 3개 | 0.85 / 0.97초 | 1.06 / 1.18초 | 3/3 → 3/3 |
| 스크롤·탭·탐색 메뉴 첫 동작 3개, 최초 단축 형식 | 2.92 / 3.04초 | 2.85 / 2.97초 | 3/3 → 3/3 |

후속 메뉴의 출력 중앙값은 146토큰에서 9토큰으로 줄었다. 도착 전후의 단축 형식 열은 같은 화면으로 보완 후 재검사한 값이다. 초기 단축 형식은 도착 근거 2/3을 맞혔고 ‘앱 알림’의 상위 화면을 한 번 잘못 인정했다. 수정 후 세 개의 도착 전 화면과 한국어 상위 화면을 모두 보류했다. 실제 한국어 목적 화면에서는 두 조건 모두 기존 서버 완료 검사가 먼저 성공해 모델을 호출하지 않았고, 해당 관측은 HTTP 중앙값에서 제외했다. 같은 입력으로 보완과 측정을 했으므로 새 앱에서의 정확도는 별도 평가가 필요하다.

후속 실험까지 포함해 이번 작업에서 실제 Qwen 호출 77회의 OpenRouter 보고 비용 합계는 $0.010063000였다. 앞서 측정한 GPT 일반 메뉴의 중앙값은 3.37초였다. 이번 에뮬레이터에서는 GPT를 같은 응답 형식으로 실행하지 않았으므로 이 수치는 현재 설정에서의 GPT 대 Qwen 속도 비교에 쓸 수 없다. [기존 GPT·Qwen 실험](./report.md)


## 최신 완료 검증을 합친 뒤의 일반 API 재검사

에뮬레이터 여섯 과제를 두 차례 실행한 다음 `50bebab`의 추가 완료 검증을 통합했다. 누를 수 있는 행 안에 들어 있는 텍스트도 Qwen의 현재 도착 근거에서 제외한다. 이 병합 뒤에는 공개 화면을 재생했다. 위의 두 에뮬레이터 수치는 병합 전 측정값이다.

도착한 네 화면에서 올바른 제목을 선택했고, 도착 전 세 화면과 한국어 ‘앱 알림’ 상위 화면에서는 근거를 보류했다. 한국어 목적 화면은 기존 로컬 검사가 확인했다. ‘언어 및 지역’은 독립적인 완료 전용 요청에서는 1.14초 만에 제목을 맞혔다. 기기 작업 중 동작과 완료를 함께 평가한 요청에서 나타난 실패는 여전히 별도 과제다.

에뮬레이터의 실험 서버는 앱별로 허용한 탐색 동작을 공급한다. 일반 앱 API에는 이 목록이 없다. 같은 파일 화면에 선택지를 더 많이 제공하자 단축형은 현재 앱을 다시 열거나, 현재 폴더의 필터를 누르거나, 현재 폴더 제목을 목적 위치로 오인했다. 재실행 후보 제외, 탐색 메뉴 지시문 추가, 짧은 구조화 계획을 각각 실험했지만 파일 두 목표의 첫 동작을 안정적으로 회복하지 못했다. 시도를 포함한 개별 결과를 원자료에 남겼다. [일반 API 재검사 기록](./qwen-primary-screen.jsonl)

최종 코드에서는 탐색 동작 제한이 없는 일반 API에서 목록과 토글 필터가 섞인 단일 목적지 화면에 기존 Qwen 전체 계획을 그대로 사용한다. 다른 모델을 재호출하는 비용은 없다. 이 형식은 최초 짝비교의 파일 탐색 메뉴를 3.12초에 올바르게 선택했다. 같은 화면에서 최종 분기가 기존 Qwen과 동일한 요청을 한 번 전송하는지 회귀 테스트로 확인했다. 일반 API의 파일 두 과제 전체와 새로운 앱에서의 성공률은 추가 측정이 필요하다.
