# Gemini 응답 시간과 앱 탐색 정확도

한국어 첫 메뉴 요청 6개에서 Gemini 3.8 Flash의 호출당 중앙값은 3.51초, Gemini 3.5 Flash-Lite는 1.64초였다. 각 모델이 같은 화면에서 한 번씩 응답했고 6개 모두 올바른 버튼을 제안했다. 여섯 쌍 모두 Flash-Lite가 빨랐다. 이 수치는 백엔드가 Gemini 호출을 준비한 시점부터 전체 응답의 파싱과 검증이 끝날 때까지의 시간이다. Google 내부 추론 시간은 별도로 관측할 수 없다.

## 같은 화면에서의 비교

| 검증 항목 | 기존 조건 | 후보 조건 |
|---|---|---|
| 같은 3.8 Flash의 요청·응답 형식 압축, 10쌍 | 3.98초, 정답 10/10 | 4.70초, 정답 9/10 |
| 다음 동작을 고르는 화면, 9쌍 | 3.8 Flash 4.83초, 정답 8/9 | 3.5 Flash-Lite 1.53초, 정답 9/9 |
| 도착 화면에서 완료 근거만 찾기, 3쌍 | 3.8 Flash 4.15초, 정답 3/3 | 3.5 Flash-Lite 1.24초, 정답 0/3 |
| 이미 목적지인 화면에서 계획을 처음 시작, 4쌍 | 3.8 Flash 정답 2/4 | 3.5 Flash-Lite 정답 0/4 |
| 새로운 한국어 첫 메뉴 요청, 6쌍 | 3.8 Flash 3.51초, 정답 6/6 | 3.5 Flash-Lite 1.64초, 정답 6/6 |

압축 실험은 백엔드 `06b9521`, 모델 비교는 이후의 계획 힌트 변경을 포함한 `755571e`를 기준으로 했다. 각 비교 안에서 실제 Gemini API를 순차 호출했고 화면별로 두 조건의 순서를 번갈아 배치했다. 모델 비교에서는 화면, 프롬프트, 응답 스키마, 추론 수준 `low`, 출력 상한 2,048토큰과 전체 시간 한도 9초를 동일하게 했다. 시간 초과도 오답 및 대기 시간에 포함했다.

첫 12개 화면은 정책 A로 안드로이드 에뮬레이터의 Settings, DeskClock, DocumentsUI에서 얻었다. 9개는 다음 동작, 3개는 완료 근거 문제였다. 정답은 실제 다음 도구와 대상, 또는 현재 목적지 제목의 패키지와 역할로 채점했다. 이미 목적지인 화면 4개는 현재 관찰을 그대로 사용해 저장된 계획 없이 시작하도록 재구성했다. 경량 모델은 최근 파일 화면에서 완료를 확인하는 대신 새 동작을 제안했다.

추가 메뉴 6개는 기존의 실험용 조작 허용 목록을 제거하고 알림, 동영상, 접근성, 다운로드, 소리 및 진동, 이미지에 대한 새 한국어 요청을 보냈다. 모두 사람이 승인하기 전의 다음 동작을 채점했다. Settings와 DocumentsUI의 공개 화면 3개를 공유하므로 서로 다른 앱 6개에 대한 일반화 검증으로 해석할 수 없다. 이 추가 측정 중에는 독립 에뮬레이터 과제 블록도 같은 API 프로젝트에서 실행됐다. [호출별 기록](./paired-calls.jsonl)

## 안드로이드에서의 완료 검증

정책 A와 같은 테스트 APK로 원래 한국어 목표 6개를 각 조건에서 한 번씩 실행했다. 자동 승인된 공개 탐색 작업이며, 에뮬레이터에서 목적 상태가 안정적으로 관찰되고 앱도 완료를 검증해야 성공이다. 과제 제한은 30초였다. 순서는 기존 모델, 첫 메뉴와 후속 메뉴, 첫 메뉴 전용이었다. 각 조건에서 모델이 선택한 동작에 따라 과제 전체의 호출 수는 달라질 수 있다. 위 표의 호출당 효과는 동일 입력의 쌍 비교로 계산했다.

후속 메뉴에까지 경량 모델을 사용한 블록에서는 성공이 4/6에서 3/6으로 떨어졌다. 최근 파일에서 실제로 메뉴를 열고 ‘Recent’를 눌러 목적지에 도달했지만 앱이 완료를 검증하지 못했다. 이 후보는 제외했다. 최종 후보는 제목·탭·상태값이 없는 버튼과 목록으로만 구성된 첫 탐색 화면에 한정했다. 이전 시도, 계획, 완료 근거, 복구, 유효한 학습 이력 또는 키보드가 있는 경우에는 기존 모델을 사용한다.

첫 메뉴 전용 블록의 첫 시도는 첫 과제 후 홈 화면 복원 과정에서 접근성 서비스가 해제돼 중단됐다. 모델 호출 2건이 있었고 저장된 완료 과제는 0건이었다. 해당 시도는 성공률 계산에서 제외했으며 전용 기기에 접근성 서비스를 다시 연결한 뒤 새로운 실행 ID로 여섯 과제를 다시 시작했다.

| 한국어 공개 앱 과제 | 기존 모델 | 후속 메뉴 포함 | 첫 메뉴 전용 |
|---|---|---|---|
| 디스플레이 및 터치 | 성공 | 성공 | 성공 |
| 언어 및 지역 | 실패 | 실패 | 실패 |
| 타이머 탭 | 성공 | 성공 | 실패 |
| 스톱워치 탭 | 성공 | 성공 | 성공 |
| 최근 파일 | 성공 | 실패 | 실패 |
| 문서 분류 | 실패 | 실패 | 성공 |
| 완료 검증 성공 | 4/6 | 3/6 | 3/6 |
| 실제 Gemini 호출 | 12 | 11 | 11 |

세 블록의 요청 로그는 에피소드와 모두 대조됐다. 잘못된 완료 제안과 보호 규칙 위반은 각 블록에서 0건이었다. [과제별 결과와 모델 대기 시간](./native.json)

## 판정과 재현

**첫 메뉴 전용 모델을 실험 설정으로 유지하고 기본 적용은 보류한다.** 첫 메뉴에서 실제 모델이 바뀐 과제는 두 개였다. 디스플레이의 첫 응답은 3.61초에서 1.99초로, 언어 및 지역은 3.33초에서 2.60초로 줄었다. 두 과제의 완료 결과는 각 조건에서 같았다. 전체 과제에서는 기존에 성공했던 타이머와 최근 파일이 실패했고, 둘 다 기존 3.8 Flash를 호출하다 약 8.6초에 시간 한도에 걸렸다. 문서 분류는 두 조건 모두 3.8 Flash를 사용했고 마지막 블록에서 성공했다. 블록별로 각 과제를 한 번 실행했으므로 이 차이에서 모델 교체의 인과 효과를 추정할 수 없다. 사전에 정한 전체 완료 기준은 충족하지 못했다.

기본 구성은 기존 Gemini를 사용한다. 독립 실험용 백엔드에서 `APP_TASK_MENU_MODEL=gemini-3.5-flash-lite`로 첫 메뉴 후보를 선택할 수 있다. 각 조건은 모델 선택 후 일반 Gemini 호출 경로를 그대로 실행한다. 기존 앱 승인, 완료 근거 검증, 출력 상한과 호출 시간 한도를 사용한다. 실제 사용자 배포의 정확도와 시간 분포는 측정하지 않았다. 다음 비교에서는 느린 3.8 Flash 호출의 시간 초과를 포함해 시간대를 바꿔 반복하고, 동일 과제에서 각 모델의 성공과 실패를 함께 집계할 필요가 있다.

재현 스크립트는 에뮬레이터에서 수집한 공개 메뉴 세 개와 고정된 한국어 목표 여섯 개를 사용한다. 백엔드 의존성이 설치된 환경에서 저장소 루트에서 다음 명령을 실행하면 Gemini에 12번 요청하고 각 응답의 동작, 정답 여부, 대기 시간을 새 파일에 쓴다. [재현 스크립트](./replay.py) · [공개 테스트 화면](./menu-fixtures.json)

```sh
python docs/reviews/2026-11-21-gemini-call-latency/replay.py --output /tmp/click-menu-replay.jsonl
```

## GPT 연결 후 같은 공개 화면 재측정

앱의 `/api/v1/agent/app-guide/task` 경로에서 OpenAI Responses API의 `gpt-6.2-sol`을 호출했다. 위의 한국어 메뉴 요청 6개에서 기대한 버튼을 6개 모두 제안했고, 실제 호출 6회의 응답 시간 중앙값은 3.37초였다. 별도로 디스플레이 및 터치, 최근 파일, 문서 분류 화면에서 읽기 전용 완료 근거 3개를 모두 찾았다. 이 3회 호출의 중앙값은 2.16초였다. 기록된 화면을 재사용한 테스트이며 단말에서 전체 과제를 다시 실행하지는 않았다. ## 로컬 SLM과 호출 비용

Apple M3, 메모리 16GB의 Mac에서 Qwen3-1.7B Q8_0을 llama.cpp b12600으로 실행했다. 모델 파일 크기는 1,834,426,016바이트였으며 제작자가 게시한 SHA-256과 일치했다. 모델을 메모리에 올린 후 루프백으로 한 건씩 보냈다. 컨텍스트 8,192, 슬롯 하나, 추론 모드 꺼짐, 온도 0, 시드 42를 사용했다. 같은 Mac에서 안드로이드 빌드도 진행 중이었으므로 전용 서버 처리량을 추정하기에는 부적절하다. 이 실험으로 발생한 클라우드 API 요금은 0원이다. [모델 카드](https://huggingface.co/Qwen/Qwen3-1.7B-GGUF) · [llama.cpp 서버](https://github.com/ggml-org/llama.cpp/tree/master/tools/server)

| Qwen에 맡긴 일 | 올바른 응답 | 호출당 중앙값 |
|---|---:|---:|
| 앱의 전체 계획을 반환하는 메뉴 요청 | 0/6 | 8.77초 |
| 앱에서 요구하는 완료 근거 반환 | 0/3 | 6.22초 |
| 짧은 응답으로 다음 버튼 하나 선택 | 6/6 | 2.12초 |
| 짧은 응답으로 이미 도착한 화면의 근거 하나 선택 | 2/3 | 2.86초 |
| 아직 도착하지 않은 화면에서 근거 없음 선택 | 0/3 | 2.51초 |

전체 계획은 GPT와 같은 프롬프트·구조화 출력·검증·호출 예산으로 평가했다. 메뉴 6건 중 5건은 시간 초과, 1건은 제한 시간 내 작업 프로세스 정리 실패였다. 짧은 응답 실험은 같은 화면의 공개 레이블, 역할, 선택 상태, 클릭 가능 여부와 사용자 목표만 제시하고 최대 32토큰으로 현재 항목 ID 또는 없음 중 하나를 고르게 했다. 오답 3건은 목적지에 도착하기 전인데 근거를 골랐다. 이 실험에서는 동작 실행이나 앱의 완료 처리를 하지 않았다. GPT에는 이 미도달 3건을 보내지 않았다. 비교 결과는 간단한 버튼 선택용 후속 실험을 뒷받침하며 전체 계획이나 단독 완료 판정의 기본 모델로 채택할 근거는 부족하다. [전체 계획 기록](./qwen-planner.jsonl) · [짧은 선택 기록](./qwen-choice.jsonl)

앞서 GPT 실호출 9회의 응답에 보고된 토큰은 입력 14,315개와 출력 1,022개였다. 일반 단가로 모든 입력을 캐시 미적용으로 계산하면 약 0.039달러다. 실제 청구액은 계정의 캐시 할인과 과금 조건에 따라 달라질 수 있다. [OpenAI 공식 단가](https://developers.openai.com/api/docs/models/gpt-6.2-sol)

## 앱 경로에서 로컬 메뉴 선택과 동시 요청

로컬 제공자를 선택하면 목표의 첫 공개 메뉴에서 현재 앱의 허용된 버튼을 짧은 ID로 제안할 수 있다. 이전 계획이나 완료 근거가 있거나 여러 앱이 선택된 화면에서는 전체 플래너가 처리한다. 짧은 응답에서도 사용자 승인과 기존 네이티브 검증을 거친다. 같은 메뉴 6건을 앱 API 경로로 순차 재생한 결과 모두 올바른 버튼을 제안했고, 호출 시간 중앙값은 3.44초였다. 도착 화면 3건에서는 전체 플래너가 완료 근거를 한 건도 찾지 못했다. 따라서 이 로컬 구성을 단독 완료 검증기로 채택하기는 어렵다. [연결 후 호출 기록](./qwen-connected.jsonl)

같은 M3에서 메모리에 올라온 Qwen 서버 한 슬롯에 백엔드 한 프로세스를 연결했다. 공개 메뉴 요청을 조건마다 세 차례 동시에 전송해 앱 API 응답을 받기까지의 시간을 측정했다. 사용자 수는 같은 순간에 모델 요청을 보낸 수다. 실험 중 같은 Mac에서 다른 개발 작업도 진행됐다. 아래 수치는 실기기 왕복 시간이나 유료 Qwen API의 속도를 나타내지 않는다. [동시 요청 기록](./qwen-local-load.jsonl) · [재현 스크립트](./local-load.py)

| 동시 요청 | 제안한 버튼이 정답 | 호출 전 거절 | 모델까지 간 요청의 응답 중앙값 |
|---:|---:|---:|---:|
| 1 | 3/3 | 0 | 3.16초 |
| 2 | 6/6 | 0 | 3.54초 |
| 4 | 6/12 | 6 | 3.47초 |

거절 6건은 모두 23~45ms 만에 백엔드의 동시 모델 요청 한도에 걸렸다. 네 명의 중앙값에는 거절된 요청을 포함하지 않았다. 모델 서버를 유료 API로 바꿔도 백엔드 프로세스당 두 건의 한도는 유지된다. API 전환과 별개로 짧은 대기열을 검토하고, 같은 실험에서 대기까지 포함한 총 응답 시간과 거절률을 함께 비교할 수 있다.

싱가포르 계정에서 텍스트 모델 `qwen-flash-character`의 무료 잔여량 100만 토큰과 `Stop-on-Exhaust` 활성화를 확인했다. 이 모델은 역할 대화에 특화돼 있다. 실험 당시 이 계정의 무료 할당 목록에는 일반 Qwen3.7-Flash와 Qwen3.8-Flash가 없었다. [모델 설명](https://www.alibabacloud.com/help/en/model-studio/qwen-flash-character) · [무료 할당 정책](https://www.alibabacloud.com/help/en/model-studio/new-free-quota)

메뉴 화면 6건, 실제 도착 화면 3건, 목적지로 가는 메뉴만 보이는 미도달 화면 3건을 실험용 전송기로 재생했다. 앱의 일반 플래너 프롬프트와 결과 검증기를 사용했다. 첫 조건은 Chat Completions의 `response_format=json_schema`에 스키마를 지정했다. 두 번째 조건은 `response_format=json_object`로 바꾸고 동일 스키마를 프롬프트 끝에 명시했다. 같은 12개 화면을 같은 순서로 조건마다 한 번씩 보냈다. 출력 상한은 2,048토큰, 온도는 0이었다. 각 요청에 새 HTTPS 연결을 열었다. 앱 작업 전체나 단말에서의 터치를 측정한 실험은 아니다.

| 항목 | API 스키마 지정 | JSON 모드와 프롬프트에 스키마 명시 |
|---|---:|---:|
| 목적에 맞는 메뉴 제안 | 0/6 · 1.31초 | 3/6 · 1.41초 |
| 도착 화면에서 올바른 완료 근거 확보 | 0/3 · 0.79초 | 0/3 · 1.38초 |
| 미도달 화면에서 규격에 맞는 빈 근거 반환 | 0/3 · 0.92초 | 0/3 · 1.20초 |
| 응답이 보고한 입출력 토큰 합계 | 14,455 | 18,736 |

시간은 호출 전부터 앱의 응답 검증이 끝날 때까지의 중앙값이며 실패도 포함한다. 24건 모두 HTTP 200이었고, 6개 미도달 응답은 앱 검증기가 모두 거부했다. 이를 모델이 스스로 미도달을 판별한 정답으로 집계하지 않았다. 두 조건은 응답 모드와 스키마 전달 위치를 함께 바꿨으므로 각각의 효과는 분리할 수 없다. 기존 GPT 기록은 메뉴 6/6, 도착 근거 3/3이며 미도달 3건의 짝비교 기록은 없다. 이 표본에서 Flash Character를 기본 플래너나 완료 검증기로 도입하는 것은 보류한다. [24건의 호출·채점 기록](./qwen-free-api.jsonl)

## OpenRouter Qwen3.8-Flash의 첫 메뉴 응답 시간

`develop`의 `f591fc0`에서 서버 완료 검증을 켜고, 앱 과제 API에 기존 Settings·DocumentsUI 메뉴 6개를 차례로 재생했다. OpenRouter Responses API에 모델을 `qwen/qwen3.8-flash`로 고정하고 두 조건 모두 추론 수준을 `none`으로 요청했다. 12개 메뉴 응답 모두 실제 모델 ID가 일치했고 추론 토큰은 0개였다. 일반 계획 6회와 완료 확인 2회를 먼저 측정하고, 같은 메뉴 순서로 버튼 선택 6회를 측정했다. 조건마다 같은 6개 메뉴에 각각 한 번씩 요청했다. 휴대전화 터치부터 화면 전환까지의 시간은 이번 재생에 포함되지 않는다. [호출별 결과](./openrouter-latency.jsonl)

| 첫 메뉴 조건 | 올바른 버튼 제안 | HTTP 왕복 중앙값 | 호출 준비부터 검증까지 중앙값 | 메뉴 6회 비용 |
|---|---:|---:|---:|---:|
| Qwen 일반 계획 | 4/6 | 3.274초 | 3.390초 | $0.001751 |
| Qwen 버튼 ID | 6/6 | 1.173초 | 1.286초 | $0.000347 |
| GPT 일반 계획, 이전 기록 | 6/6 | 미계측 | 3.369초 | — |
| Gemini 3.8 Flash 일반 계획, 이전 기록 | 6/6 | 미계측 | 3.51초 | — |

HTTP 왕복은 백엔드 워커가 요청 전송을 시작한 시점부터 전체 응답을 읽고 스트림을 닫을 때까지다. 이 값에는 네트워크·OpenRouter·모델 제공자 대기와 생성 시간이 함께 들어간다. 실패한 메뉴도 대기 시간에 포함했다. FastAPI 요청 직전부터 응답을 받기까지의 중앙값은 일반 계획 3.393초, 버튼 선택 1.289초였다.

버튼 선택은 매번 모델을 호출한다. 첫 메뉴에서 공개 버튼의 현재 ID와 레이블을 제공하고, 선택한 ID 또는 `none`을 받는다. 이를 허용된 버튼 동작에 연결하고 기존 검증을 거친다. 일반 계획 대비 중앙 입력 토큰은 1,470개에서 348개로, 출력은 146개에서 9개로 줄었다. 같은 메뉴 여섯 쌍에서 모두 빨랐다. 일반 계획에서 다운로드와 이미지 두 건은 완료 근거의 상태값을 현재 화면에서 검증할 수 없어 버튼 제안이 차단됐다. 두 건 모두 버튼 선택 형식에서는 올바른 대상을 제안했다. 실행 순서가 고정됐고 입력과 출력 형식이 함께 바뀌었으므로 입력 길이, 생성, 캐싱 효과를 개별적으로 추정할 수 없다. GPT도 같은 짧은 형식으로 시험해야 모델 자체의 속도를 비교할 수 있다.

**완료 경로.** 영어 디스플레이 도착 화면에서는 Qwen이 실제 근거를 반환하지 못했다(앱 API 2.538초). 도착 전 화면은 올바르게 근거를 보류했다(1.388초). 한국어 단위 테스트에서 구성한 화면으로 서버의 로컬 완료 검증도 재생했다. 정확한 ‘디스플레이’ 제목을 모델 호출 없이 확인했다(2.274ms). ‘앱 알림’ 목표는 상위 화면 제목 ‘알림’만 보고도 완료로 잘못 처리했다(1.368ms). 원격 `feat/backend-completion-triage`는 이미 이번 `develop`에 포함돼 있었다. 이 거짓 완료는 기존 실기기 실험에도 기록돼 있다. [실기기 2차 보고서](../2026-11-21-device-round2/report.md)

**적용 범위.** 단순 첫 메뉴의 버튼 선택을 제한적으로 실험할 근거가 있다. 일반 계획과 완료 검증을 Qwen으로 일괄 교체하는 것은 보류한다. GPT를 주 플래너로 두고 조건에 맞는 첫 메뉴만 Qwen을 호출하는 서버 옵션을 추가했다. 두 계열의 실험 조건과 서버 자체 완료 경로를 포함해 OpenRouter 유료 호출 14회가 보고한 비용은 총 $0.00242763이었다. 두 조건의 메뉴 측정은 아래 명령을 각각 별도 출력 파일로 실행해 재현할 수 있다.

```sh
python docs/reviews/2026-11-21-gemini-call-latency/replay.py --provider openrouter --output /tmp/click-qwen-full.jsonl
python docs/reviews/2026-11-21-gemini-call-latency/replay.py --provider openrouter --short-menu --output /tmp/click-qwen-short.jsonl
```
