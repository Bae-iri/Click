# 실기기 검증: 요청 해석 · 설정 안내 · 범용 앱 안내 (2026-11-22)

Galaxy Note20(SM-N981N, Android 13) 1대에서 측정했다. 스크립트가 승인 버튼을 대신 눌렀고 사람 참여는 없다. 실패와 시간 초과는 모두 분모에 넣었다. 모델이 스스로 완료라고 한 것은 성공으로 세지 않고, 기기 화면을 독립적으로 읽는 판정기가 목표 도달을 확인한 경우만 성공으로 셌다.

|---|---|---|
| 요청 해석 | 배포 서버, Jev 분류 | 지원 요청 378건 중 372건 즉시 확정(98.4%), 잘못된 목표 0건 |

## 1. 요청 해석 (417건)

- 카탈로그 139개 목표 × 표현 3개. API 해석 단계만 측정했고 화면 실행은 포함하지 않는다.
- 지원 요청 378건:
  - 수정 전 362건(95.8%), 수정 후 372건(98.4%)이 바로 정확한 목표로 확정됐다.
  - 나머지 6건은 휴대폰 전체인지 특정 앱인지 묻는 정상적인 되묻기다.
  - 잘못된 목표를 고른 경우는 0건이다.
  - 카탈로그 예문과 똑같은 문장 43건을 빼면 348건 중 344건(98.9%)이다.
- `catalog_only` 39건은 서버가 모두 `unsupported`로 돌려줬다.
  - 이것은 서버 해석 단계의 결과다. 앱은 `unsupported`를 받으면 범용 앱 안내로 넘기므로, 사용자에게 보이는 최종 결과는 아니다.
- 입력부터 해석까지 걸린 시간(수정 전, 배포 서버 기준): 중앙값 529ms, p95 1,043ms.
  - 수정 후 값은 로컬 서버라 네트워크가 빠져 있어 비교에 쓰지 않는다.
- 원자료: [수정 전](resolution-baseline.json) · [수정 후](resolution-after-local.json)

## 2. 설정 안내 (Task Graph + Jev)

26과제 × 2회 = 52회. 수정본(`1e769fe7`) APK와 로컬 서버를 썼고, Jev는 실제 API를 호출했다.
- 과제 구성: 설정 화면 열기 20종, 설정값 변경 6종(글자 크기·밝기·미디어 음량 각각 올리기·내리기).
- 1회차와 2회차는 요청 표현과 시작 위치(설정 홈 맨 위 / 아래로 스크롤한 상태)를 바꿨다.
- 원자료: [part1](fixed-matrix-part1.json) 시행 0~11, [part2](fixed-matrix-part2.json) 시행 12~51.
- 집계 스크립트: [summarize_overlay.py](summarize_overlay.py)

수정 전과 후는 과제 순서와 구성이 달라 엄밀한 짝비교가 아니다. 수정 전 38회 중 1회는 앱 크래시로 끝났다.

- **2회 모두 성공(13종):** 디스플레이, 소리 및 진동, 연결, 접근성, 화면 자동 꺼짐, 자막, 편안하게 화면 보기, 확대, 음량, 글자 크기 키우기·줄이기, 미디어 음량 줄이기.
- **실패가 몰린 과제:** 밝기 올리기·내리기, 미디어 음량 올리기, 방해 금지, 벨소리, 알림 소리, 시인성 향상, 청각 보조, TalkBack. 대부분 삼성 접근성·소리 하위 화면에서 2단계 이후 대상을 확정하지 못하고 도움 요청(`EXPLICIT_HELP_REQUIRED` 18회)이나 시간 초과(5회)로 끝났다. 잘못된 곳을 누르거나 거짓 완료로 끝난 경우는 없었다.
- **속도:** 첫 안내까지 걸리는 시간의 대부분은 목표 메뉴가 첫 화면에 보이지 않을 때 위아래로 스크롤하며 찾는 시간이다. 스크롤 한 번에 서버 왕복과 화면 안정 대기로 약 1.4초가 든다.

## 3. 범용 앱 안내: 운영 서버 qwen → triage → jev (30회)

카탈로그에 없는 요청이 실제로 타는 경로다.
- USB 전용 중계 서버(`Backend/scripts/serve_device_audit_proxy.py`)로 운영 API의 `/app-guide/task`만 호출했다.
- 운영 서버 설정: Qwen 3.8 Flash(OpenRouter), 서버 triage, Jev 완료 선택.
- 운영 서버에 임시 감사 계정을 만들어 썼고, 측정 직후 삭제했다.
- 과제: 시계·Chrome·YouTube 10개 × 3회. 시행마다 목표가 아닌 화면에서 시작했다.
- 원자료: [apps-production.json](apps-production.json) 앞 30행. 31행은 시간 제한으로 시작 직후 중단해 제외했다.

| 지표 | 값 |
|---|---|
| 완료 확인까지 성공 | 4/30 |
| 목적 화면 도착(독립 판정기 기준) | 16/30 |
| 거짓 완료 | **1건** (YouTube 검색: 동작 없이 완료 확인을 띄움) |
| 첫 동작 제안까지 시간 | 중앙값 4.8초, p90 6.7초 (제안이 나온 16회 기준) |
| Qwen 호출 왕복 시간 | 중앙값 1.3초, p90 2.9초 (43회) |
| 성공한 회차의 완료 확인 시간 | 중앙값 11.7초 |

### 실패 원인

1. **시계 앱이 타이머 탭으로 열려 시작하지 못함 (9회)**
   - 삼성 시계는 마지막에 본 탭으로 열린다. 타이머의 숫자 입력칸 때문에 화면 전체가 `protected`로 분류되고, 탭 이동 안내조차 시작하지 않는다.
   - 수정 방향: 입력칸만 가리고, 탭처럼 공개된 이동 컨트롤은 계속 안내한다.
2. **Chrome 메뉴·새 탭에서 화면 대기만 함 (6회)**
   - `awaiting_screen`에서 넘어가지 않았다.
   - 다음 작업: Chrome 창이 읽기 불가로 판정되는 조건을 확인한다.
3. **도착했지만 완료로 인정하지 못함 (약 10회)**
   - YouTube Shorts·구독·검색, 스톱워치에서 독립 판정기는 도착을 확인했지만, 앱은 완료 증거를 잡지 못하고 사용자 확인 상태로 넘어갔다.
4. **거짓 완료 1회**
   - YouTube 검색 2회차에서 동작 제안 없이 `checking_result → confirm_result`로 끝났다. 판정기 기준으로는 검색창이 열려 있지 않았다.
   - 사용자에게 잘못된 "완료"를 보여준 사례이므로 가장 먼저 고칠 대상이다.

측정 도구의 한계도 있다. 이 하네스는 안전을 위해 미리 정한 버튼 이름만 실행한다. 그래서 정상적인 제안이 거부된 회차(`proposed → needs_input`)가 일부 섞여 있다.

## 후속 코드 점검: 삼성 하위 메뉴와 조절 경로

아래는 저장된 화면과 코드로 확인한 입력 문제다. 수정 후 실기기 성공률을 다시 측정한 결과는 아니다. 위의 29/52 수치는 그대로 유지한다.

- **같은 버튼의 출발 화면 중복:** 저장된 접근성·연결·소리 화면에서 시인성 향상, 청각 보조, TalkBack, 입력 및 동작, Wi-Fi, 블루투스, 벨소리, 알림 소리 버튼 하나를 `OPEN_PAGE`와 `OPEN_PAGE_FROM_HOME` 두 후보로 보냈다. 후보가 둘이라 `immediate_request`도 생성되지 않았다. 독립적인 네이티브 화면 제목이 출발 화면 하나를 정확하게 지목할 때만 같은 버튼·목적지의 다른 출발 경로를 제외하도록 수정했다. 제목이 없거나, 메뉴 내부 글자이거나, 비전 결과이거나, 출발 화면이 모호하면 후보를 유지한다. 최종 선택과 보류 기준은 계속 Jev가 적용한다.
- **페이지 이름과 조절 단계 이름의 혼동:** 삼성 디스플레이 화면에는 밝기 슬라이더가 바로 있다. 하지만 atomic 판정의 화면 선택지에는 조절 단계 이름인 `화면 밝기`와 `unknown_page`만 있었고, 화면 제목을 식별하라고 지시했다. 네이티브 슬라이더와 검토된 설정 이름으로 식별하는 조절 단계임을 명시하고, 실제 페이지 제목이 디스플레이·음량 등 상위 페이지 이름으로 남아 있을 수 있음을 설명하도록 수정했다. 신뢰도 기준, 승인, 실행 후 실제 설정값 검증은 유지한다.
- **음량 증가 실패 원인은 미확정:** 증가 실패 2회 모두 OS 미디어 음량이 6에서 바뀌지 않았다. 다만 `EXPLICIT_HELP_REQUIRED`는 모델 보류뿐 아니라 프런트엔드에서 자동 조작을 거부하거나 직접 조작을 요청한 상태도 포함한다. 기존 52회 자료에는 시행별 `ui_selection`이나 `native_dispatch`가 없어 이 둘을 구분할 수 없다. 코드상 증감은 같은 실행 함수를 쓰며, 기기의 미디어 음량 범위와 네이티브 슬라이더 범위를 대응시켜 한 단계만 움직인다. 조절 함수와 승인 조건의 단위 테스트는 실기기에서 증가에 성공했다는 증거가 아니다.

저장된 삼성 화면으로 후보 중복·화면 설명 회귀 테스트를 추가했다. Android 실행 함수에도 밝기 양방향 드래그와 미디어 음량 양방향 `SET_PROGRESS` 검사를 추가했다. 다음 실기기 실행에서는 실패 시행의 `ClickAgent` `agent.debug.ui_selection`(보류 사유·화면/대상 신뢰도)과 `ClickAutomation` `native_dispatch`(실제 동작 전달 여부)를 함께 수집해야 한다.

검증: 모델 응답을 제어한 Backend 관련 회귀 검사 187개, Android 단위 테스트 32개가 통과했다. 신규 실제 Jev 호출이나 실기기 재측정은 포함하지 않는다.
