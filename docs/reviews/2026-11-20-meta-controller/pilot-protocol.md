# MetaController 기술 파일럿 — 2026-11-20

이 문서는 결과를 보기 전에 고정한 기술 파일럿 범위다. 원래 제안한 252회 제품 평가와 구분한다.

최종 계측은 `native-navigation.v4`다. v2 실행은 이미 선택된 시계 시작 탭을 다시 클릭하려다 준비 실패로 처리하는 계측 오류가 있어 63회 후 중단했다. v3에서도 점검 직후 실제 반복 실행의 시작 패키지가 간헐적으로 달라지는 준비 경합을 발견했고, 드라이버가 tap 이외의 기존 안전 탐색 도구를 거절해 복구 경로를 제한하고 있었다. v2/v3 자료는 `development/`에 보존하고 최종 성능 집계에서 제외한다. v4는 후보 정책·모델·12개 요청·목표 정답을 유지하고 하네스만 수정한 뒤 하나의 최종 216회 코호트를 수행한다. 이후 결과를 보고 후보나 정답을 바꾼 실행을 같은 최종 코호트에 합치지 않는다.

v4에서는 모델 없는 시작 상태 점검과 본 실험이 동일한 준비 함수를 사용한다. 총 10초 준비 제한 안에서 예상 패키지·public 상태·같은 window가 서로 다른 관측 3개 이상과 600ms 이상 유지되어야 시작하며, 피드 전체 내용이나 fingerprint가 같을 것을 요구하지 않는다. 시작 탭/메뉴 준비 이후에도 같은 barrier를 적용한다. UiAutomation의 독립 root도 같은 패키지·window로 읽히고 목표 부재가 확인되어야 시작하며, root가 없으면 제한 안에서 다시 관찰한다. 이 준비 관찰과 재시도는 세 arm의 15초 실행 예산 밖에 있으며 횟수·대기 기간·허용된 패키지 범주를 기록한다. 시작 상태 해시는 barrier가 반환한 실제 snapshot의 허용된 공개 컨트롤로 계산하며 공개 컨트롤이 없으면 빈 해시를 만들지 않고 준비 실패로 기록한다. 준비 중 독립 정답은 목표가 이미 달성된 시작을 배제하는 데만 쓰며, 목표가 달성될 때까지 기다리지 않는다.

실제 모델을 쓰는 에피소드는 준비 전에 serial loopback facade의 `/health`가 200/ready로 답할 때까지 최대 15초 기다려 이전 에피소드의 남은 provider 작업이 다음 arm의 지연에 섞이지 않게 한다. 이 모델 호출 없는 fence는 실행 시간 밖에서 `provider_drain_ms`로 기록하며, 준비 상태가 아니면 provider 품질 실패와 구분한 준비 실패로 남긴다. 에피소드 제한 뒤까지 이어진 모델 작업의 호출 수·처리 시간은 기존 서버 로그의 원래 에피소드 비용에 계속 포함한다.

실행 드라이버는 허용된 공개 tap 외에 기존 정책·네이티브 실행기가 승인하는 back, 공개 목록 scroll, 명시적으로 선택한 같은 앱 open_app을 그대로 허용한다. 텍스트 입력과 다른 앱 열기는 허용하지 않는다. 무반응/dispatch 지연은 세 arm 모두 첫 번째 정책상 유효한 TAP 요청에만 주입하고, 복구용 back/scroll/open_app에는 주입하지 않는다. 실제 변경을 관찰한 fingerprint 차이에만 화면 변화 알림을 보내며, 준비 barrier의 반복 읽기를 MC 이벤트로 전달하지 않는다.

탐색 tap의 허용 목록은 관찰·정답용 공개 라벨 목록과 분리한다. 시작·일시정지·초기화, 밝기·소리 모드, 음성 검색, 시크릿 탭 생성 등은 관찰 가능하더라도 누르지 않는다. 이 공통 실험 범위 제한은 모든 arm에 동일하게 적용한다.

성능 측정 전 개발 점검 `dev-smoke1`은 명사형 목표를 쓴 `native-navigation.v1`이었다. 시작 화면의 메뉴 이름을 모델이 완료 조건으로 선택해, 실제 이동 없이 VERIFIED 결과 확인을 제시하는 기존 완료 조건 grounding의 빈틈을 발견했다. 당시 드라이버가 그 제시를 자동 확인한 것은 사용자 확인을 과도하게 가정한 계측 문제였다. 해당 점검은 개발 데이터로만 보존하고 본 성능 표에서 제외한다. v1은 폐기하고, 명시적인 화면 열기·탭 이동 요청을 쓰는 v2를 본 실행 전에 고정한다. 독립 정답과 앱·과제 목록은 유지하며, 기존 제품/MC 정책을 이 변경으로 수정하지 않는다. 명확한 요청에서도 같은 현상이 발생할 수 있으므로 v2에서 별도 측정한다.

개발용 공개 컨트롤 점검에서 Chrome 시작 화면에도 `새 탭` 버튼이 있음을 확인했다. 메뉴 열기의 v1 정답은 시작 상태와 목표를 구분하지 못했으므로, 본 실행 전 v2에서는 메뉴에만 나타나는 `새 시크릿 탭` 항목의 표시로 교정한다. 시크릿 탭을 누르거나 생성하지 않으며 메뉴의 표시만 확인한다. 다른 독립 정답 조건은 변경하지 않는다.

## 후보와 비교군

- A: 같은 계측 빌드의 현재 AppTask 정책. 기존 실행 전 안전 검사, 5초 실행 후 검증, 보호 화면·완료 검증 유지.
- B: 같은 구성에 비루팅 MC-v0 추가. 최대 16개 이벤트/결과 기억, 최근 공개 화면 이벤트가 있으면 최대 8초 관찰, 확인되지 않은 동작 이후 최대 3회 재관찰. 정확히 같은 상태·대상의 수락 후 미확인 동작은 자동 재실행하지 않는다.
- C: B에서 새 이벤트에 따른 대기 연장만 제외. 기존 안전 검사와 복구 예산 유지. 주 A/B와 같은 과제·조건에서 수행하는 보조 비교군이다.
- D: 매 단계 모델 reflector는 구현하지 않았으므로 NOT_IMPLEMENTED. 다른 기능의 시간을 D 결과로 대신하지 않는다.

UIAnchor의 LSPosed 이벤트 수집, 학습한 VLM reflector, 파서·모델 교체는 포함하지 않는다. 기존 AppTask 모델을 통한 다음 동작 제안은 실제 Gemini 3.8 Flash로 실행한다. AI2 경험 재사용은 양쪽 모두 사용하지 않는다. 새로운 사용자 버튼과 FE 변경은 없다. 기존 앱에서는 A가 기본이다.

## 실제 실행 범위

고정 과제는 `pilot-catalogue.json`의 4개 앱·12개 공개 탐색 목표다. 목표를 모델에 준 뒤 실제 AppTaskController와 AppTaskExecutor를 사용한다. 스크립트가 동일한 승인 역할을 수행하므로 사람의 사용 시간이나 중장년층 사용성 결과가 아니다.

1. 개발용 공개 컨트롤 점검 및 연결 smoke test. 성능 표에서 제외.
2. 주 A/B: 12과제 × 3조건 × 2반복 × A/B = 144회 예약. 같은 과제·조건·반복의 C 72회를 추가해 총 216회를 예약한다. D는 미구현으로 제외한다.
3. 각 목표·조건·반복 안에서 A/B/C 순서를 결정론적 회전·역순으로 균형 배치하고, 반복마다 순서 인덱스를 이동한다. 실제 순서는 실행 전 manifest의 `scheduled_arm_orders`에 고정한다. 매 에피소드 새 컨트롤러를 생성한다. `arms` 인자로 A/B 또는 C만 선택한 실행도 가능하지만 별도 실행 범위로 명시한다.
4. 과제 실행 제한은 세 조건 모두 15초. 초기 관찰·모델 계획·실행·검증을 포함한다. 원 설계의 180초와 다르므로 제품 실험 결과로 합치지 않는다. 30초였던 초기 구현 기본값은 성능 측정 전에 15초로 수정했다.
5. 과제 누락·준비 실패·API 장애·불확실한 결과도 전체 예약 시도에 남긴다. 실행 준비가 된 과제만의 결과는 보조 지표다.

조건은 정상, 첫 수락된 탐색 조작을 버리는 무반응, 첫 네이티브 조작 요청을 5.5초 늦추는 **dispatch 지연**이다. 지연은 실제 앱 렌더링 지연이 아니며, 장애 빈도도 실제 서비스 발생 비율이 아니다. 양쪽 같은 의미의 첫 탐색 조작에 주입한다. 실제 주입까지 도달하지 못한 시도도 배정 조건에 유지한다.

시작 상태는 앱 진입과 지정 시작 탭/메뉴를 맞춘 뒤, 허용된 공개 컨트롤의 label/resource/선택 상태/경계를 정렬해 해시로 기록한다. 완전한 앱 내부 상태 초기화나 피드 동일성을 보장하지 않는다. 해시가 다른 쌍은 엄격 대응 비교에서 제외하되 전체 시도 집계에는 남긴다. 결정론적 순서 균형 배치는 완전 무작위 배정과 구분한다.

원래 계획의 설정값 변경 108회는 graph/네이티브 설정 실행 경로에 MC를 동일하게 연결하는 별도 작업이 필요하다. 이 파일럿의 설정 메뉴 진입을 글자 크기·밝기·음량 변경 성공으로 대체하지 않는다. 범용성의 정식 holdout 평가와 대상 사용자 연구도 이 파일럿에 포함하지 않는다.

## 측정과 정답

- 독립 정답: UiAutomation으로 사전 지정 공개 결과 label/resource/선택 상태를 확인한다. 같은 label의 별개 대상은 모호함으로 취급하고, 결과가 700ms 유지되어야 목표 도달로 센다. 컨트롤러의 VERIFIED/DONE는 정답 입력으로 쓰지 않는다.
- UiAutomation root를 읽지 못한 순간은 목표 부재 0이 아니라 UNKNOWN이다. 이 순간에는 결과 확인 제시의 오판 타이머를 진행하지 않는다. 마지막에도 root를 읽지 못했고 안정된 목표 도달을 관찰하지 못했으면 `oracle_success=null`, `oracle_observable=false`, `oracle_final_match_count=null`로 남긴다. `false_verified_offer`도 확인 불가·모호한 경우 null이며 이를 오판 0건이나 성공으로 바꾸지 않는다.
- 검색창을 연 뒤 IME가 active root가 되는 경우를 위해, 독립 관측은 목표와 무관하게 window 정보로 foreground root를 선택한다. IME와 실험 앱 자신의 접근성 overlay만 제외하고 가장 위의 active/focused window를 읽는다. 다른 앱이나 시스템 권한창은 그대로 존중하고, 해당 root가 없거나 active/focused 후보가 없으면 UNKNOWN이다. 목표 앱이나 원하는 결과가 보이는 window를 찾아 선택하지 않는다. 점검·시작 window 교차 확인·실행 정답이 이 함수를 공유한다. UiAutomation의 interactive-window 조회 flag는 시험 중에만 켜고 종료 시 원래대로 복원한다.
- 목표 도달 시간, 컨트롤러의 완료 확인 시간, 최초 동작 제안 시간을 구분한다. 드라이버는 탐색 동작만 승인하고 결과를 사용자 대신 확인하지 않는다. `runtime_verified_offer`는 runtime이 결과 반영을 확인했다고 제시한 사건이며 `declared_done`와 다르다. 독립 목표가 없는 결과 확인 제시가 700ms 유지되면 `runtime_offer_without_goal`로 종료하며, `false_verified_offer`를 독립 검수 대상으로 남긴다. 독립 결과가 모호하면 해당 지표는 null이다. 목표 도달 시 시험이 끝날 수 있으므로 완료 확인이 없으면 null로 남긴다. 독립 정답은 MC 판단에 전달하지 않는다.
- 실패 포함 시간: 독립 목표 확인에 성공하면 실제 경과 시간, 그렇지 않으면 15초를 부여한다. 준비 실패의 짧은 실제 경과 시간을 속도 개선으로 세지 않는다.
- 모델 호출 수와 처리 시간은 로컬 facade가 실제 모델 진단에서 기록한다. raw goal/화면/응답/API 키는 파일에 남기지 않는다. 해시 task ID로 합치고, 에피소드 밖까지 이어진 provider 작업 시간은 별도 보존한다.
- 모델 의미상의 잘못된 대상 조작을 독립 판독하지 못하면 해당 측정은 null이다. native rejection 수를 잘못된 대상 조작 0건으로 바꾸지 않는다.
- 이벤트 버퍼 길이는 이벤트 수집률이 아니다. 이 파일럿에는 원시 시스템 이벤트의 전체 정답이 없으므로 수집률을 주장하지 않는다.

## 분석·판정

전체 배정 시도, 실행 준비 시도, 초기 상태가 일치한 대응쌍을 구분한다. 정상/무반응/dispatch 지연, 앱별 결과를 각각 보고한다. 작업 템플릿을 군집으로 한 대응 bootstrap 신뢰구간은 탐색적이며 반복 클릭을 독립 표본으로 세지 않는다.

제품 기본 적용은 정식 252회 범위·독립 오동작 평가·미사용 앱 평가가 미완료면 NO-GO(근거 미충족)다. 이는 논문의 MetaController 전체가 효과 없다는 판정과 다르다.

확장 파일럿 GO는 최소 6개 실제 기기 대응쌍/2개 작업군, 독립 정답, 측정된 오동작·허위/미검증 완료 없음, 성공률 저하 없이 실패 포함 시간 또는 성공률 개선, 해당 방향의 군집 신뢰구간 지지, 정상 p95 지연 10% 이내라는 탐색적 gate를 사용한다. 미측정 안전 지표는 통과로 처리하지 않는다. 효과가 불명확하면 NEEDS_DATA, 관찰된 회귀나 안전 문제는 NO-GO/수정 후 재검증이다.

기존 사용자 로그인·데이터·앱은 보존한다. 실험에서는 다른 CLICK 접근성 서비스를 일시 분리하고 종료 시 원래 접근성 설정을 복원한다. 보호된 입력·계정·구매·전송·삭제·설정값 변경은 수행하지 않는다.
