# AI Agent 2: Jev 판단을 분석해서 안내를 개선하기

## 팀에 공유할 설명

Jev는 지금 화면을 보고 다음에 누를 대상을 고릅니다. AI2는 그 판단의 점수와 이후 결과를 모아서, 어디서 잘 맞고 어디서 불필요하게 멈추는지 확인합니다.

기존 경로의 순서만 바꾸는 기능은 대체 경로가 있을 때 효과가 있습니다. 이번에는 AI2의 중심 역할을 **Jev의 판단 품질과 실제 실행 결과 분석**으로 확장했습니다.

확인하려는 질문은 다음과 같습니다.

- 높은 점수를 준 안내 뒤 실제 조작이 성공했는가?
- 낮은 점수로 보류한 대상이 검수해 보니 맞는 대상이었는가?
- 어떤 설정 단계와 기종에서 보류·실행 실패·연결 오류가 많이 생기는가?
- 화면 정보나 후보 구성 등을 수정한 뒤, 같은 검수 화면에서 대상 선택이 나아졌는가?

분석 결과는 수정할 위치를 정하는 근거입니다. 보고서가 모델이나 점수 기준을 자동 변경하지 않습니다.

## 이번에 추가한 기능

| 기능 | 하는 일 |
| --- | --- |
| 판단 기록 수집 | 원본 점수, 보정 점수, 최종 점수, 기준값, 후보 수, 보류 이유, 모델·코드 버전을 기록합니다. |
| 판단과 조작 연결 | 원래 Jev 호출과 이후의 검증된 성공·실패를 연결합니다. 확인창 승인이나 안내 재표시는 새 호출로 세지 않습니다. |
| 문제별 집계 | 같은 단계의 반복 보류, 검수로 확인된 불필요한 보류, 높은 점수의 오답, 조작 실패, 연결 오류를 따로 보여줍니다. |
| 독립 검수 | 결정 번호·화면 해시·대상 해시가 일치하는 검수 기록만 정답 판단에 사용합니다. |
| 점수 기준 비교 | 검수한 후보에서 기준값별 통과 수, 틀린 대상 통과 수, 맞는 대상 보류 수를 보여줍니다. |
| 수정 전후 비교 | 같은 작업·그래프·기종·화면의 독립 holdout을 비교하고, 악화된 사례를 표시합니다. |
| 보호된 저장 | 개인 내용, 세션, 실행 기록, 분석 결과는 DB 저장 전에 암호화합니다. 분석 내용에는 화면 원문·전화번호·계정 이름을 추가하지 않습니다. |

## 두 성공률의 차이

**대상 선택 정답률**은 검수에서 맞다고 확인한 대상 수 / 정답·오답을 판정할 수 있었던 대상 수입니다. Jev 자신의 점수나 조작 성공만으로 정답을 만들지 않습니다. `unknown` 검수는 분모에서 제외합니다.

**실행 시도 성공률**은 원래 안내·대상·행동·관측이 연결된 성공 수 / 연결된 성공과 실패 수입니다. 대기, 미실행, 취소, 관측 부족은 실패로 세지 않습니다. 이 수치는 사용자 만족도나 전체 작업 완료율과 동일하지 않습니다.

예를 들어 안내 10건 중 실제 실행 결과가 확인된 것이 4건이고 그중 3건이 성공했다면, 실행 시도 성공률은 3/4입니다. 나머지 6건을 실패로 넣어서 3/10으로 만들지 않습니다. 이 숫자는 설명용 예시이며 실측 결과가 아닙니다.

로컬 규칙이 Jev가 고른 대상을 바꿔 실행한 결과는 Jev 원래 대상의 실행 성공률에서 제외하고 별도 집계합니다. 높은 점수의 실행 실패만으로 Jev가 틀린 대상을 골랐다고 단정하지 않습니다.

## 기록과 근거

실행 이벤트의 선택적 `jev_decision`에는 점수·허용된 상태 코드·해시·모델/코드 버전만 들어갑니다. `decision_hash`는 실제 호출마다 생성하며, 동일 안내의 재사용·승인·대기에서는 원래 번호를 유지합니다. 이전 형식의 이벤트도 처리하지만, 없는 과거 점수를 추측해서 채우지는 않습니다.

기종·설정 단계·그래프 해시·모델·코드 해시·기준값·자료 출처별로 나눠 봅니다. 합성 테스트와 실기기 기록은 별도 그룹입니다. 검수의 train/validation/holdout도 따로 집계합니다.

화면 내용이 저장되는 것이 아니므로, 검수자는 승인된 실기기 캡처나 별도 검수 근거를 보고 판단해야 합니다. 해시 자체를 보고 정답을 알 수는 없습니다. 외부 근거 원문은 이 보고서에 복사하지 않습니다.

## 실행 방법

운영과 같은 암호화 키·DB 설정으로 Backend 디렉터리에서 실행합니다. `model_training` 동의 이후이고 보존 기간 안에 있는 기록만 읽습니다. 동의 철회·탈퇴·만료된 이벤트를 참조하는 검수는 거부합니다.

```sh
python scripts/agent2.py process --limit 100
python scripts/agent2.py assess-jev --limit 100
python scripts/agent2.py assess-jev --reviews target-reviews.json --format json
python scripts/agent2.py compare-jev --before before-report.json --after after-report.json
```

배포 후 목표별 실행 구성을 확인하려면 `python scripts/agent2.py audit`를 실행합니다. 카탈로그 v2.4.0의 승인 목표 181개(설정 110개·쿠팡 71개)를 Backend 선택기로 대조하고 누락·비활성·최상위 우선순위 중복·슬롯 불일치를 보고합니다. `status=PASS`와 `catalog_coverage.selectable_goals=181`이 정상 seed의 기대값입니다. 쿠팡의 화면 이동·확인 후 조작·직접 진행 안내 구분은 [실행 문서](tasks/coupang.md)를 따릅니다. 이 감사는 DB를 변경하지 않고 Jev 호출이나 실기기 조작도 수행하지 않습니다. 세부 결과는 [AI2 감사 안내](../AI-Agent/src/ai_agent/graph_proposal/README.md#db-기록-처리)를 따릅니다.

`process`는 세션별 분석을 암호화된 DB 결과에 저장합니다. `assess-jev`는 여러 세션을 읽어 최신 보고서를 계산하며, 기본 출력은 쉬운 한국어입니다. `--format json`은 점수 구간·기준값별 표와 검수 대기 목록을 포함합니다. 자동 파일 저장은 하지 않습니다. 파일을 보관할 때도 근거의 동의·보존 기간을 따릅니다.

검수 파일 형식은 `ai2-jev-reviews.v1`입니다. 아래 `...`에는 보고서 `review_queue`가 준 해시를 그대로 넣습니다. 그대로 실행하는 fixture가 아닌 형식 설명입니다.

```json
{
  "schema_version": "ai2-jev-reviews.v1",
  "revision": "review-1",
  "records": [{
    "event_id": "captured-event-id",
    "decision_hash": "...",
    "screen_hash": "...",
    "target_hash": "...",
    "label": "correct",
    "reviewer": "reviewer-id",
    "review_revision": "1",
    "evidence_refs": ["approved-capture-id"],
    "split": "holdout",
    "group_id": "independent-case-1"
  }]
}
```

`label`은 `correct`/`incorrect`/`unknown`입니다. 같은 세션이나 검수 그룹을 서로 다른 split에 나누면 거부합니다. 전후 비교는 양쪽에 같은 holdout 사례가 하나씩 있어야 하며, 모델·코드·기준값을 식별할 수 있어야 합니다. 화면이 다르거나 합성 자료뿐이면 `NEEDS_DATA`입니다.

비교가 가능해도 결과는 `REVIEW_REQUIRED`입니다. 대상 선택 검수만으로 새 조작의 실제 성공을 만들어 내지 않습니다. 바뀐 행동은 새로 실행한 결과가 필요합니다. 기준값 표도 검수한 표본에서의 계산이므로 운영 전체로 일반화하거나 자동 배포하는 근거로 사용하지 않습니다.

## 개선 작업에 연결하기

| 보고서에서 발견한 일 | 다음에 확인할 곳 |
| --- | --- |
| 검수에서 맞는 대상인데 낮은 점수로 보류 | 원본 점수와 보정 점수 중 어디에서 기준 미달이 생겼는지 확인합니다. |
| 높은 점수인데 검수에서 대상 오답 | 화면 문맥, 후보 구성, 대상 식별 정보를 확인합니다. |
| 대상은 맞는데 조작 실패 | 실제 조작·관측 시점·설정 반영·완료 검증을 확인합니다. |
| 같은 단계에서 여러 번 보류 | 재관측이 새 근거를 줬는지, 복구 한도와 사용자 도움 전환이 작동했는지 확인합니다. |

이번 검증은 통제된 Jev 응답과 합성·독립 검수 fixture로 코드 동작을 확인합니다. 실제 운영 정답률 개선 수치를 주장하려면 별도의 검수 및 실기기 실행 자료가 필요합니다.
