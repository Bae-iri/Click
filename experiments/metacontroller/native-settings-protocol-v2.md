# 실제 Android Settings 재비교 — 사전 프로토콜 v2

현재 `6292fa2` 계열 코드의 A=CURRENT와 B=MC-v0를 새 cohort에서 비교한다. 실제 Android Settings·접근성 관찰·native 실행기·현재 Gemini 플래너를 사용한다. 목표는 현재 두 정책의 완료·복구·호출 비용 차이를 기술하는 것이다. 모델 요청 전에 실제 실행 소스·APK·환경·모델·카탈로그·전체 일정을 해시로 고정한다. 학습된 UIAnchor reflector 전체 재현이나 중장년층 사용자 실험으로 표시하지 않는다.

## 이전 실행과 분리

v1의 36회·사전 기준·원자료·감사·요약·해시는 그대로 보존한다. v2에는 공통 제목 증거 수정, 선택적 복구 context, 서버가 제공하는 실행 capability 제한이 포함된다. capability는 A/B 모두에 제공하고 B의 context는 실제 재관찰 이후에만 생성한다. 미처리 native dispatch를 복구 정책에 전달하는 기능과 같은 화면의 원래 조작을 다시 허용하는 정책은 변경하지 않는다.

v2는 안내가 실패·직접 입력·불가 상태로 끝나도 독립 관찰을 공통 30초 창까지 유지한다. 공동 성공을 관찰하면 그 시각에 끝낼 수 있다. 이 관찰 방식은 v1의 이른 종료와 다르다. v1의 공동 성공 0건과 현재 결과를 나란히 기술할 수 있지만 차이를 특정 수정 하나의 인과 효과로 배분하지 않는다. 안정 도달·도달 시각은 관찰 기회가 달라 직접적인 정책 개선 근거로 쓰지 않는다.

## 고정 행렬과 준비

같은 여섯 목표 `settings_display`, `settings_sound`, `settings_accessibility`, `settings_bluetooth`, `settings_datetime`, `settings_language`에 정상·첫 유효 TAP 수락 후 무효·첫 유효 TAP의 native dispatch 5,500ms 지연을 적용한다. 각 조건에서 A/B를 한 번씩 실행해 **36회·18쌍**이다. 쌍별 순서를 교차 배치한다. 정상 12회를 먼저 수행하며 이 원본을 전체 36회에 그대로 포함한다. 좋은 결과를 고르기 위한 정상 재실행이나 과제 교체는 하지 않는다.

모델 없이 다음을 확인한 뒤 전체 manifest를 빈 실행 조건 `[]`로 고정한다.

1. 계정 없는 격리 에뮬레이터, 영어 UI·한국어 목표, 같은 app/SDK/locale/정답 버전에서 안정된 Settings 홈을 확보한다.
2. 각 목표에서 홈의 음성 대조와 공개 Intent·실제 GUI 경로의 양성 대조, 독립 목적 상태 700ms 안정 확인을 통과한다. 목적 Intent는 준비에만 쓰고 측정 도구로 제공하지 않는다.
3. 같은 실제 화면의 공개 native 탐색 수락, 다른 화면·창 및 보호 입력 화면의 거절과 계측한 설정값 불변을 확인한다. 보호용 test APK는 두 번째 성능 평가 앱으로 세지 않는다.
4. A/B 시작 정합성은 창 ID나 노드 경로 대신 공개 라벨·리소스·역할·좌표·네이티브 상태의 의미 지문과 동일 `measurement_context_key`로 대조한다. 실행기의 창·신선도·대상 검사는 유지한다.

준비·manifest·에피소드는 `click.native-settings.v2`, guard는 `click.native-settings-guard-readiness.v2`를 사용한다. 공통 측정 개정은 `equal_independent_observation_window_v2`이며 context 지문에 결합한다. 출력은 `files/settings-meta-v2`와 새 검토 디렉터리다. 여섯 목표와 독립 판정은 사전에 확정된 같은 카탈로그를 사용한다. 지원되지 않는 환경이면 사유를 남기고 모델 결과를 본 뒤 정답을 바꾸지 않는다.

## 조작·대기·종료

에피소드 예산은 실제 30,000ms다. 모델 대기·native 실행·복구·완료 관찰을 포함한다. 조작 승인은 스크립트로 제공하지만 허용된 공개 탐색에 한정한다. 설정값·토글·입력·계정·인증·권한·제출을 변경하지 않으며 사용자 최종 확인/DONE를 대신하지 않는다.

무효·지연은 첫 유효 native TAP에서만 적용한다. 지연은 앱 렌더링 지연과 구분한다. 실제 TAP까지 가지 못한 시행도 배정 분모에 남긴다. 지연 예약과 실제 dispatch 수락을 각각 기록하고, 예약 후 native 검사에서 거절되면 실현된 장애 노출로 세지 않는다.

실제 접근성 이벤트만 Controller의 화면 이벤트로 전달한다. 주기적인 독립 판정 자체를 화면 이벤트로 세지 않는다. 미처리 예약이 있는 동안 추가 native 조작 승인을 막지만 현재 B의 재계획 정책 자체는 바꾸지 않는다.

공동 성공 전에는 terminal 표시 상태나 거짓 검증 발견만으로 관찰을 일찍 끝내지 않는다. 독립 관찰과 현재 검증 제시의 평가는 공통 예산까지 유지한다. 거짓 검증·설정값 변경·승인 없는 조작은 즉시 안전 사건으로 기록하고 다음 단계 진행을 멈춘다. 별도 안전 조치로 조기 중단하면 그 이유와 짧아진 관찰을 계측 한계로 명시하고 정상 30초 시행처럼 분석하지 않는다.

예산 이후 예약 조작과 공급자 callback 정리는 별도 시간으로 기록한다. 예산 후 도달이나 검증을 예산 내 공동 성공으로 올리지 않는다. `goal_present_after_cleanup`는 정리 뒤 목적 상태의 존재이며 최초 도달 시각이 아니다. 정리 시 판정이 불명확하면 null과 별도 oracle 상태를 남긴다.

## 지표와 불명확 값

주 지표는 **예산 안에 독립 목적 상태가 700ms 안정되고, 현재 유효한 앱의 자동 완료 검증이 있으며, 미처리 native 조작이 없는 공동 성공**이다. 과거에 제시됐다가 철회된 검증을 나중의 화면과 결합하지 않는다. 다음 시각을 별도로 기록한다.

- `first_independent_stable_goal_ms`: 독립 목적 상태의 첫 안정 확인 시각.
- `first_runtime_verified_ms`: 실제 `verified` 제시가 처음 나타난 시각. 일반 `confirm_result` 질문은 검증 제시가 아니다.
- `ms_to_joint_success`: 현재 목적 안정·현재 검증·예약 정리가 함께 성립한 시각.

첫 안정 도달과 `ever_independent_goal_stable`, 현재/과거 검증 제시, 종료 시 목적 상태는 구분한다. 첫 시각·공동 시각과 ever 표시는 측정창 안에서만 기록한다. 실제 종료 시각의 초과분은 보존하지만 예산 후 상태는 별도 cleanup 필드로 남긴다. 최초 시각·공동 시각이 서로 모순되거나 공동 성공 없이 예산 전에 관찰이 끝난 경우를 계측 문제로 표시한다.

`oracle_samples`, `oracle_known_samples`, `oracle_unknown_samples`는 예산 안에 끝난 독립 판정 횟수이며 합계가 일치해야 한다. `last_oracle_sample_ms`는 그중 마지막 시각이다. 최종 목적 상태도 마지막 예산 내 판정을 사용한다. 불명확 관찰은 안정 확인을 끊고 알려진 음성으로 바꾸지 않는다. 일시적 불명확 횟수와 비율을 공개하며, 알려진 안정 구간에서 성립한 성공을 소급 취소하지 않는다. 최종 정답이 불명확하거나 전체 측정 관찰이 불명확한 시행은 미평가로 남긴다.

거짓 검증은 알려진 음성 상태에서 실제 검증 제시가 존재한 경우다. 안정 시간을 기다리는 양성이나 판정 불가를 거짓 검증으로 세지 않는다. 판정 불가에서 제시한 검증은 별도 기록한다.

실패·공급자/모델 오류·허용 범위 밖 제안 거절을 36회 배정 분모에서 제외하지 않는다. 미실행·불명확은 예정·실행·평가 가능 수와 성공률 범위에 드러낸다. 실패 포함 시간은 성공 시 공동 시각, 나머지는 공통 30초로 한다. 성공한 양팔만의 시간은 별도 기술 통계다.

## 직접 요청 감사와 단계 진행

클라이언트와 서버 terminal을 정확한 요청·작업 해시로 결합한다. 서비스 전 0회, 확인된 모델 시도, 불명확을 구분한다. HTTP 거절 후에도 이미 수행한 모델 시도는 포함한다. 호출 수는 토큰·청구 금액과 구분한다. 프레임 시각과 관찰 신선도는 변환하지 않는다.

전송 형식이 같은 native facade v1 terminal은 사용할 수 있으나 에피소드·감사·요약의 v1/v2 cohort를 혼합하지 않는다. 감사 출력은 `click.native-settings-provider-audit.v2`, 요약은 `click.native-settings-summary.v2`다. v1 입력의 출력과 사전 판정은 바꾸지 않는다.

복구 context와 capability의 전달 여부는 공급자 진단의 제한된 플래그·개수로 확인한다. 정확히 결합된 `observed` 1회 시도와 유효한 true 플래그가 함께 있을 때 기술적 전달 근거로 집계한다. 불명확 호출이나 빠진 진단을 전달 완료로 간주하지 않는다. 이 근거는 모델의 주의·이해·효과를 입증하지 않는다.

정상 12회 후 준비·guard·대응 시작·oracle·시계·직접 결합·안전을 확인하고 남은 장애 24회를 같은 일정에 추가한다. 분류된 성능 실패만으로 자료를 버리지 않는다. 안전 사건이나 계측 문제라면 중단 이유와 미실행 배정을 공개한다. 모델 호출 전 고정한 코드·목표·정답·예산을 중간 결과에 맞춰 고치지 않는다.

## 판정 범위

현재 A/B의 공동 성공·장애 실현 쌍의 복구·실패 포함 시간·모델 시도를 함께 비교한다. B만 공동 성공한 실제 양팔 장애 노출 쌍이 있고 안전·계측이 통과하면 더 넓은 기술 검증을 검토할 수 있다. 노출되지 않은 조건을 복구 성공으로 표시하지 않는다.

단일 앱·한 번 반복·스크립트 승인의 결과로 일반성·통계적 우월·중장년층 효과·B 기본 적용 GO를 선언하지 않는다. v1과의 변화는 공통 수정·context/capability·관찰 방식·공급자 응답이 함께 바뀐 기술 비교다. 어느 변경이 얼마만큼 기여했는지는 이 설계로 분리하지 못한다.
