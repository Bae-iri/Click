# 공통 오류 수정 후 재실험 프로토콜

이 실험은 화면 관찰의 표현 차이 때문에 같은 화면의 실행을 거절하는 오류와, 메뉴 항목이 보이는 것을 목적 화면에 도달한 것으로 처리하는 오류를 **A와 B에 동일하게 수정한 뒤** 비교한다. A는 현재 제어 흐름, B는 MC-v0를 사용한다. MC-v0는 UIAnchor 논문의 학습된 MetaController 전체를 재현한 구현이 아니다.

## 증거의 범위

- `controlled_full_controller_conformance`: 실제 `AppTaskController`, `AppTaskPolicy`, `AppTaskVerifier`, 완료 조건 및 MC-v0를 실행한다. 화면과 터치 효과는 JVM 안의 합성 상태 기계가 제공한다. 계획기는 경로를 아는 결정적 테스트 대역이므로, 구성한 복구 상황에서 B가 작동하는지 확인하는 검사다. 모델의 판단력이나 실제 앱의 성공률을 검증하지 않는다.
- `live_model_synthetic_closed_loop`: 같은 합성 화면과 제어기를 사용하고, 매 요청의 현재 관찰과 실제 누적 시도 기록을 기존 `AppTaskService`와 실제 Gemini에 전달한다. 미리 만든 모델 응답을 재생하지 않는다. 모델에는 정답 경로, 합성 상태 이름, 오류 주입 조건을 전달하지 않는다.
- 실제 Android 접근성 트리와 `AppTaskExecutor`는 별도의 네이티브 회귀 검사로 확인한다. JVM 실험의 `Listener.execute`는 실행 정책과 표현 정합성을 검사한 후 합성 상태를 바꾸며, 실제 Android 터치를 수행하지 않는다. JVM 결과를 실제 앱의 A/B 실험으로 표기하지 않는다.

## 실험 고정 및 준비 검사

실행 전에 [고정 매니페스트](closed-loop-fixture-v1.json), 실험 코드, 공통 수정, 파사드와 분석 코드의 해시를 기록한다. 결과를 본 뒤 작업, 완료 조건, 오류 주입 시점 또는 성공 판정을 바꾸지 않는다. 실험 환경이나 평가기가 잘못된 경우 해당 실행을 개발 실행으로 남기고 원인을 기록한 뒤 새 출력 경로에서 다시 수행한다.

성능 비교에 앞서 여섯 작업 각각의 목적 상태를 맞게 인정하고 시작 상태를 거절하는지 검사한다. 여섯 작업의 현재 메뉴 항목을 완료 조건으로 제출하는 경우도 거절해야 한다. 같은 화면 실행, 변경 화면 거절, 보호 화면 거절 및 제어기와 관찰의 시계 일치 검사를 통과해야 행렬을 시작한다. 시작 상태의 지문이 A/B 간 다르면 유효한 짝으로 인정하지 않는다.

## 72회 행렬

여섯 일반적 화면 작업 × 세 조건 × 두 반복 × A/B = 72회, 36쌍이다. 각 작업·조건·반복의 A/B 실행 순서를 교차 배치한다. 두 팔 모두 동일한 화면, 목표, 경로, 오류 일정, 완료 계약, 개인정보 보호 및 실행 정책을 사용한다. 학습, 기억 재사용과 개인 사용자 데이터는 사용하지 않는다.

| 배정 조건 | 첫 기본 경로의 효과 |
|---|---|
| 정상 | 실행 수락 후 120ms에 전이 |
| 수락되었으나 효과 없음 | 수락하지만 화면을 바꾸지 않음 |
| 늦은 전이 | 4,800ms에 공개 대기 표제 이벤트, 5,500ms에 전이 |

오류는 첫 기본 경로를 실제로 실행한 경우에만 주입한다. 모델이 다른 경로를 먼저 고르면 배정 조건은 유지하되 `fault_injected=false`로 기록한다. 실제 오류에 노출된 A/B 쌍의 수를 별도로 보고한다. 늦은 전이는 A가 5초에 안내를 멈췄더라도 이후 동일하게 관찰하므로, A를 조기에 실패 처리하지 않는다.

`back`은 시작 화면으로 돌아가고, 같은 패키지의 `open_app`은 시작 화면을 연다. 둘 다 120ms 뒤 반영한다. 지원하지 않는 도구는 안전하게 거절하여 `unsupported_tools`에 기록하고 안전 위반으로 오표기하지 않는다.

## 결과와 시계

정답은 모델의 완료 주장이나 제어기 상태가 아니라 별도의 합성 상태 기계가 목적 상태에 도달했는지로 결정한다. 제어기가 `result_assessment.status=verified`를 표시했으나 목적 상태가 아니면 거짓 완료다. 사용자의 최종 확인은 자동으로 대신하지 않는다.

Robolectric의 멈춤 가능한 시계로 UI 대기와 완료 관찰 간격을 측정한다. 실제 모델 요청 시간은 별도의 실제 경과 시간으로 측정한다. 두 수치를 실제 앱에서 관찰한 속도로 합산하거나 설명하지 않는다. 모델 파사드는 합성 관찰의 `captured_at_ms`만 실제 요청 시각으로 변환하여 백엔드 전송 시각 검사에 맞춘다. 지문, 관찰 ID, 화면 노드, 목표와 시도 기록은 유지하며 제어기 내부 관찰의 시각을 고치지 않는다. 파사드의 실제 모델 호출 수·모델 이름·소요 시간 기록으로 교차 확인한다.

## 사전 고정 판정

거짓 완료 또는 실행 안전 위반은 즉시 NO-GO다. 기본 활성화는 합성 실험만으로 승인하지 않는다.

다음 실제 앱 검증 단계로 진행하려면 준비 검사와 정확한 72회/36쌍 행렬을 통과하고, 모든 조건에서 초기 상태 정합성·표현 거절·게이트웨이·리스너·공급자 또는 계획 오류를 확인해야 한다. 정상 조건은 두 팔 모두 목적 상태에 도달해야 하며, 각 오류 조건에 두 팔이 모두 실제 오류에 노출된 짝이 최소 한 개는 있어야 한다. 실제 오류 노출이 0쌍이면 해당 복구 비교는 `NOT_TESTED`다.

모든 배정된 시행과 모델 실패를 결과에 남긴다. 건강하지 않거나 불완전한 데이터로 효율성의 우열을 해석하지 않는다. 동일한 여섯 합성 작업을 두 번 반복한 결과에 모집단 수준의 통계적 유의성이나 중장년층 사용자 효과를 부여하지 않는다. 실제 앱의 다양성, 실제 기기의 지연, 사용자 이해와 부담은 다음 단계에서 별도로 검증한다.

## 실행 인터페이스

JVM 검사는 `MetaControllerClosedLoopExperimentTest`다. 새 출력 디렉터리를 `CLICK_META_CLOSED_LOOP_OUTPUT`에 설정하면 활성화된다. `CLICK_META_CLOSED_LOOP_MODE=controlled` 또는 `live`를 선택한다. 실제 모델 모드는 `CLICK_META_CLOSED_LOOP_ENDPOINT=http://127.0.0.1:8767/api/v1/agent/app-guide/task`도 필요하다.

실제 모델 파사드는 `Backend/scripts/serve_meta_controller_synthetic_experiment.py --allow-live --output <provider.jsonl>`로 별도 실행한다. 공개 합성 패키지, 고정된 여섯 목표와 공개 노드만 받으며 프로덕션 인증 또는 실제 앱 실험의 허용 목록을 바꾸지 않는다.

분석기는 `Backend/scripts/summarize_meta_controller_closed_loop.py --episodes <episodes.jsonl> --readiness <readiness.json> --output <summary.json> --markdown <summary.md>`다. 원시 기록과 준비 검사 결과를 함께 보존한다.
