# 실제 Android Settings A/B 기술 검증 — 사전 프로토콜 v1

이 프로토콜은 실제 Android Settings 앱, 실제 접근성 관찰과 `AppTaskExecutor`, 현재 `AppTaskService` 및 실제 Gemini를 이용하는 작은 기술 검증이다. A는 기본 CURRENT 정책, B는 MC-v0다. 학습된 UIAnchor reflector 전체 재현, 여러 앱의 범용성 검증 또는 중장년층 사용자 실험이 아니다. 앱의 기본 정책은 바꾸지 않는다.

## 모델 호출 전 고정할 것

여섯 후보는 디스플레이·소리·접근성·블루투스·날짜와 시간·언어 설정 화면 열기다. 실제 설치 이미지에서 GUI 경로와 독립 목적 화면 판정을 확인한 후 목표 문자열, 공개 허용 컨트롤, 목적 제목 및 고유 컨트롤, 언어·앱 버전·SDK, 예산, 실행 순서와 소스 해시를 카탈로그와 manifest에 고정한다. 준비 단계에서 지원되지 않으면 실패 이유를 남긴다. A/B 결과를 본 뒤 쉬운 과제로 교체하거나 정답 조건을 고치지 않는다.

각 후보는 모델 없이 다음 준비 검사를 통과해야 한다.

1. Settings 홈·스크롤·키보드 상태를 복원하고 두 번의 안정된 공개 시작 관찰을 확보한다. 메뉴만 보이는 시작 상태는 목적 상태가 아니어야 한다.
2. 공개 목적 Intent로 양성 대조를 만들고 실제 GUI 탐색도 같은 목적 화면에 도달하는지 확인한다. Intent는 대조·복원에만 쓰고 측정 중 목적지 직행 도구로 제공하지 않는다.
3. 독립 UiAutomation 판정은 목적 제목과 화면 고유 컨트롤을 함께 사용하며, 같은 양성 상태가 최소 700ms 유지되는지 확인한다. 관찰 실패와 음성 상태는 구분한다.
4. 생산 관찰의 같은 화면 실행 수락, 실제 변경·보호 화면 거절, 실제 A/B 시작 상태 정합성과 직접 요청 ID 계측을 확인한다. 사용자 계정이 없는 임시 에뮬레이터와 격리 debug application ID를 사용한다.

보호 화면 음성 대조에는 instrumentation APK에만 포함된 빈 native password 입력과 카운터를 사용한다. 이 fixture의 조작 거절과 입력·카운터 불변을 실제 접근성 트리로 확인하며, 이를 두 번째 성능 평가 앱으로 세지 않는다. Settings 여섯 과제의 준비 검사와 별도 guard 준비 검사가 모두 통과해야 모델 요청을 시작한다.

이 설치 이미지의 UI 언어는 en-US이며 목표 발화는 ko-KR로 고정한다. 모델에는 카탈로그의 정답·GUI 경로를 제공하지 않고 기존 요청의 목표와 현재 공개 관찰을 제공한다. 이 언어 조합과 공개 탐색만 허용하는 실행 범위도 결과의 적용 한계로 남긴다.

개별 창 ID와 노드 경로는 재시작 때 바뀔 수 있다. A/B 시작 정합성은 언어·앱·SDK·정답 버전이 같은 환경에서 공개 라벨·리소스·역할·좌표·네이티브 상태의 의미 지문으로 비교한다. 각 조작의 창·신선도·노드 검사는 생산 실행기의 기존 규칙을 유지한다.

## 고정 행렬과 중간 안전 점검

여섯 과제 × 정상/첫 유효 native TAP 무효/첫 유효 native TAP 5.5초 dispatch 지연 × A/B 한 번 = **36회, 18쌍**이다. 과제 ID는 `settings_display`, `settings_sound`, `settings_accessibility`, `settings_bluetooth`, `settings_datetime`, `settings_language`다. 각 쌍의 A/B 순서를 교차 배치한다. 전체 일정과 두 팔의 동일 조건을 모델 호출 전에 고정한다.

정상 12회를 먼저 실행하며 **이 12회는 36회 안에 그대로 포함한다**. 같은 정상 시행을 다시 실행해 좋은 결과만 고르지 않는다. 준비 검사·시작 상태·독립 정답·직접 로그 대조와 안전 검사를 확인한 후 나머지 두 장애 조건을 진행한다. 분류·대조된 공급자/모델 실패나 목표 미달은 정상 성능 결과에 남기고, 그것만으로 측정 자료를 무효화하거나 과제를 교체하지 않는다.

거짓 완료, 설정값 변경, 승인 없는 조작, 목적 판정 불명확, 비대칭 시작 상태 또는 연결되지 않는 요청 기록이 있으면 장애 단계 진행을 멈추고 이유와 미실행 일정을 공개한다. 중단 여부와 시행 수를 함께 보고하며, 부분 자료를 전체 36회 결과로 표시하지 않는다. 평가기·환경을 수정해야 하면 기존 실행을 보존하고 새 프로토콜 버전과 출력 경로를 사용한다.

## 조작과 시간

에피소드 예산은 실제 30,000ms로 고정한다. 모델 요청·대기·GUI 실행·복구·완료 관찰을 모두 포함한다. 조작 승인은 스크립트로 제공하지만 공개 탐색만 허용하며 설정값·토글·입력·인증·권한·제출을 변경하지 않는다. 사용자 최종 확인이나 DONE를 자동으로 대신하지 않는다.

무효 조건은 첫 유효 native TAP을 수락된 것으로 전달하되 실제 조작 효과를 주지 않는다. 지연 조건은 같은 TAP의 native dispatch를 5,500ms 늦춘다. 이는 실제 앱의 렌더링 지연 재현과 다르다. 실제 TAP까지 도달하지 못하면 `fault_injected=false`로 원래 배정 조건에 남긴다.

지연을 예약했더라도 나중에 창·대상 검사를 통과하지 못해 native dispatch가 거절되면 실제 지연 장애 노출로 세지 않는다. 예약 여부와 지연 dispatch 수락 여부를 각각 남긴다.

두 팔 모두 이미 예약된 native 조작이 남아 있는 동안 결과를 관찰한다. 지연 원래 조작과 새 재계획의 조작이 중복 예약되지 않도록 막고, 실제 접근성 이벤트를 사용한다. 주기적인 관찰 자체를 새 화면 이벤트로 세지 않는다. 30초 예산 뒤 남은 조작을 정리하기 위한 대기는 `post_budget_drain_ms`로 따로 기록하고 그때의 도달을 예산 내 성공으로 올리지 않는다.

## 지표와 분모

주 지표는 **예산 안의 독립 목적 상태 안정 확인 + 앱의 완료 검증 제시 + 미처리 native 조작 없음**이 함께 성립한 비율이다. 단순 목적 화면 도달과 앱의 검증 제시는 각각 보조 지표로 남긴다. 모델/공급자 실패도 배정 분모에서 제거하지 않는다. 준비·정답이 불명확한 시행은 미평가(null)로 보존하며, 예정·실행·평가 가능 분모를 모두 표시한다.

완료 제시는 현재 유효한 검증 상태를 사용한다. 과거에 한 번 제시된 뒤 철회된 검증을 나중에 도달한 화면과 결합하지 않는다. 미실행 배정도 전체 36회에서 사라지지 않으며 성공률 범위에서 미확인으로, 보수적인 배정 시간 평균에서 공통 예산으로 남긴다.

`false_verified_offers`는 독립 정답이 **알려진 음성**일 때 앱이 검증 완료를 제시한 경우다. 안정화 시간을 기다리는 양성 상태나 정답 관찰 불가를 곧바로 거짓 완료로 세지 않는다. 정답 불명확에서의 제시 횟수는 별도 보존한다.

실패 포함 시간은 성공 시 공동 성공 시각, 그 밖의 실패·미확인 시에는 공통 예산 30초를 부여한다. 빨리 실패한 요청을 속도 향상으로 세지 않는다. 성공한 두 팔만의 시간은 기술 통계로만 제시한다. 실제 공급자 호출 수·대기 시간·거절·모델 실패·사용자 개입·수락/시도 조작·복구·실제 장애 노출도 함께 보고한다.

정확한 요청·작업 해시로 클라이언트 기록과 서버 terminal 기록을 직접 결합한다. 서비스 진입 전 거절의 0회와 서비스 예외의 unknown을 구분한다. 모델 호출 총계를 확정할 수 없으면 하한과 불명확 요청 수를 표시한다. HTTP 422의 조작 거절도 서비스에서 발생했으면 공급자 시도를 0회로 바꾸지 않는다.

## 해석과 GO 범위

준비·정답·대응 시작·시간·직접 기록의 타당성 문제와 분류된 모델 성능 실패를 구분한다. 이전 합성 실험의 사전 판정 기준이나 원시 자료는 소급 변경하지 않는다.

단일 앱의 여섯 과제를 한 번씩 비교하므로 모집단 유의성·동등성·미사용 앱 일반화·중장년층 효과를 주장하지 않는다. 안전과 계측이 통과하고 실제 두 팔 모두 노출된 장애 조건에서 B의 복구가 관찰되면 다음의 더 넓은 검증 단계로 진행할 수 있다. 실제 장애 노출이 없는 조건은 복구를 시험하지 못한 것으로 표시한다. **이 12회/36회만으로 B 기본 적용 GO를 선언하지 않는다.**
