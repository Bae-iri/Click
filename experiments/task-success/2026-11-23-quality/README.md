# CLICK 범용성·속도·정확도와 실패 처리 평가

2026년 11월 23일의 `develop` 커밋 `5dd53e6`에서 실행했다. **첫 보완 대상은 사용자가 말한 변경 방향이다.** “새 방송이 저절로 내려받아지지 않게 해줘”에 대해 실제 서버가 자동 다운로드가 켜진 화면을 완료 후보로 반환했다. 목표를 반대로 저장하면 화면을 정확하게 읽어도 사용자 요청과 어긋난다. 이 사례의 관측 지점은 서버의 결과 확인 응답이다. [실험 설계](protocol.md) · [48개 API 응답의 판정과 시간](api-results.json)

## 어디까지 범용적인가

빈 SQLite DB에 정식 그래프를 로드해 카탈로그 v2.6.0의 139개 항목을 전수 확인했다. 정형 요청으로 선택할 수 있는 그래프는 **119개**였다. Android 설정 111개와 쿠팡 8개로, 119개 중 93%가 설정이다. 정부24의 공개 화면 안내 7개와 분류 전용 13개는 다른 경로를 사용하거나 분류까지만 지원한다. 그래프 선택은 기기에서 해당 과제를 완수했다는 증거와 구별한다. [선택기 실행 결과](api-results.json)

CLICK은 그래프에 등록하지 않은 앱에도 공개 Android 화면을 읽어 안내하는 경로가 있다. 기존 Galaxy Note20 시험에서 새 탐색 과제 13개를 Qwen 연결 상태로 두 번씩 실행했다. 목표에 도착한 것은 **19/26**, 도착하고 CLICK이 정확히 확인한 것은 **12/26**이었다. 도착한 7회에서 확인이 빠졌고, Chrome 검색창은 실제 주소 입력칸을 열기 전에 두 번 완료 처리됐다. 앱별 도착과 완료 확인을 따로 재야 하는 이유다. 이 수치는 해당 시험 버전의 기기 기록이다. ## 이번 갤럭시 설정 실험

Galaxy Note20(SM-N981N, Android 13)에 같은 소스의 독립 진단 APK를 설치했다. 세 설정 화면에서 정답은 Android 전경 Activity로, CLICK의 확인은 컨트롤러가 내보낸 기기 검증 이벤트로 판정했다. 실행기의 수락 여부와 도착 시점은 시험으로 통제했다. 각 행의 시간은 승인 시점부터이며 중앙값이다. [18개 개별 시행](galaxy-settings.json)

| 상황 | 실제 도착 | CLICK의 완료 확인 | 사용자에게 먼저 보인 반응 |
| --- | ---: | ---: | --- |
| 정상 도착 | 3/3 | 3/3 | 1.52초에 완료 확인 |
| 예측한 중간 화면을 건너뛰고 도착 | 3/3 | 3/3 | 1.56초에 완료 확인 |
| 5.8초 후 이동을 시작해 도착 | 3/3 | 3/3 | 5.34초에 사용자 확인 요청, 7.36초에 기기 완료 확인 |
| 화면 변화 없음 | 0/3 | 0/3 | 5.40초에 사용자 확인 요청 |
| 다른 설정 화면으로 이동 | 0/3 | 0/3 | 2회는 확인 요청, 1회는 8.5초 관측 끝까지 화면 대기 |
| 실행기가 즉시 거절 | 0/3 | 0/3 | 0.09초에 사용자 확인 요청 |

도착 9건을 모두 확인했고 미도착 9건에서 거짓 완료는 0건이었다. 18건 모두 실행기를 한 번만 불렀다. 중간 예측이 빗나가도 최종 상태를 확인한 점은 강점이다. 늦게 도착한 3건에서는 사용자가 기다리면 해결될 상황에 먼저 도움 요청을 받았다. 사용자 최종 확인 버튼을 누른 횟수와 실제 사용자 참여는 모두 0이다.

**시계 앱 이탈은 별도의 실패 유형이었다.** 정상 이동은 탭 1회 후 616ms에 확인했다. 설정으로 잠시 이동했을 때에는 CLICK이 완료나 다른 조작을 제시하지 않고 기다렸다. Android ‘뒤로’를 한 번 누른 후 4초 동안 공개 스톱워치 화면이 돌아오지 않아 복귀 시험은 실패했다. 같은 시험을 한 차례 더 추적했을 때도 설정에서 다른 전경으로 이동했고, 시험의 관측 창이 끝날 때까지 시계가 돌아오지 않았다. 마지막의 시계 전경은 시험 정리 코드가 시계 앱을 다시 여는 구간과 겹친다. 이 경우에는 실제 복귀 뒤 컨트롤러가 얼마나 빨리 재개하는지 측정할 수 없다. [전경 추적](clock-trace.json) · [원 시행과 재시도](device-runs.json)

초기 설정 시험은 전경 Activity를 읽지 못하고 중단됐고 초기 시계 시험도 전경 대기에서 중단됐다. 갤럭시가 깨어 있고 잠금이 풀린 것을 확인한 뒤 다시 실행했다. 명시적으로 시계 앱을 앞으로 가져오는 추가 진단용 APK도 빌드했으나, 설치 전 USB 연결이 끊겨 그 조건은 미실행이다. [기기 시행 기록](device-runs.json)

완료·복구 관련 Backend 테스트 151개와 Android JVM 테스트 42개가 통과했다. JVM에서는 외부 창이 사라지고 목표 창이 다시 주어지면 기존 작업이 중복 실행 없이 재개되는 사례도 통과했다. 실제 갤럭시에서 ‘뒤로’ 눌렀을 때 어느 앱이 오는지는 별도의 기기 측정값이다.

## 같은 기록으로 시험한 속도 보완안

정답과 오답을 모두 수집한 후, **요청한 상태와 정반대인 탭·스위치를 기기가 이미 보여주는 경우**의 결과 확인을 모의 실행했다. 규칙은 명시적 요청에서 로컬로 만든 조건, 같은 앱의 최신 공개 화면, 이름이 유일한 네이티브 요소에만 적용했다. 기능은 읽기 전용 결과 확인을 ‘아직 미충족’으로 끝낸다. 목표 조건 또는 화면 근거가 모호하면 원래 서버 응답을 사용한다. [재현 코드](shadow.py)

화면 32개 중 오답 6개가 이 규칙에 걸렸다. 원래 API에서는 6회 모두 Qwen을 호출했고 응답 중앙값은 **1.57초**였다. 모의 실행에서 32건의 정답 수는 **27→27**, 거짓 완료는 **1→1**이었다. 중복 항목·OCR·오래된 관찰·다른 앱·모델이 추론한 조건 등을 포함한 경계 사례 11개도 의도한 대로 처리했다. 운영 도입 시 기대할 수 있는 것은 이 조건에서의 호출 생략이다. 사용자가 실제로 몇 초 빨라지는지는 기기 A/B에서 측정해야 한다.

## 보완 순서와 다음 검증 기준

1. **끄기·부정·복합 요청의 방향을 먼저 지킨다.** 사용자의 원문에서 대상과 원하는 최종값을 독립적으로 확인한 뒤 모델이 만든 각 조건과 대조한다. 조건이 반대이거나 사라졌다면 동작 제안 전에 “보관함을 열고 자동 다운로드를 끌까요?”처럼 결과를 한 번 확인한다. 한 조건을 수동으로 넘겨도 나머지 조건만으로 전체 완료를 표시하지 않는다. 검증 세트에는 같은 화면에서 켜기와 끄기, “받고 싶지 않아”와 “끄지 마”, 복합 요청과 중간 상태를 짝지어 넣는다. 잘못된 방향의 행동 제안과 완료 후보를 각각 0건으로 요구하고 과도한 보류도 함께 센다.
2. **다른 앱에서 같은 목표를 검증하는 근거를 늘린다.** 검색창은 입력 포커스와 편집 가능한 필드를, 탭은 같은 탭 그룹에서 선택된 항목을, 복합 목표는 요청한 상태 전부를 확인한다. 우선순위는 기존 기기 시험에서 도착·확인이 갈린 갤러리와 Play 스토어, 미도착 상태에서 완료를 표시한 Chrome이다. 앱별로 이동 전의 유사 화면과 이동 후의 실제 화면을 한 쌍으로 두고, 제조사나 앱 버전이 다른 기기를 추가한다. ‘도착’, ‘기기 확인’, ‘거짓 완료’의 분모를 각각 보고한다.
3. **반복 호출과 조기 인계를 줄인다.** 읽기 전용 확인에서 명시적 목표와 네이티브 상태가 정반대인 경우, 위 모의 규칙을 기기 A/B에 올린다. 실행기 거절에는 즉시 다른 선택을 제시하고, 수락 뒤 화면 전환이 진행 중이면 같은 동작을 다시 보내지 않고 짧게 재관측한다. 앱 이탈 시에는 대상 앱 이름과 복귀 방법을 보여주고, 복귀가 실제로 관측된 뒤 기존 작업을 재개한다. 첫 안내 시간과 결과 확인 가능 시간의 중앙값·90백분위, 시간 초과, 불필요한 사용자 확인 횟수를 함께 기록한다. 거짓 완료가 늘거나 도착률이 떨어지면 채택을 보류한다.

후속 사용자 흐름 검증에는 저장소의 **37과제 × 표현 2개 × 시작 상태 2개** 계획을 사용할 수 있다. 사용자에게 결과가 실제로 보이는 시점과 CLICK의 완료 판정을 각각 기록하고, 다른 기기에서 같은 앱·표현 쌍을 반복한다. 이번 실험은 Galaxy 1대와 4개 합성 UI에서 시행했으며 사람의 만족도·전체 앱 성공률·배포 후 체감 개선은 측정 범위 밖이다. [148회 후속 설계](../2026-11-23/protocol.md)
