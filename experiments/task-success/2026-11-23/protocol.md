# 요청부터 사용자가 결과를 확인할 수 있는 화면까지

상태: **설계 확정안. 아직 실행하지 않음. 기존 하네스의 종료 조건 변경 필요.**

## 평가 질문과 종료점

“사용자가 요청한 목표 상태까지 안내했고, 사용자가 실제 화면에서 그 결과를 확인할 수 있는가?”를 평가한다. CLICK의 자동 완료 판정, ‘네, 됐어요’ 응답, 서버 `COMPLETED`는 주 지표의 조건으로 사용하지 않는다. 모델 응답이나 안내 버튼 제안만 나온 것도 성공이 아니다.

한 시행은 다음 세 조건을 모두 충족한 화면에서 끝난다.

1. **실제 목표 충족:** 제품의 완료 코드와 독립적인 기기 판정으로 목적 페이지·선택 탭·설정값 변화를 확인한다.
2. **사용자에게 보이는 근거:** 목표 제목, 선택 표시, 입력칸, 변경된 슬라이더·미리보기 등 과제별 증거가 실제 화면에 보인다. CLICK 패널·로딩·다른 창에 가려지면 아직 종료하지 않는다. 앱 내부 변수나 OS 값만 변하고 화면 근거가 없으면 통과하지 않는다.
3. **안정성:** 위 두 조건이 1초 이상 함께 유지된다. 영상 콘텐츠나 시계의 픽셀 전체가 정지할 필요는 없으며, 목표 제목·선택 표시 등 결과 근거가 유지돼야 한다. 잠깐 도착했다가 이동한 화면은 주 지표 성공으로 세지 않는다. 주 시각 `t_ready`는 이 유지 조건을 확인한 시각이다. 최초 도착 시각은 별도로 기록한다.

목표 충족과 가려지지 않은 근거가 처음 관찰되면 다음 탭·스크롤 승인을 잠시 보류하고 1초 유지 여부를 관찰한다. 앱 실행·화면 갱신 자체를 멈추거나 화면을 강제로 고정하지 않는다. 유지되지 않으면 안내 관찰을 재개한다. 충족 시 추가 승인을 중단하고 근거를 보존한다. 자동 완료가 먼저 표시돼도 그 신호를 성공 근거나 종료 조건으로 쓰지 않는다. 사용자가 화면을 읽고 판단하는 데 걸리는 시간은 재지 않는다. 이 실험으로 ‘사용자가 실제로 판단한 정확도·시간’을 주장하지 않는다.

## 대상과 표본

Galaxy Note20(Android 13) 1대. 실제 제품 경로로 **37과제 × 4조건 = 148회** 실행한다. 기기 1대의 반복 시행이며 사람 148명이나 서로 독립적인 사용자 표본으로 표현하지 않는다.

| 과제군 | 과제 수 | 과제당 조건 | 시행 수 |
|---|---:|---:|---:|
| 설정 페이지 이동 | 기존 20종 | 표현 2개 × 시작 상태 2개 | 80 |
| 설정값 변경 | 글자 크기·밝기·미디어 음량 각각 증가·감소, 6종 | 동일 | 24 |
| 시계 | 세계시각·스톱워치·타이머·알람, 4종 | 동일 | 16 |
| YouTube | Shorts·구독·검색창, 3종 | 동일 | 12 |

정확한 요청·시작 상태·종료 증거는 [tasks.json](tasks.json), 실행 순서는 [schedule.json](schedule.json)에 고정한다. 표현과 시작 상태를 함께 바꾸는 단순 4회 반복이 아니라 모든 조합을 한 번씩 실행한다. 표현은 공개된 시험 문장이므로 미공개 요청 일반화 성능으로 해석하지 않는다.

## 동일하게 유지할 실행 조건

- 모든 주 시행은 **CLICK 홈에서 텍스트 요청을 전송**해 시작한다. 대상 앱의 초기 상태는 준비 후 백그라운드에 두며, 측정 전에 목표가 이미 충족되지 않았는지 확인한다. 요청 접수 시각 `t0`를 앱의 단조 시계로 기록한다. 음성 인식 시간은 이번 범위에 없다.
- 설정·쿠팡은 등록 경로를 강제로 생략하지 않는다. 일반 앱도 제품이 실제로 인계하도록 한다. 실제 라우팅이 예상과 달라도 기록하며, 하네스가 정답 경로로 우회시키지 않는다. 지도 없는 설정 비교군은 이번 주 실험에서 제외한다.
- APK, 서버 배포 버전, 모델·제공자·신뢰도 기준, 기기·앱 버전을 시작 전에 고정하고 종료 때 다시 확인한다. 운영 서버로 측정하며 로컬 서버 결과와 속도를 합치지 않는다. 버전이 바뀌면 별도 블록으로 분리한다.
- 기본 수동 안내를 유지한다. 스크립트가 **실제로 표시된 제품 제안**을 500ms 뒤 승인·실행한다. 정답 판정기는 실행할 버튼을 고르는 데 사용하지 않는다. 표시가 없는 상태에서 정답 좌표를 직접 누르거나 정답 경로를 넣지 않는다. 승인 수와 고정 대기 시간도 기록한다. 사람이 참여한 사용성 실험으로 표현하지 않는다.
- 제품이 기본 제공하는 패널 접기 등 정상 조작은 허용하되 그 시간·횟수를 포함한다. 증거를 찍기 위해 패널을 강제로 숨기거나 앱을 목표 화면으로 직접 이동시키지 않는다.
- 과제와 무관한 내용 입력·전송·구매·알람/타이머 시작은 하지 않는다. 값 변경은 지정한 세 설정에만 허용하며 시행마다 복원한다. 실제 동작이 안전 허용 범위 밖이면 중단 사유와 제안 내용을 남긴다.
- 4라운드마다 37과제를 한 번씩 실행한다. 순서는 고정 시드 `20261123`으로 섞고 이웃 라운드 경계의 같은 과제 연속 실행을 피한다. 성공한 것만 재시도해 교체하지 않는다.
- 제한 시간은 요청부터 **75초**다. 오류·도움 요청·시간 초과·미실행 과제도 배정 148회에서 숨기지 않는다. 도구 오류는 별도 표시하고 수정 후 재시도는 원 시행과 연결해 별도로 보고한다. 도구 오류를 제품의 오선택이라고 해석하지 않는다.

## 과제별 사용자가 볼 수 있어야 하는 것

| 종류 | 독립 기기 근거 | 실제 화면에서 확인할 근거 |
|---|---|---|
| 설정 페이지 | 목적 페이지의 비동작 제목·패키지 | 같은 제목과 해당 설정 화면. 출발 메뉴의 같은 이름은 불충분 |
| 글자 크기 | OS 글자 배율이 요청 방향으로 변화 | 글자 크기 대상명과 미리보기·조절 위치 변화 |
| 밝기 | 밝기 값이 요청 방향으로 변화 | 밝기 슬라이더 위치 변화. 스크린샷 픽셀 밝기로 실제 패널 휘도를 측정했다고 주장하지 않음 |
| 미디어 음량 | OS 미디어 음량이 요청 방향으로 변화 | 미디어 대상명과 해당 음량 슬라이더 변화 |
| 시계·YouTube 탭 | 요청한 네이티브 탭/버튼의 실제 선택 상태 | 해당 탭의 선택 표시와 목적 화면. 버튼이 보이기만 해서는 불충분 |
| YouTube 검색창 | 활성 검색 입력 컨트롤 | 입력 가능한 검색창. 키보드는 목적 화면 증거를 가리지 않으면 허용 |
| Chrome 메뉴 | 같은 앱의 실제 메뉴 창과 미리 정한 공개 메뉴 구성 | 열린 팝업 메뉴 항목들이 식별됨. 메뉴를 여는 버튼만 보이는 것은 불충분 |
| Chrome 설정 | 설정 페이지의 제목과 고유 설정 항목 | 설정 제목과 설정 목록 |
| Chrome 새 탭 | 요청 전후 탭 생성/선택 변화와 새 탭 화면 | 새 탭이 활성화된 화면. 원래부터 열린 새 탭을 다시 보는 것은 불충분 |
| 쿠팡 카테고리 | 선택된 카테고리 탭 또는 독립 제목 | 카테고리 화면·목록과 선택 표시 또는 제목 |

각 종료 근거 영역을 사전에 지정한다. 제목·탭·컨트롤을 보고 목표 충족을 확인할 수 있어야 한다. SSID, 계정명, 주소, 검색 이력, 콘텐츠 제목 등은 수집하지 않거나 근거를 훼손하지 않게 가린다. 공개 메뉴·탭·조절 컨트롤 주변만 보존한다.

스크립트가 검출한 시점의 화면과 짧은 연속 프레임을 별도 검토한다. 검토자는 요청과 실제 화면 근거를 보고 `목표 충족이 보임 / 충족되지 않음 / 근거 부족`을 기록한다. CLICK의 완료 문구나 모델의 설명만으로 채점하지 않는다. 기기 판정과 화면 검토가 모두 긍정일 때만 주 지표 성공이다. 불일치·근거 부족은 별도 사유로 남기며 성공으로 올리지 않는다. 사람의 판단 능력을 비교하려면 별도 참여자 실험이 필요하다.

## 지표

| 지표 | 정의·분모 | 보고 |
|---|---|---|
| **목표 결과 화면 제시율** | 실제 목표 충족 + 화면 근거 + 1초 유지 + 화면 검토 통과 / 배정 시행 | 전체와 과제군별 n/N·% |
| **첫 유효 안내 시간** | `t0` → 실제 화면에 올바른 조작 안내가 처음 표시됨 | 중앙값·p95와 측정 n/N. 모델 응답 콜백 시간으로 대체 금지 |
| **결과 확인 가능 시간** | `t0` → `t_ready` | 성공 시행 중앙값·p95와 n/N. 실패는 성공률 분모에 유지 |
| 올바른 첫 안내 제공률 | 첫 안내가 올바르게 표시된 시행 / 배정 시행 | n/N. 안내가 없던 시행도 분모에 포함 |
| 관찰된 첫 조작 정확도 | 정답과 대조 가능한 첫 조작 중 올바른 것 | 조건부 n/N과 관찰 커버리지를 함께 표기 |
| 목표 도착률 | 독립 판정기가 도착을 관측한 시행 / 배정 시행 | 화면 제시율과 별도. 화면 가림·유지 실패를 포함할 수 있음 |
| 라우팅·호출·후보 추출 | Goal Type/앱 인계, 실제 모델 호출, 정답 후보 포함 여부 | 원인 분석용. 과제 성공과 합산 금지 |

첫 안내에는 눌러야 할 메뉴·탭, 스크롤 방향, 조절 대상 등 실행 가능한 정보가 있어야 한다. ‘처리 중’ 표시·앱을 정하지 못한 되묻기·잘못된 버튼 강조는 첫 유효 안내가 아니다. `onDraw` 진단 신호가 없으면 실제 표시 증거를 확인한다. 그 신호의 부재만으로 제품이 안내하지 않았거나 모델이 틀렸다고 단정하지 않는다.

`t_ready` 이후의 자동 완료 인식, 사용자 완료 버튼, 서버 요청 종료와 추가 반복 동작은 별도 연구다. 이번 속도·성공률에 섞지 않는다. 종료 후 생긴 정리용 요청 취소도 실패/성공 판정을 바꾸지 않는다.

## 시행 기록과 도구 변경

[trial-template.json](trial-template.json)에 새 필드 예시를 둔다. 핵심은 `passed`를 재사용하지 않고 `judgment_ready_success`와 `time_to_judgment_ready_ms`를 새로 기록하는 것이다.

기존 하네스는 `native_goal && verified_completion`을 기다린다. 새 실험 전 다음을 수정해야 하며, **기존 실행 명령만 다시 돌려서는 이 설계가 구현되지 않는다.**

1. 실제 텍스트 전송 시각과 첫 표시 시각을 연결한다. 인계 이후 컨트롤러 시작 시각을 요청 시작으로 쓰지 않는다.
2. 매 동작 승인 **전**에 독립 목표·가림·안정 조건을 관찰한다. 후보 구간에서는 다음 승인을 보류한다. 조건 충족 후 승인 중단, 근거 보존, 제품 세션 정리 순서로 종료한다. 완료 신호를 기다리지 않는다.
3. 목표 감지와 표시 여부·가림은 완료 판정 함수와 분리한다. Chrome 메뉴/새 탭, 값 변경의 증거 검출을 각각 점검한다.
4. 본 실험 전에 앱 5개 각각의 ‘이미 충족된 화면’과 ‘충족되지 않은 화면’으로 채점기 10건을 점검한다. 또한 요청 승인·안내 표시 계측이 작동하는지 확인한다. 제품 과제의 성공을 점검 통과 조건으로 삼아 쉬운 과제만 고르지 않는다. 점검은 주 분모에 합치지 않는다.

## 이전 결과와의 관계

11월 22일 자료의 `target_ever_reached`는 화면의 가림·안정·판단 가능성을 모두 검사한 값이 아니다. 이를 그대로 새 성공률로 이름만 바꾸지 않는다. 스톱워치가 6.82초에 도착한 기록은 후보 시각으로 참고할 수 있지만, 새 설계의 종료 근거를 재검토하기 전에는 ‘6.82초 성공’으로 발표하지 않는다. 예전 기록은 기존 정의로 보존하고 새 배포·새 분모·새 종료점을 명시해 다시 측정한다.
