# 사용자 요청에서 완료 확인까지의 실기기 실험

이 문서는 기존 측정의 정의를 보존한다. 다음 실험은 자동 완료 확인을 제외하고 [사용자가 결과를 확인할 수 있는 화면까지의 설계](../2026-11-23/protocol.md)를 따른다. 기존 도착 기록을 새 성공률로 재분류하지 않는다.

Galaxy Note20 한 대에서 설정, 삼성 시계, YouTube, Chrome을 시험한다. 비교 단위는 모델 응답 한 건이 아니라 사용자가 말한 과제 한 건이다. 앱 서버는 develop의 be25070c로 만든 로컬 인스턴스이며 전용 계정과 임시 DB를 쓴다. 그래프의 화면 선택기는 실제 Jev, 범용 안내의 외부 플래너는 OpenRouter의 qwen/qwen3.8-flash로 설정한다. 각 시행에서 실제 호출 여부는 응답 기록으로 확인한다.

| 조건 | 요청 | 진입점 | 예정 횟수 |
|---|---|---|---:|
| 등록 경로 | 디스플레이 설정 열기, 와이파이 설정 열기 | 일반 요청 큐와 설정 그래프 | 2종 × 2회 |
| 같은 과제에서 그래프 생략 | 위와 같은 문장 | 범용 앱 컨트롤러에 설정 앱과 목적을 지정 | 2종 × 2회 |
| 일반 앱 | 시계의 스톱워치·타이머 탭, YouTube의 Shorts·검색창, Chrome의 메뉴·설정 | 일반 요청 큐에서 제품이 직접 경로를 결정 | 6종 × 2회 |

각 회차는 대상 앱을 연 상태에서 시작한다. 이미 목적지이면 다른 탭이나 화면으로 돌아간 후 시작한다. 준비 과정에서 목적지를 벗어나지 못하면 준비 실패를 기록한다. 2회차는 과제 순서를 뒤집는다. 수동 승인에 필요한 클릭은 테스트가 대신한다. 일반 앱의 승인은 해당 앱에서 검사 대상인 탐색 컨트롤에만 허용한다. 두 회차는 같은 설치와 실험 계정을 공유한다.

## 측정 기준

1. 요청 해석에서 반환한 Goal Type을 기대값과 대조한다. 범용 요청은 전용 타입이 없어도 적절한 앱 컨트롤러로 인계되면 정상 라우팅으로 집계한다. 컨트롤러에 직접 넣은 비교군에는 해석 점수를 부여하지 않는다.
2. 플래너의 실제 호출, 실패 코드, 반환된 하위 목표를 기록한다. 계획의 내용은 요청의 대상과 동작을 보존하는지, 중간 상태와 마지막 상태가 실행 순서에 맞는지 읽어 판정한다. 응답 형식 통과와 계획 내용의 적합성은 따로 본다. 요청에 들어 있던 계획을 다시 반환한 턴은 새 계획으로 세지 않는다.
3. 첫 UI 선택은 사전에 정한 첫 메뉴나 요청한 탭과 대조한다. 와이파이는 설정 첫 화면의 ‘연결’도 적절한 첫 선택이다. 모델명이 기록된 실제 선택만 그 모델의 실적으로 센다. 선택 없음, 공급자 실패, 접근성 트리 부족은 오선택과 구분한다.
4. 설정은 시스템 화면 제목, 시계·Shorts는 선택된 탭, YouTube 검색은 검색창 리소스, Chrome 메뉴·설정은 목적 화면에서만 나타나는 컨트롤을 독립 판정기로 쓴다. 제품의 완료 신호와 독립 판정이 함께 있어야 성공이다. 도달 후 완료 누락, 거짓 완료, 제한 시간까지 미도달을 구분한다. 범용 안내는 독립 판정이 500ms 이상 유지돼야 한다.
5. 대기 한도는 75초다. 제품의 오류·도움 요청·시간 초과도 배정 분모에 남긴다. 모델이 답했지만 제품에서 적용되지 않은 경우는 성공으로 세지 않는다. 독립 판정기나 테스트 도구 자체가 깨진 경우 별도로 표시한다.

등록 경로와 범용 경로의 비교는 동일한 두 설정 과제에서 해석한다. 두 조건은 시작 지점과 클릭 승인 방식이 다르므로 경과 시간 차이를 그래프 단독 효과로 해석할 수 없다. 앱별 2회 반복의 결과는 이 기기와 지정한 과제에서 관찰한 값이다.

## 재현

프로젝트의 Android SDK와 Python 백엔드 의존성을 사용한다. Backend/.env의 실험용 Jev·OpenRouter 자격증명은 서버 프로세스에서 읽는다. 아래 명령은 저장소 루트 기준이며 서버와 중계는 각각 별도 터미널에서 실행한다.

```sh
study=experiments/task-success/2026-11-22
out=$(mktemp -d)
python Backend/scripts/serve_device_audit.py
python "$study/trace_proxy.py" "$out"
(cd Frontend && bash gradlew -PCLICK_CANDIDATE_DIAGNOSTICS=true -PCLICK_APPLICATION_ID=com.clueclick.taskstudy.deviceaudit -PCLICK_API_BASE_URL=http://127.0.0.1:8774 :app:assembleDebug :app:assembleDebugAndroidTest)
python "$study/run_device.py" --serial "$ANDROID_SERIAL" --output "$out" --apk Frontend/app/build/outputs/apk/debug/app-debug.apk --test-apk Frontend/app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
python "$study/jev_controls.py" --serial "$ANDROID_SERIAL" --output "$out/jev-controls.json"
```

Jev 단독 검사는 네 앱에서 접근성 트리를 새로 읽어 미리 정한 공개 메뉴 이름만 후보로 사용한다. 긴 콘텐츠 제목이나 계정 정보는 후보에 넣지 않는다. 화면에 정답이 있는 경우와 없는 경우를 분리하고, 후보가 두 개 미만인 화면은 판정 불가로 기록한다. 이 검사는 같은 모델에 표준화된 후보를 준 결과로, 본 실험에서 Qwen이나 기기 코드가 고른 버튼을 Jev가 골랐다고 간주하지 않는다.

## 설정 외 등록 경로 추가 검사

본 실험의 앱별 요청을 확장하기 위해 쿠팡 ‘카테고리 열어줘’를 두 번 추가한다. 카탈로그의 승인 경로는 `coupang.category.browse`와 `CP-category-browse`다. 일반 요청 큐로 시작하고 제품의 강조 표시가 쿠팡의 ‘카테고리’ 컨트롤과 겹칠 때 그 컨트롤만 누른다. 독립 판정은 카테고리 탭의 선택 상태 또는 클릭할 수 없는 네이티브 카테고리 제목을 요구한다. 제품이 반환한 기술적 열림 또는 검증된 이동 완료와 이 판정이 함께 있어야 통과다. 주 실험과 같은 명령에 `--cohort commerce`를 추가하고 별도 출력 경로로 중계를 실행하면 재현할 수 있다.

## 최종 요청 상태 추가 검사

주 실험의 성공 지점은 제품이 근거를 갖고 완료 확인을 제시하는 순간이다. 후속으로, 첫 회차에서 이 지점에 도달한 일반 앱의 두 과제(Chrome 설정, YouTube 검색창)를 새 실험 계정으로 한 번씩 다시 시작한다. 목표가 500ms간 유지되고 제품 확인이 있을 때만 실제 ‘네, 됐어요’ 버튼을 누른다. 같은 요청 ID를 서버에서 다시 읽어 `COMPLETED`를 확인한다. 재시행에서 버튼까지 못 가도 분모에 남긴다. 첫 회차에서 선정한 후속 검사이므로 주 실험의 성공률에 합치지 않는다. 재현 옵션은 `--cohort terminal`이다.

## 등록 경로의 첫 표시 조건 대조

초기 설정 실험은 첫 안내 표시 시간을 기록하는 빌드 옵션이 꺼져 있어 테스트가 자동 모드로 넘어갈 수 없었다. 수동 안내에서 시작하는 검사는 앱을 반드시 `-PCLICK_CANDIDATE_DIAGNOSTICS=true`로 빌드한다. 위 실행 명령에 `--cohort registered`를 추가하면 같은 요청과 순서로 등록 경로 네 건만 다시 측정한다. 시작부터 자동 모드를 켜고 같은 두 과제를 한 번씩 실행한다. 이 대조 실험은 별도 `--cohort auto`로 기록한다.

## 실험 중 추가된 Android 수정 재검증

비교 실험을 시작한 뒤 develop의 ad84ef51에서 선택된 네이티브 버튼을 목표 도착 증거로 허용했다. 기존 서버는 그대로 두고 이 커밋의 Android 앱을 별도로 빌드해, 앞서 두 번씩 도착 후 미완료였던 시계 스톱워치와 YouTube Shorts를 새 계정에서 각각 한 번 재실행한다. `--cohort arrival`을 사용해 서버 요청 종료까지 검사한다. 구 버전의 주 실험과 별도로 보고한다.

쿠팡 추가 2건에서는 올바른 Goal Type 확인 요청이 돌아왔지만 테스트가 구형 확인 화면만 승인해 실행을 시작하지 못했다. 이 2건의 최초 기록은 도구 실패로 보존한다. 서버 기반 요청 검토 화면도 승인하도록 도구를 고친 뒤 재검증 빌드에서 쿠팡 2건을 다시 수행한다. 집계에서 `routecheck`로 구별한다.

## 일반 앱의 앱 열기 승인 재검사

주 실험에서 Chrome 메뉴 두 건은 ‘앱 열기’ 제안에서 멈췄다. 수정한 큐용 시험 도구는 제안에 적힌 패키지가 과제의 대상과 일치할 때 앱 열기를 승인한다. 앱 안에서는 기존 탐색 버튼 목록을 적용한다. `--cohort app-entry`는 새 계정에서 Chrome 메뉴, YouTube 검색, YouTube 검색, Chrome 메뉴 순서로 검사한다. 제품 검증과 목표 화면이 일치하면 완료 버튼과 동일 요청의 서버 종료 상태도 확인한다. 이 네 건은 주 실험 집계와 별도로 기록한다.
