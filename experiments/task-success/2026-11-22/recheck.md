# 11월 23일 실기기 성능 정정

11월 22일 주 실험에서 설정 등록 경로 0/4를 제품 성능으로 보고한 결론을 철회한다. 실험 APK는 첫 안내 표시 시각을 기록하는 옵션이 꺼져 있었고, 시험 도구는 이 값이 있어야 다음 조작을 허용했다. 이전 실험의 2회차 Wi-Fi와 디스플레이에서는 Jev가 탭 대상을 반환한 단말 로그도 확인했다. 당시 화면에 안내가 실제 표시됐는지는 그 기록으로 판정할 수 없다. 주 실험과 별도로 처음부터 자동 모드를 켰던 두 건은 이 대기 조건을 거치지 않았고 모두 도움 요청으로 끝났다.

## 설정 등록 경로 네 건 재측정

실패한 세 건 모두 서버에서 작업 시작 응답을 받는 단계에서 막혔다. 이 서버 턴의 기본 시간 한도는 20초다. 계측은 시간 초과 안에서 모델 호출과 서버 내부 처리에 각각 얼마나 걸렸는지 보여주지 않는다. 성공한 한 건은 UI 후보가 없는 관찰 네 번에 이어 후보 한 개를 확보했다. Jev 1.14.0이 202ms에 그 항목을 선택했고 첫 강조 위치가 사전에 정한 디스플레이 항목과 맞았다.

같은 이름의 등록 과제는 앞선 실기기 행렬에서 디스플레이 2/2, Wi-Fi 1/2였다. 앞선 행렬은 두 번째 시행의 요청 표현과 설정 목록 시작 위치를 바꿨다. 이번 반복은 두 시행 모두 같은 문장과 초기 목록을 썼다. 기기 한 대에서 관측한 3/4와 1/4의 차이만으로 제품 버전에 따른 하락폭을 추정하기 어렵다. 이전 첫 회차 · 이전 두 번째 회차

## 앱 열기 승인 수정 후 추가 네 건

동일한 제품 소스에서 큐용 시험 도구가 요청한 앱의 패키지와 일치하는 ‘앱 열기’ 제안을 승인하도록 고쳤다. Chrome과 YouTube를 새 계정에서 과제당 두 번씩 실제 요청 큐로 실행했다. [재측정 단말 기록과 모델 응답](recheck-results.json)

| 순서 | 과제 | 기기에서 목적지 확인 | 제품 완료 확인 | 요청 종료 |
|---|---|---:|---:|---|
| 1 | Chrome 메뉴 | 35.15초 | 75초 이내 없음 | 미확인 |
| 2 | YouTube 검색창 | 9.23초 | 14.40초 | 14.96초에 서버 `COMPLETED` 확인 |
| 3 | YouTube 검색창 | 8.37초 | 48.05초 | 48.66초에 서버 `COMPLETED` 확인 |
| 4 | Chrome 메뉴 | 75초 이내 없음 | 없음 | 미확인 |

첫 Chrome 시행은 전용 ‘앱 열기’를 승인한 뒤 Android에서 메뉴 항목 ‘새 시크릿 탭’이 보였다. 이어 Qwen은 메뉴 버튼 탭과 뒤로가기를 제안했다. 도구는 뒤로가기를 승인하지 않았고 메뉴가 보이는 상태에서 제한 시간이 지났다. 두 번째 시행은 범용 컨트롤러가 `awaiting_screen` 상태에서 끝났다. 승인할 동작이나 Qwen 호출은 기록되지 않았다. 앱 열기 승인 누락은 이전 결과에 영향을 준 시험 조건이었고, 이를 고친 뒤에도 Chrome 요청 종료는 0/2였다.

YouTube에서는 Qwen이 두 시행 모두 ‘검색’을 골랐고, 독립 판정과 제품 확인을 통과한 뒤 ‘네, 됐어요’를 눌렀다. 두 번째 시행은 검색창 도착부터 제품 확인까지 39.69초가 걸렸다. 이 결과는 검색창 열기 과제에 해당한다. 두 실험 회차는 저장 상태를 공유했으므로 앱별 두 건을 독립적인 장기 성공률로 해석하기 어렵다.
