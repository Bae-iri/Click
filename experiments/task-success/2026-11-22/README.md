# 사용자 요청의 단계별 성공률

후속 실험의 종료점을 [사용자가 결과를 확인할 수 있는 화면까지](../2026-11-23/protocol.md)로 변경했다. 아래는 자동 완료 확인을 포함한 기존 정의의 결과이며, 새 설계의 측정값은 아니다.

2026년 11월 22~23일, Galaxy Note20(SM-N981N, Android 13)에서 설정·삼성 시계·YouTube·Chrome·쿠팡을 검사했다. 기기 한 대, 스크립트 승인, 로컬 격리 서버와 실제 외부 모델을 사용했다. 요청마다 OS 화면이 목표와 일치하는지와 CLICK이 검증된 완료를 제시하는지를 따로 판정했다. 후속 검사에서는 ‘네, 됐어요’ 버튼을 눌러 서버가 같은 요청을 종료하는지도 확인했다. [실험 설계와 재현 방법](protocol.md) · [시행별 결과와 모델 응답](results.json)

**11월 23일 정정.** 주 실험에서 설정 등록 경로 4건을 제품 실패로 집계한 결론을 철회한다. 당시 APK는 첫 안내 표시 시각을 기록하지 않았고 시험 도구는 그 시각을 기다려야 다음 조작을 실행했다. 원본 JSON은 당시 관측을 보존한다. [동일 과제 재측정 및 일반 앱 비교](recheck.md)

## 주 실험 20회

Android와 로컬 백엔드를 be25070c에 고정했다. 일반 앱 요청 12회 모두 사용자가 입력한 문장에서 시작해 범용 컨트롤러에 도달했다. 이 중 8회는 실제 목적 화면에 도착했고, 2회는 제품도 완료를 확인했다. 완료 확인에 성공한 Chrome 설정과 YouTube 검색창의 소요 시간은 각각 22.7초와 20.9초였다. 사용자가 화면을 읽고 판단하는 시간은 포함하지 않았다.

| 과제와 진입 조건 | 시행 | 실제 도착 | 도착과 제품 완료 확인 |
|---|---:|---:|---:|
| 설정의 등록 경로 · 디스플레이 / Wi-Fi | 2 + 2 | 판정 제외 | 판정 제외 |
| 동일한 설정 요청을 범용 안내에 직접 전달 · 디스플레이 / Wi-Fi | 2 + 2 | 2 + 2 | 0 + 2 |
| 시계 · 스톱워치 / 타이머 탭 | 2 + 2 | 2 + 2 | 0 + 0 |
| YouTube · Shorts / 검색창 | 2 + 2 | 2 + 1 | 0 + 1 |
| Chrome · 메뉴 / 설정 화면 | 2 + 2 | 0 + 1 | 0 + 1 |

‘도착’은 독립 판정기가 시행 중 한 번 이상 확인한 값이다. 범용 안내의 성공은 종료 시점에 목표 상태가 유지되고 CLICK의 근거 있는 결과 확인이 함께 관측된 경우다. 유효한 범용 시행 16건에서 거짓 완료는 관측되지 않았다. 2회차의 YouTube 검색창과 Chrome 설정은 목표에 도달하지 못한 채 앱 로그에 `confirm_result`가 나타났고, 네이티브 검증 근거는 없었다. 사용자가 보는 결과 질문과 기술적으로 검증된 완료를 구분해야 한다.

## 중간 단계에서 확인한 점

- **Goal Type과 인계.** 실제 요청 큐를 거친 주 실험 16회의 해석 HTTP 시간 중앙값은 270ms였다. 설정 4회는 모두 기대한 `settings.navigation.display` 또는 `settings.navigation.wifi`를 반환했다. 앱 요청 12회는 전용 유형 미지원 10회, 추가 확인 2회(Chrome 설정)였고 모두 요청한 앱의 범용 컨트롤러까지 진입했다. 강제로 그래프를 생략한 4회는 해석 분모에서 제외했다.
- **Qwen 하위 목표.** 호출이 확인된 Qwen 턴은 34회였고, 모델 진단에 기록된 지연 중앙값은 1.79초였다. 범용 16개 시행 중 호출과 함께 비어 있지 않은 첫 계획을 관찰한 것은 9개였다. Chrome 설정 1회는 ‘메뉴 열기 → 설정 선택’, Wi-Fi 1회는 ‘연결 → Wi-Fi’로 필요한 조작 두 개를 모두 담았다. 다른 Wi-Fi 시행은 ‘연결 → Wi-Fi 화면 확인’으로 중간 탭 조작이 빠졌지만 후속 턴에서 목적을 달성했다. 디스플레이 2회 계획은 ‘목록 탐색’만 담았다. 나머지 4회는 한 단계 요청을 그대로 나타낸 문구였다. 서버는 단순 요청에서 원문으로 하위 목표를 만들기도 한다. 이 4개를 모델이 자체적으로 분해한 실적으로 세지 않았다.
- **버튼 선택.** Qwen의 첫 제안이 탭이고 허용 목록에서 실제 버튼 이름을 확인할 수 있던 7회는 모두 기대한 컨트롤을 골랐다. 나머지 시행에는 스크롤, 로컬 처리, 모델 미호출이 포함된다. 이는 Qwen의 관찰 가능한 첫 탭에 대한 조건부 수치다.
- **도착 후 반복.** YouTube Shorts는 도착 후 새 동작 ID로 같은 탭을 누르는 제안이 36회와 33회 더 승인됐다. 시계는 스톱워치·타이머 모두 두 번씩 도착했지만 완료 신호를 내지 못했다. 스톱워치에서는 요구한 결과가 입증되지 않았다는 `outcome_requirements_unproven`이 기록됐다.
- **등록 경로와 시험 도구.** 설정 등록 경로에서는 목표 좌표를 얻었지만 측정 옵션을 끈 APK여서 안내를 실제로 그렸더라도 시험 도구가 다음 동작을 허용할 수 없었다. 이 네 시행으로 첫 UI 선택의 정확도나 제품 성공률을 산출할 수 없다. Chrome 메뉴 2회는 앱 열기 제안 상태에 머물렀다. 일반 앱 시험 도구의 승인 목록은 앱 안의 탐색 버튼으로 제한돼 있어 이 결과만으로 제품의 메뉴 선택 능력을 판단하기 어렵다.

## Jev의 UI 선택

같은 기기에서 네 앱의 접근성 트리를 새로 읽고 공개 메뉴 이름만 제공했다. 설정과 Chrome은 후보가 각각 한 개뿐이어서 네 문항을 채점할 수 없었다. 나머지 네 문항에서 Jev가 실제로 호출됐다. 정답 후보가 있던 세 문항(시계 타이머, YouTube Shorts·검색)은 3/3 정확했다. 스톱워치 컨트롤은 추출된 후보에 없었고 Jev는 신뢰도 기준에서 선택을 보류했다. 이 검사는 Jev의 선택 능력과 후보 추출의 누락을 분리하며, 제품 내 모든 UI를 Jev가 골랐다는 뜻으로 해석할 수 없다. ## 추가 검증

- **요청의 서버 종료.** 별도 계정에서 Chrome 설정과 YouTube 검색창을 처음부터 다시 실행했다. 두 요청 모두 목적 화면과 제품 검증이 일치해 실제 ‘네, 됐어요’ 버튼을 눌렀고, 해당 요청 ID의 조회 결과가 각각 `COMPLETED`였다. 확인 후 서버 조회까지 Chrome 18.7초, YouTube 16.0초였다. 이 두 과제는 앞서 성공했던 사례에서 고른 후속 검사다.
- **설정 등록 경로.** 시작 시점부터 자동 모드를 켜 다시 실행해도 디스플레이와 Wi-Fi 모두 도착 전에 ‘도움 필요’ 상태로 종료됐다(각각 23.8초, 23.7초). 이 두 건에서는 첫 테두리를 기다리는 시험 조건을 제거해도 실패가 재현됐다. 이 기록으로 어떤 Jev 후보가 잘못 뽑혔는지 특정할 수는 없다.
- **선택된 탭 판정 수정 후.** 실험 도중 배포 브랜치에 들어온 Android ad84ef51로 스톱워치와 Shorts를 각각 한 번 재실행했다. Shorts는 탭 한 번, 4.60초에 실제 도착, 5.22초에 제품 검증, 5.79초에 서버 `COMPLETED`까지 도달했다. 스톱워치는 6.82초에 도착하고도 75초 안에 완료되지 않았다. 스톱워치의 후속 Qwen 응답에 `outcome_requirements_unproven`이 남았다. 각 한 건의 결과로 전체 앱에 대한 개선율을 추정하지 않았다.
- **쿠팡 카테고리.** 최초 2회는 Goal Type 해석 후 테스트가 신형 요청 확인 화면을 승인하지 않아 도구 실패로 분리했다. 확인 동작을 고친 2회 모두 `coupang.category.browse`가 수락됐다. 그러나 75초 동안 제품 강조 위치와 일치해 승인할 수 있는 ‘카테고리’ 버튼이 관찰되지 않았고, 목적 화면과 완료도 0/2였다. 이 증거로는 후보 추출, 모델 선택, 강조 표시 중 어느 하나를 단독 원인으로 지목할 수 없다.

총 30회에는 주 실험 20회, 최초 쿠팡 도구 실패 2회, 완료 버튼 후속 검사 2회, 설정 자동 모드 대조 2회, 새 Android 빌드의 탭 재검증 2회와 승인 도구 수정 후 쿠팡 재검사 2회가 포함된다. Jev 단독 8문항은 이 분모에서 제외했다. 각 실험 뒤 전용 앱과 USB 중계를 정리하고 기존 접근성 서비스 목록을 확인했다. 실험용 앱 APK의 SHA-256은 주 실험용 `5636af17264d87b5e75d1f3548e338a06e8bd53bbb85066dee38d19cbb0340bb`, Android 재검증용 `868d0314d1df6eda80e4d1ec55f57fc45e47ee4e2fd61a62eb85b17b8157e0d7`이다.
