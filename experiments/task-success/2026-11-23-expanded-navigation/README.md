# Galaxy Note20 앱 탐색과 완료 확인

2026년 11월 23일, 전화·갤러리·캘린더·연락처·내 파일·Play 스토어·시스템 설정·Chrome에서 새 탐색 과제 13개를 선정했다. 이전에 통과한 시계 타이머와 YouTube 검색창을 별도 대조군으로 두었다. 각 과제를 외부 모델을 끈 조건과 Qwen을 연결한 조건에서 각각 두 번 시험했다.

**Qwen 연결 조건에서 26회 중 19회(73%)가 목표 화면에 도착했고 12회(46%)가 정확한 완료 확인까지 이어졌다.** 도착한 19회 중 7회는 완료 확인이 빠졌다. 도착하지 못한 7회 중 2회는 Chrome 검색창의 거짓 완료였다.

## 완료 확인이 갈린 화면

- **갤러리 앨범과 Play 스토어 검색 탭**은 Android에서 선택됐지만 CLICK이 확인에 쓰는 화면 정보에서 해당 이름은 일반 텍스트로 분류됐다. 갤러리에서는 텍스트에도 선택 표시가 남았고, Play 스토어에서는 선택 표시가 상위 요소에 있었다. 기기 판정은 탭이나 버튼으로 분류된 요소의 선택만 인정한다. 두 과제 모두 클릭 후 기기 로그에 새 화면을 관측한 `not_observed`가 반복됐다. [화면 요소 변환](../../../Frontend/app/src/main/java/com/click/data/snapshot/AppTaskObservation.java#L180) · [선택 판정](../../../Frontend/app/src/main/java/com/click/service/overlay/AppTaskOutcomes.java#L169)
- **Chrome 검색창**은 누르기 전의 새 탭 검색 상자와 누른 후의 실제 주소 입력칸이 모두 `editable text_field`로 전달됐다. 기기는 같은 창에서 두 번 관측하고 완료를 표시했지만, 시작 화면에는 포커스를 받은 `url_bar`가 없었다. 외부 모델을 끈 두 시험의 완료 신호는 시작 후 각각 718ms, 661ms였고 실행된 탭은 0회였다. [검색 컨트롤 분류](../../../Frontend/app/src/main/java/com/click/data/snapshot/AppTaskObservation.java#L38) · [입력칸 완료 조건](../../../Frontend/app/src/main/java/com/click/service/overlay/AppTaskOutcomes.java#L169)
- **내 파일 설정**의 Qwen 1차 시험에서는 메뉴와 설정을 차례로 눌러 설정 화면에 도착했다. 서버가 완료 후보를 보냈지만 기기가 화면 변경을 감지해 후보를 폐기했고, 컨트롤러 시작 후 75초가 될 때까지 확인을 받지 못했다. 2차에서는 첫 실행 안내 전에 서버가 `outcome_requirements_unproven`을 반환했다. [기기의 완료 후보 재검사](../../../Frontend/app/src/main/java/com/click/service/overlay/AppTaskController.java#L666)
- **Chrome 메뉴**는 Qwen 시험에서 두 번 모두 열렸고 기기 판정은 계속 `unknown`이었다. 2차에서는 도착이 6,206ms에 확인된 뒤 7,243ms에 제안한 추가 탭이 이 과제의 허용 경로 밖이라 테스트가 실행을 막았다. **Chrome 설정**은 두 번 모두 첫 탭을 실행했지만 설정 화면에 도착하지 못했다. 설정 화면을 직접 열고 새 요청을 시작한 독립 시험에서는 기기가 완료를 확인했다.
- **전화 최근기록**은 키패드 탭에서 시작했다. CLICK은 키패드를 `protected`로 판정해 첫 실행 안내 전에 멈췄다.

## 측정 방법

제품 소스는 `2e369a4a`, 기기는 Android 13의 Samsung Galaxy Note20 SM-N981N이다. 두 조건에 같은 제품 APK를 사용했다. 기기는 USB로 연결하고 개발기에서 같은 소스의 백엔드를 실행했다. 각 조건에서 독립된 메모리 데이터베이스와 시험 계정을 사용했다. 운영 서버에서 측정한 24/36은 서버, 진입점과 과제 구성이 다른 별도 실험이다.

- 대상 앱을 앞에 띄우고 목표가 아직 충족되지 않았는지 Android 접근성 트리로 확인한 후 실제 `AppTaskController`를 시작했다. 시험이 제품이 제안한 공개 탐색 동작을 승인했다. 기록한 시간의 원점은 컨트롤러 시작이다.
- **도착**은 Android가 직접 보여 주는 선택 탭, 편집 가능한 입력칸, 메뉴 목록 또는 대상 화면의 표식을 500ms 이상 연속해 관측한 경우다. 예를 들어 내 파일 다운로드는 홈 타일 대신 현재 경로에 표시된 ‘다운로드’, Chrome 검색은 실제 주소 입력칸의 포커스로 확인했다.
- **정확한 완료**는 실제 탭을 실행해 도착한 상태에서 CLICK이 `confirm_result`와 기기 증거 `device_observation/verified`를 제시한 경우다. 같은 요청의 두 개의 새 화면 관측 기록도 대조했다. 사용자가 최종 확인 버튼을 누르기 직전까지 측정했다. **거짓 완료**는 완료 표시 순간과 400ms 후에 모두 실제 목표가 없었던 경우다.
- 새 과제와 대조군 15개 모두에서 시작 화면은 도착 판정에 실패했고, 수동으로 목적지를 열면 15/15 통과했다. Chrome 설정은 Android 공통 제목 ID인 `android:id/title`을 사용하도록 측정기를 교정한 뒤 확인했다. 별도로 실패한 8개 목표를 직접 연 뒤 외부 모델을 끈 상태에서 새 요청의 완료 판정만 살폈다. 이 조건에서 8/8이 목표 화면이었고, CLICK이 확인한 건 캘린더 검색창·Chrome 검색창·Chrome 설정 3/8이었다. [독립 도착 판정과 과제 목록](../../../Frontend/app/src/androidTest/java/com/click/data/remote/ExpandedNavigationCases.java) · [실기기 러너](../../../Frontend/app/src/androidTest/java/com/click/data/remote/LiveAppTaskAuditTest.java)
- 외부 호출에는 기존 OpenRouter `qwen/qwen3.8-flash` 어댑터와 `APP_TASK_OPENROUTER_COMPACT=1`을 사용했다. 두 서버 모두 앱 탐색 그래프의 백그라운드 처리를 껐다. 완료 조건 생성, 계획 생성, 재호출을 모두 집계했다. 매 호출을 전송 전에 SQLite 트랜잭션으로 예약하고 시험 전체 15회, 단일 시도 4회로 제한했다. 외부 호출이 필요했던 4개 과제를 먼저 두 번씩 실행했다. 나머지 과제의 재실행에서도 실제 모델 호출 수와 제한에 걸린 요청 수를 확인했다.

## 재현과 기록

테스트 러너는 `auditSet=expanded`, `auditRepeats=2`를 사용한다. `auditTask`에 쉼표로 구분한 과제 ID를 지정해 같은 과제만 실행할 수 있다. `calibrateDestinations=true`는 수동 도착 점검, `auditAtDestination=true`는 이미 도착한 상태에서 기기의 완료 확인만 시험한다. 각 시험의 단계별 시간과 기기 판정, 제공자 호출 기록을 확인할 수 있다. [측정 데이터](result.json)
