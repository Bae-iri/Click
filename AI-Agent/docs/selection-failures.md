# 화면 선택 실패와 복구 계약

Primary 선택 실패는 `ui_selection.failure`와 `recovery.failure`에 다음 정보를 유지한다.

| 필드 | 의미 |
| --- | --- |
| `stage` | 관찰, 후보 생성, 설정, 요청 준비, 공급자 호출, 응답 검증, 모델 선택, 실행 검증 중 실패한 단계 |
| `cause` | 원래 실패 원인. 예: `candidate_limit`, `no_candidates`, `network_error`, `abstained` |
| `retryable` | `required_change`가 충족된 뒤 재시도가 가능한지 |
| `required_change` | 재시도에 필요한 관측·사용자 판단·서비스 상태의 변화 |
| `outcome_uncertain` | 이미 실행한 조작의 결과가 아직 불확실한지 |
| `reason_code`, `next_action` | 원인에 대응하는 복구 코드와 행동 |

`MODEL_ABSTAINED`는 모델을 호출하고 유효한 보류 응답을 받은 경우에만 생성한다.
알 수 없는 상태나 호출 전의 `abstained`는 `SELECTION_FAILED`로 처리한다.
일시 정지된 다음 turn의 `called=false`는 해당 turn에서 새로 호출하지 않았다는 뜻이며,
이때 `failure`는 최초 실패의 사실을 보존한다.

| 원인 | 필요한 변화와 복구 |
| --- | --- |
| 후보 또는 입력 크기 초과 | `narrow_observation`: 하위 메뉴를 열어 보이는 범위를 줄인 뒤 재판단 |
| 후보 없음 | `new_target_evidence`: 목록 이동 또는 메뉴 이동으로 대상의 증거 확보 |
| 후보 중복, 낮은 확신, 모델 보류 | `user_clarification`: 사용자에게 원하는 메뉴를 묻고 직접 연 메뉴에서 재판단 |
| 네트워크 오류 | `connection_restored`: 연결 복구를 안내하고 명시적 확인 후 연결 재검사 |
| 공급자 오류·설정 누락·잘못된 응답 | 필요한 서비스 복구를 안내하고 명시적 확인 후 재검사 |
| 조작 결과 불명·안정화 대기 | 새 결과 증거 또는 안정화 시간 확보. 선택 실패만으로 조작을 반복하지 않음 |

관측 ID나 시간만 바뀐 동일 화면은 새로운 선택 근거가 아니다. 화면·대상 조건이 필요한 실패는
관측 지문이 바뀌기 전까지 모델을 다시 호출하지 않는다. 재시도 버튼만으로도 풀리지 않는다.
공급자 복구는 화면 변화로 판단할 수 없으므로 사용자가 복구 후 명시적으로 확인할 때 재검사한다.
이 확인 자체가 연결 복구 성공을 증명하지는 않는다. 다시 실패하면 같은 원인으로 대기한다.

범위 축소와 모호성 해소는 현재 앱에서 사용자가 메뉴를 직접 열어 수행한다.
서버가 근거 없이 후보를 잘라내거나 모델 대신 대상을 선택하지 않는다.
기존 목록 탐색의 `TARGET_NOT_VISIBLE` 같은 복구 코드는 유지하면서 `failure`에 원래 원인을 남긴다.
체크포인트, 응답, 개인정보 필터를 거친 진단 기록에서도 동일한 실패 정보를 보존한다.
